
# 추상화

## 추상화란

추상화는 복잡한 내부 구조를 감추고 외부에 꼭 필요한 기능만을 명확하고 간결하게 보여주는 설계의 핵심 원리이다.  
우리가 프로그램을 만들 때 모든 상세 내용을 하나씩 드러내기보다는, 사용자가 알아야 할 본질적인 것만 제공하여 이해와 사용을 쉽게 만드는 전략이라 할 수 있다.

이렇게 하면 소프트웨어가 더욱 깔끔하고 유지보수하기 쉬우며 변화하는 요구에도 유연하게 대응할 수 있다.  
마치 자동자를 운전할 때 엔진의 복잡한 작동원리를 몰라도 핸들과 페달만 조작하면 되는 것처럼 핵심 인터페이스만 노출시켜 불필요한 혼란을 줄이는 것과 같다.

추상 클래스는 완성되지 않은 설계도로, 공통적으로 사용되는 기능은 직접 구현하고 구체적으로 개별 클래스마다 달라져야 할 부분은 구현하지 않고 비워둔다.  
이 비워진 부분을 '추상 메소드'라고 하며, 자식 클래스에서는 반드시 이 메서드를 구체적으로 완성해야 한다. 이를 통해 개발자는 코드의 일관성을 지키면서도 세부 구현에 유연성을 제공할 수 있다.

## 예시 코드
```
abstract class Vehicle {

    String model;

    public void startEngine() {
        System.out.println(model + " 엔진이 시동됩니다.");
    }

    public abstract void move()​;  // 자식 클래스 각자가 다르게 구현해야 하는 추상 메서드
}

class Car extends Vehicle {
    @Override
    public void move()​ {
        System.out.println("자동차가 도로를 주행합니다.");
    }
}
```

## 인터페이스(interface)란?

인터페이스는 동작해야 하는 기능 목록을 정의한 계약서와 같다.  
자체적으로 메서드 실행 내용을 포함하지 않고, 그 기능들이 반드시 구현되어야 한다는 규칙만 정한다.  
여러 개의 인터페이스를 동시에 구현할 수 있어 다양한 기능을 조합해 객체를 설계하는 데 특히 유용하다.

인터페이스의 사전적 정의는 서로 다른 두 개의 시스템, 장치 사이에서 정보나 신호를 주고받는 경우의 접점이나 경계면이다.  
즉 인터페이스란 일종의 매게체이자 '소통하기 위한 접점'이며, 개발자에겐 통신과 상호작용을 위해 정해둔 약속의 개념이다.(소프트웨어 인터페이스)  
또한 사용자가 기기를 쉽게 동작시키는 데 도움을 주는 상호작용 시스템을 의미한다.(유저 인터페이스)  
이를 OCP에 접목시켜 보면 '객체의 내부 구현이 어떻든 깊이 학습할 필요 없이 원하는 메소드만 호출하고 결과값을 제대로 받게 해주는 간편한 상호작용 기능'이라 할 수 있다.


## 추상 클래스와 인터페이스의 차이점

추상 클래스는 공통 데이터나 기본 구현을 포함할 수 있으며, 단일 상속만 가능해 구조가 비교적 엄격하다.  
반면에 인터페이스는 구현 내용이 없고, 여러 인터페이스를 한 클래스가 다중으로 구현할 수 있어 훨씬 융통성 있는 설계가 가능하다.
실질적으로 공통 속성과 기능이 융합되어야 한다면 추상 클래스를, 다양한 역활가 기능을 자유롭게 조절하고 싶다면 인터페이스를 사용하는 것이 적절하다.  
이를 통해 개발자는 요구사항과 상황에 맞춰 최적의 추상화 도구를 선택할 수 있다.

# 캡슐화

캡슐화는 객체지향 프로그래밍에서 매우 중요한 개념으로, 데이터의 안정성과 프로그램의 견고함을 높이는 핵심 기술이다.

## 캡슐화(Encapsulation)란?

캡슐화는 프로그램 내에서 중요한 데이터와 그것을 다루는 메서드를 하나의 단위로 묶어 외부의 무분별한 접근을 차단하는 방법이다.  
이 원칙을 통해 데이터가 임의로 변형되거나 잘못 다뤄지는 것을 방지하고, 프로그램의 안정성을 높일 수 있다.

## 접근 제한자의 역할

캡슐화 구현을 위해 데이터를 보호하는 첫걸음은 접근 제한자를 적절히 사용하는 것이다.  
- 공개(public) : 어디에서나 접근할 수 있다
- 보호(protected) : 같은 패키지나 상속받은 클래스에서 접근할 수 있게 한다
- 내부(internal) : 같은 패키지 내에서만 허용한다
- 비공개(private) : 가장 엄격하게 데이터 접근을 막아 해당 클래스 내부에서만 조작하도록 한다

## 데이터 보호와 조작의 공식적 통로, 게터와 세터

데이터 필드를 private으로 선언하고, 데이터를 읽거나 수정할 때에는 public 메서드인 게터(getter)과 세터(setter)를 사용한다.
- setter는 데이터를 수정할 때 유효성 검사를 포함해 잘못된 값이 들어가지 않도록 보호 역할을 한다.
- getter는 외부에 데이터를 안전하게 제공하는 역할을 한다.

## 예시 코드
```
public class User {

    private int age; // 외부로 직접 접근 불가

    public void setAge(int age) {
        if(age >= 0 && age <= 120) {
            this.age = age;
        } else {
            System.out.println("나이가 올바르지 않습니다.");
        }
    }

    public int getAge() {
        return age;
    }
}
```

## 캡슐화가 주는 장점

캡슐화는 단순히 데이터를 숨기는 것에 그치지 않고, 코드 유지 보수성을 높이고, 프로그램의 복잡성을 줄여준다.  
내부 동작을 숨김으로써 개발자는 구현 방식 변경 시 외부에 영향을 최소화할 수 있고, 협업 시에도 각자의 역할에 맞게 안전하게 작업할 수 있는 환경을 조성한다.  
또한 데이터 무결성이 보장되어 예기치 않은 오류 발생을 감소시킨다.

# 다형성

## 다형성이란

다형성이란 '여러 가지 형태를 가질 수 있는 능력'을 뜻한다. 프로그래밍에서는 하나의 부모 타입으로 여러 자식 객체를 다룰 수 있다는 뜻이다.  
이렇게 하면 다양한 객체들을 '통일된 인터페이스'로 제어할 수 있어 코드가 훨씬 유연해지고, 확장성과 유지보수성이 좋아진다.

## 다형성의 작동 원리

부모 클래스 또는 인터페이스 타입의 변수에 자식 클래스 객체를 할당해서 사용하는 것을 말한다.  
이렇게 하면 프로그램이 다양한 객체를 부모 타입 하나만으로 활용할 수 있다.

중요한 점은 부모 타입 변수를 통해 접근할 수 있는 기능은 부모 클래스나 인터페이스에 선언된 메서드에 한정된다는 사실이다.  
자식 클래스만의 고유 메서드를 사용하기 위해서는 별도로 형변환(casting)을 해야 한다.

## 다형성의 장점

- 유지보수의 용이 : 코드를 한 곳에서 관리하기 때문에 수정이 편하다
- 확장성이 강하다 : 새로운 자식 클래스를 만들어도 기존 코드를 거의 바꾸지 않아도 된다.
- 코드 중복 최소화 : 비슷한 기능을 공유하니 코드가 깔끔해지고 중복을 줄인다.

## 예시 코드
```
// 부모 클래스
class Animal {
    void sound() {
        System.out.println("동물이 소리를 냅니다.");
    }
}

// 자식 클래스 - 고양이
class Cat extends Animal {
    @Override
    void sound() {
        System.out.println("야옹~");
    }
}

// 자식 클래스 - 개
class Dog extends Animal {
    @Override
    void sound() {
        System.out.println("멍멍!");
    }
}

public class PolymorphismExample {
    public static void main(String[] args) {
        // 부모 타입 변수에 자식 객체 대입(다형성)
        Animal myCat = new Cat();
        Animal myDog = new Dog();

        myCat.sound();  // 출력: 야옹~
        myDog.sound();  // 출력: 멍멍!

        // 다형성의 강점 - 배열에 여러 동물 저장 가능
        Animal[] animals = {myCat, myDog};
        for(Animal animal : animals) {
            animal.sound();  // 각각 고양이, 개의 소리를 냄
        }
    }
}
```

## 매개변수와 반환 타입에서의 다형성 예시
```
public class Farm {
    // 매개변수를 부모 타입으로 선언 - 고양이도 강아지도 인자로 가능
    void makeSound(Animal animal) {
        animal.sound();
    }

    // 부모 타입을 반환형으로 사용
    Animal getAnimal(String type) {
        if(type.equals("cat")) {
            return new Cat();
        } else if(type.equals("dog")) {
            return new Dog();
        } else {
            return new Animal();
        }
    }

    public static void main(String[] args) {
        Farm farm = new Farm();

        Animal animal = farm.getAnimal("cat");
        farm.makeSound(animal);  // 야옹~

        animal = farm.getAnimal("dog");
        farm.makeSound(animal);  // 멍멍!
    }
}
```

# 상속, 위임, 구성, 집합

객체지향 프로그래밍에서는 객체 간의 관계를 설계하는 방법이 매우 중요하다.

특히 **상속(Inheritance)**, **위임(Delegation)**, **구성(Composition)**, **집합(Aggregation)** 은 객체 간의 관계를 표현하는 대표적인 방법이며, 게임 개발에서도 매우 자주 사용된다.

좋은 객체지향 설계는 가능한 한 **상속보다 구성과 위임을 우선적으로 사용**하며, 필요한 경우에만 상속을 사용하는 것이 일반적이다.

---

# 상속(Inheritance)

## 상속이란?

상속(Inheritance)은 **기존 클래스의 기능과 데이터를 새로운 클래스가 물려받는 관계**이다.

즉,

> **"A는 B이다 (Is-A 관계)"**

를 표현할 때 사용한다.

상속을 사용하면 부모 클래스의 변수와 함수를 자식 클래스가 그대로 사용할 수 있으며, 필요한 기능만 추가하거나 재정의(Override)할 수 있다.

---

## 게임 예시

RPG 게임을 만든다고 가정해 보자.

모든 캐릭터는

- 체력
- 이동
- 공격

기능을 가지고 있다.

이를 부모 클래스로 만들 수 있다.

```csharp
public class Character
{
    public int HP;

    public virtual void Attack()
    {
        Debug.Log("기본 공격");
    }
}
```

플레이어

```csharp
public class Player : Character
{
    public override void Attack()
    {
        Debug.Log("플레이어 공격");
    }
}
```

적

```csharp
public class Enemy : Character
{
    public override void Attack()
    {
        Debug.Log("적 공격");
    }
}
```

관계는 다음과 같다.

```text
Character
   ▲
   │
 ┌─┴─────┐
 │        │
Player  Enemy
```

Player와 Enemy는 모두 Character의 기능을 상속받는다.

---

## 장점

- 코드 재사용이 쉽다.
- 공통 기능을 한 곳에서 관리할 수 있다.
- 다형성을 사용할 수 있다.

---

## 단점

- 부모 클래스와 강하게 결합된다.
- 부모가 변경되면 자식도 영향을 받는다.
- 상속 구조가 깊어질수록 유지보수가 어려워진다.

예를 들어

```text
Character
    │
Humanoid
    │
NPC
    │
Merchant
    │
QuestMerchant
```

처럼 상속이 깊어질수록 구조를 이해하기 어려워진다.

---

## 언제 사용하는가?

다음과 같은 경우 사용한다.

- Player는 Character이다.
- Enemy는 Character이다.
- Boss는 Enemy이다.

즉, **명확한 Is-A 관계**일 때 사용하는 것이 좋다.

---

# 위임(Delegation)

## 위임이란?

위임(Delegation)은

> **자신이 해야 하는 일을 다른 객체에게 맡기는 설계 방식**이다.

객체는 직접 기능을 구현하지 않고, 해당 기능을 담당하는 객체에게 작업을 전달한다.

즉,

> **"내가 하지 않고 다른 객체가 대신 한다."**

라는 개념이다.

---

## 게임 예시

플레이어가 공격한다고 해서 공격 로직을 Player가 직접 구현할 필요는 없다.

공격은 AttackSystem이 담당하도록 만들 수 있다.

```csharp
public class AttackSystem
{
    public void Attack()
    {
        Debug.Log("공격");
    }
}
```

Player

```csharp
public class Player
{
    private AttackSystem attackSystem = new AttackSystem();

    public void Attack()
    {
        attackSystem.Attack();
    }
}
```

실제로 공격을 수행하는 것은 AttackSystem이다.

Player는 단지 요청만 한다.

관계는 다음과 같다.

```text
Player
   │
   ▼
AttackSystem
```

---

## Unity에서 자주 사용하는 예

```text
Player
 ├── PlayerMovement
 ├── PlayerAttack
 ├── PlayerAnimation
 └── PlayerHealth
```

Player는

```csharp
movement.Move();
attack.Attack();
health.TakeDamage();
animation.PlayRun();
```

처럼 각 기능을 담당하는 객체에게 일을 맡긴다.

---

## 장점

- 기능을 쉽게 교체할 수 있다.
- 테스트하기 쉽다.
- 책임이 명확하게 분리된다.
- 유지보수가 쉽다.

---

## 단점

- 객체 수가 많아질 수 있다.
- 처음에는 구조가 조금 복잡하게 느껴질 수 있다.

---

# 구성(Composition)

## 구성이란?

구성(Composition)은

> **객체가 다른 객체를 자신의 일부로 소유하는 관계**이다.

즉,

> **"Has-A 관계"**

를 의미한다.

구성에서는 포함된 객체의 생명주기가 상위 객체와 함께한다.

상위 객체가 삭제되면 포함된 객체도 함께 삭제된다.

---

## 게임 예시

플레이어는

- 체력
- 이동
- 인벤토리

를 가진다.

```csharp
public class Health
{
}

public class Inventory
{
}

public class Player
{
    private Health health = new Health();
    private Inventory inventory = new Inventory();
}
```

관계

```text
Player
 ├── Health
 └── Inventory
```

Player가 삭제되면

Health와 Inventory도 함께 사라진다.

---

## Unity에서의 구성

Unity는 구성 기반(Component-Based Architecture)을 사용하는 대표적인 엔진이다.

```text
Player(GameObject)
 ├── Transform
 ├── Rigidbody
 ├── CapsuleCollider
 ├── PlayerMovement
 ├── PlayerAttack
 ├── PlayerHealth
 └── Animator
```

각 기능은 독립적인 컴포넌트이다.

Player는 이들을 조합하여 하나의 캐릭터를 만든다.

---

## 장점

- 기능을 자유롭게 조합할 수 있다.
- 재사용성이 매우 높다.
- 상속보다 유연하다.
- Unity에서 가장 권장되는 방식이다.

---

## 단점

- 객체 수가 증가한다.
- 객체 간 협력이 많아질 수 있다.

---

# 집합(Aggregation)

## 집합이란?

집합(Aggregation)은

> **객체가 다른 객체를 참조하지만 소유하지는 않는 관계**이다.

역시 Has-A 관계이지만,

구성과 가장 큰 차이는

> **생명주기를 공유하지 않는다.**

이다.

즉,

참조 대상 객체는 독립적으로 존재할 수 있다.

---

## 게임 예시

파티 시스템을 생각해 보자.

```csharp
public class Character
{
}

public class Party
{
    public List<Character> Members = new();
}
```

Party는 Character를 가지고 있지만

Character는 Party가 없어도 존재할 수 있다.

관계

```text
Party
 ├── Player
 ├── Mage
 └── Healer
```

Party가 해체되어도

Player와 Mage는 계속 존재한다.

---

## 또 다른 예시

길드

```text
Guild
 ├── Player1
 ├── Player2
 ├── Player3
```

길드가 삭제되어도

플레이어는 삭제되지 않는다.

---

## 장점

- 객체를 공유할 수 있다.
- 생명주기가 독립적이다.
- 유연성이 높다.

---

## 단점

- 참조 관계를 잘 관리해야 한다.
- 객체가 이미 삭제되었는지 확인하는 로직이 필요할 수도 있다.

---

# 구성과 집합의 차이

구성과 집합은 둘 다 **Has-A 관계**이지만 가장 큰 차이는 **생명주기**이다.

### 구성

```text
Player
 ├── Health
 ├── Inventory
 └── Attack
```

Player가 삭제되면

Health도 함께 삭제된다.

즉,

**생명주기를 공유한다.**

---

### 집합

```text
Party
 ├── Player
 ├── Mage
 └── Archer
```

Party가 삭제되어도

Player는 그대로 존재한다.

즉,

**생명주기를 공유하지 않는다.**

---

# 상속과 구성의 차이

상속

```text
Character
   ▲
   │
Player
```

Player는 Character이다.

(Is-A)

---

구성

```text
Player
 ├── Health
 ├── Inventory
 └── Attack
```

Player는 Health를 가진다.

(Has-A)

객체지향 설계에서는

> **상속보다 구성을 우선 사용하라(Favor Composition over Inheritance).**

라는 원칙이 매우 유명하다.

상속은 부모 클래스와 강하게 결합되지만,

구성은 필요한 기능만 자유롭게 조합할 수 있기 때문이다.

---

# 위임과 구성의 차이

많은 사람들이 헷갈리는 개념이다.

구성은

> **객체를 소유하는 관계**

이다.

```text
Player
 └── AttackSystem
```

위임은

> **소유한 객체에게 일을 맡기는 행위**

이다.

```csharp
public void Attack()
{
    attackSystem.Attack();
}
```

즉,

- 구성은 **관계(Has-A)** 를 의미하고,
- 위임은 **행동(작업을 맡기는 것)** 을 의미한다.

따라서 대부분의 경우

**구성을 이용하여 객체를 보유하고, 위임을 이용하여 기능을 수행한다.**

---

# 정리

| 관계 | 의미 | 관계 | 생명주기 | 게임 예시 |
|------|------|------|---------|-----------|
| **상속(Inheritance)** | 기능을 물려받는다 | Is-A | 공유 | `Player`는 `Character`이다. |
| **위임(Delegation)** | 일을 다른 객체에게 맡긴다 | Uses | 독립 | `Player`가 `AttackSystem`에게 공격을 맡긴다. |
| **구성(Composition)** | 객체를 자신의 일부로 소유한다 | Has-A | 함께 생성·삭제 | `Player`가 `Health`, `Inventory`를 가진다. |
| **집합(Aggregation)** | 객체를 참조하지만 소유하지 않는다 | Has-A | 독립 | `Party`가 `Player`들을 관리한다. |

# Unity에서 가장 권장되는 설계

Unity에서는 다음과 같은 구조가 가장 많이 사용된다.

```text
Player(GameObject)
│
├── PlayerMovement
├── PlayerAttack
├── PlayerHealth
├── PlayerAnimation
├── Inventory
└── Equipment
```

각 컴포넌트는 하나의 책임만 담당하며,

Player는 필요한 기능을 **구성(Composition)** 으로 보유하고,

실제 작업은 각 컴포넌트에게 **위임(Delegation)** 한다.

이러한 구조는

- 낮은 결합도
- 높은 응집도
- 뛰어난 재사용성
- 쉬운 유지보수

를 모두 만족하기 때문에 현대 Unity 프로젝트에서 가장 권장되는 설계 방식이다.
