
# 객체지향 설계 원칙

어떤 기술은 언제 그 기술을 써야 하고 왜 써야 하는지 아는 것이 사용하는 방법 그 자체보다 더 중요하다.  

많은 개발자들이 디자인 패턴의 중요성을 인식하기 때문에 적극적으로 사용하기 위해 노력하지만 종종 언제, 왜 써야 하는지 모르는 경우도 있다.  

디자인 패턴은 말 그대로 반복적으로 나오는 설계 솔루션이다. 객체지향 기초를 이루는 상속, 추상화, 캡슐화, 다형성과 객체 지향 설계 원칙에 기반해 소프트웨어를 설계하다 보면 반복적으로 나타나는 공통적인 설계 구조가 나온다.  

디자인 패턴을 언제, 왜 써야 하는지, 그리고 어떤 결과를 얻을 수 있는지 분별하려면 객체 지향 기본 요소는 물론이고 객체 지향 설계 원칙을 빠짐없이 이해하고 있어야 한다.  

그에 더해 특정 디자인 패턴이 어떻게 객체 지향 설계 원칙을 준수하고 있는지 이해한다면 제대로 디자인 패턴을 사용하게 될 것이다.

## 클래스 상속을 통한 잘못된 기능 확장

### 1. 클래스를 상속받아 재사용을 하고 서브 클래스가 고유한 행동을 구현하도록 한다

- 필요 없는 메서드 상속 : 필요 없는 함수를 상속받아 영향을 받게 되는 문제가 생길 수 있다. 필요 없는 함수를 사용하지 않기 위해 빈 함수 오버라이드를 해줘야 하는 문제도 생긴다.
- 코드 중복 : 일부 서브 클래스에만 필요한 기능이 있다면 같은 메서드를 각각 오버라이드 해서 구현해야 한다. 코드가 중복되지 때문에 유지 보수하기가 어렵다.
- 실행 중에 동적으로 행동 변경 불가 : 메서드를 상속받게 되면 컴파일 시점에 기능이 결정된다. 실행 중에 기능을 변경하고 싶어도 할 수 없게 된다.
- 확장하기 어려움 : 기능을 추가하게 되면 슈퍼 클래스를 수정하게 될 수 있다. 심지어 다른 서브 클래스들에도 영향을 미칠 수 있다. 이는 OCP 원칙을 어기는 것이고, 확장하기가 어려워진다.

### 2. 특정 기능에 대한 함수를 가진 인터페이스 상속

- 인터페이스는 구현 클래스에서 똑같이 구현해야 하므로 코드 중복이 발생한다.

## 디자인 원칙

### 1. 애플리케이션에서 달라지는 부분을 찾아내고 달라지지 않은 부분에서 분리시킨다.

달라지는 부분을 찾아서 나머지 코드에 영향을 주지 않도록 캡슐화를 한다. 그렇게 하면 나중에 바귀지 않는 부분에 영향을 미치지 않은 채로 그 부분만 고치거나 확장할 수 있다.  

모든 디자인 패턴의 기반을 이루는 원칙이다. 모든 패턴은 시스템의 일부분을 다른 부분과 독립적으로 변화시킬 수 있는 방법을 제공하는 것이기 때문이다.

### 2. 구현이 아닌 인터페이스에 맞춰서 프로그래밍한다.

달라지는 부분에 대한 함수를 가진 인터페이스를 만든다. 그런 다음 그 인터페이스를 구현하는 다수의 구현 클래스로 구성하여 달라지지 않는 부분에 영향을 미치지 않게 한다.  
인터페이스에 맞춰서 프로그래밍하라는 말은 추상 클래스를 사용하지 말라는 의미가 아니다. 여기서 말하는 인터페이스는 프로그래밍 언어에서 지원항는 인터페이스와 개념적인 인터페이스를 말하는 중의적인 표현이다.

중요한 점은 실제 실행 시에 쓰이는 객체가 코드에 의해 고정되지 않도록, 어떤 상위 형식(Supertype)에 맞춰서 프로그래밍함으로써 다형성을 활용하라는 것이다.

### 3. 상속보다는 구성을 활용한다.

클래스 상속으로는 기능을 확장하지 어렵고 문제도 많다. 그러므로 구성을 활용해야 한다.  
구성(Composition)이란 특정 클래스가 인터페이스에 맞춰서 구현된 알고리즘군의 구성요소를 부여받는 것이다.

구성을 활용한 가장 대표적인 패턴은 전략 패턴이다.

### 4. 느슨한 결합(Loose Coupling)

느슨하게 결합되어 있단는 것은 두 개 이상의 객체가 상호작용을 하기는 하지만 서로에 대해 잘 모른다는 것을 의미한다.

서로 상호작용을 하는 객체 사이에서는 가능하면 느슨하게 결합하는 디자인을 사용해야 한다.  
그러면 변경 사항이 생겨도 무난히 처리할 수 있는 유연한 객체지향 시스템을 구축할 수 있다. 객체 사이의 상호의존성을 최소하하기 때문이다.

#### 느슨한 결합의 정의
1. 시스템의 구성 요소가 서로 약하게 연관돼 관계를 떼어낼 수 있고, 그 때문에 한 구성요소에 변화가 생겼을 때 다른 구성요소의 성능이나 존재에 최소한의 영향을 끼치는 상태. (구성요소 간의 결합 양상)
2. 구성요소가 다른 구성요소의 정의에 대해 많은 지식이 없어도 사용할 수 있는 상황. (결합의 양상에 따른 효과와 결합의 범주. 클래스, 인터페이스, 데이터, 서비스 등이 구성요소가 될 수 있음)

#### 느슨한 결합을 어떻게 사용할 수 있는가

1. 프로그래머들에게 익숙한 클래스 단위, 다시 말해 내가 짠 프로그램 수준에서 활용
2. 네트워크와 하드웨어의 발달로 나눠서 짤 수 있는 상황에 어울리는 분산 프로그래밍 형태에서 활용하기
3. 복잡한 일을 조직화할 때 일사불란함을 만들기 위한 도구인 '단위', 그리고 자유로운 여지를 두기 위한 장치인 '경계'를 구축하는 데 활용하기

### 5. 최소 지식 원칙(Principle of Least Knowledge)

정말 친한 친구하고만 이야기하라. 객체 사이의 상호작용은 될 수 있으면 아주 가까운 "친구" 사이에서만 허용하는 것이 좋다.  
어떤 객체든 그 객체와 상호작용을 하는 클래스의 개수에 주의해야 하며, 그런 객체들과 어떤 식으로 상호작용을 하는지에도 주의를 기울여야 한다.

여러 클래스들이 서로 복잡하게 의존하고 있다면 관리하기 힘들고, 남들이 보기에도 이해하기 어려운 불안정한 시스템이 된다.

최소 지식 원칙을 지키는 가이드라인이 있다. 어떤 메서드에서든지 다음 네 종류의 객체 속 메서드만을 호출해야 한다.
1. 객체 자체 (this 또는 self) : 자기 자신의 메서드 호출 가능.
2. 메서드의 매개변수 : 인자로 전달받은 객체의 메서드 호출 가능.
3. 메서드 내에서 생성된 객체: 메서드 내부에서 직접 new 등으로 인스턴스화한 객체의 메서드 호출 가능.
4. 객체의 인스턴스 변수(필드): 해당 클래스가 속성으로 가지고 있는 직속 객체의 메서드 호출 가능

이 가이드라인을 지키면 직접적으로 알고 지내는 객체의 개수가 줄어든다. 그로 인해 객체들 사이의 의존성이 줄어들어 소프트웨어 관리가 용이하다.  
단점도 있는데, 다른 구성요소를 호출하기 위한 래퍼 클래스가 많아진다. 그러다 보면 시스템이 복잡해지고 개발 시간도 늘어나고 성능 또한 떨어질 수 있다.


### 6. 할리우드 원칙(Hollywood Principle)

높은 수준의 모듈간의 상호작용을 관리하기 위해 사용되는 원칙이다.

상위 모듈이 하위 모듈에 의존할 때 상위 모듈은 직접적으로 하위 모듈에 의존하지 말아야 한다.  
즉 구상 클래스로 이루어진 하위 모듈에 의존하는 게 아니라 추상 클래스나 인터페이스로 작성된 추상 클래스 하위 모듈에 의존해야 한다.

또한 하위 모듈이 상위 모듈을 호출하거나 접근해 사용하면 안된다.
