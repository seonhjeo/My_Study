# 아키텍처, 모듈, 프레임워크, 라이브러리, 디자인 패턴 비교

| 구분             | 아키텍처(Architecture)                                              | 모듈(Module)                                                     | 프레임워크(Framework)                                         | 라이브러리(Library)                                        | 디자인 패턴(Design Pattern)                   |
| -------------- | --------------------------------------------------------------- | -------------------------------------------------------------- | -------------------------------------------------------- | ----------------------------------------------------- | ---------------------------------------- |
| **의미**         | 소프트웨어 전체를 어떤 구조로 나누고 각 요소가 어떻게 협력할지를 정의하는 상위 수준의 설계             | 특정 책임이나 기능을 수행하도록 묶은 독립적인 소프트웨어 단위                             | 애플리케이션 개발에 필요한 기본 구조, 실행 흐름, 공통 기능과 확장 지점을 제공하는 개발 기반    | 특정 기능을 재사용할 수 있도록 만들어진 함수, 클래스 또는 코드의 집합              | 반복적으로 발생하는 설계 문제에 대한 일반적이고 검증된 해결 방법     |
| **형태**         | 계층, 모듈 경계, 의존 방향, 데이터 흐름, 통신 규칙 등의 구조와 원칙                       | 네임스페이스, 어셈블리, 패키지, 폴더, 클래스 집합, 서브시스템                           | 실제 실행 가능한 코드, API, 생명주기, 규약, 기반 클래스, 설정 체계               | 함수, 클래스, API, 패키지, DLL, 정적 메서드 등의 코드                  | 클래스와 객체의 관계를 표현한 개념적 구조 또는 설계 지침         |
| **범위**         | 애플리케이션 또는 시스템 전체                                                | 하나의 기능 영역이나 서브시스템                                              | 애플리케이션 전체 또는 특정 기술 영역                                    | 특정 기능이나 기술적 문제                                        | 특정 설계 문제나 객체 간 협력 관계                     |
| **주요 관심사**     | 시스템 분리, 책임 배분, 의존성, 데이터 흐름, 확장성, 유지보수성, 성능, 보안                  | 기능 캡슐화, 독립성, 재사용성, 공개 인터페이스, 의존성 제한                            | 실행 흐름, 제어의 역전, 객체 생명주기, 공통 규약, 확장 지점, 개발 생산성             | 특정 기능의 정확한 수행, 재사용성, 사용하기 쉬운 API                      | 책임 분리, 객체 간 협력, 변경 대응, 결합도 감소, 코드 재사용    |
| **예시**         | 계층형 아키텍처, 클린 아키텍처, 헥사고날 아키텍처, 이벤트 기반 아키텍처, 마이크로서비스              | 전투 모듈, 인벤토리 모듈, 퀘스트 모듈, 저장 모듈, 네트워크 모듈                         | Unity, ASP.NET Core, Spring, Django, VContainer, Zenject | Newtonsoft.Json, MessagePack, `Mathf`, LINQ, 압축 라이브러리 | 전략 패턴, 옵저버 패턴, 팩토리 패턴, 상태 패턴, 어댑터 패턴     |
| **Unity 예시**   | `Presentation`, `Application`, `Domain`, `Infrastructure` 계층 분리 | `Combat`, `Inventory`, `UI`, `Network`, `Save` 어셈블리 또는 UPM 패키지 | Unity 게임 루프, `MonoBehaviour`, VContainer, Photon Fusion  | `JsonUtility`, MessagePack, DOTween, 수학 또는 컬렉션 유틸리티   | 적 AI의 상태 패턴, 무기 교체의 전략 패턴, UI 알림의 옵저버 패턴 |
| **적용 방식**      | 프로젝트 초기에 큰 구조와 의존 규칙을 결정하고 개발 과정에서 유지한다                         | 관련 클래스와 데이터를 하나의 경계로 묶고 외부에는 제한된 인터페이스만 공개한다                   | 프레임워크가 제공하는 규약과 생명주기를 따르고 정해진 확장 지점에 코드를 작성한다            | 개발자가 필요한 시점에 라이브러리의 함수나 클래스를 직접 호출한다                  | 문제 상황에 맞는 패턴을 선택하고 프로젝트 코드에 직접 구조를 구현한다  |
| **실행 흐름의 제어권** | 직접적인 실행 주체라기보다 실행 구조와 방향을 정의한다                                  | 일반적으로 자신에게 전달된 요청을 처리한다                                        | 대체로 프레임워크가 실행 흐름을 제어하고 개발자의 코드를 호출한다                     | 개발자 코드가 라이브러리를 직접 호출한다                                | 구현 방식에 따라 달라지며 패턴 자체는 실행 흐름을 가지지 않는다     |
| **개발자의 구현 여부** | 개발자가 프로젝트 특성에 맞게 직접 설계한다                                        | 개발자가 직접 구현하거나 외부 패키지의 모듈을 사용할 수 있다                             | 핵심 구조는 프레임워크가 제공하고 개발자는 필요한 기능과 확장 부분을 구현한다              | 기능 구현은 라이브러리가 제공하고 개발자는 호출 및 연결 코드를 작성한다              | 패턴은 개념만 제공하므로 개발자가 구체적인 클래스와 관계를 직접 구현한다 |
| **코드 제공 여부**   | 일반적으로 개념과 구조이며 반드시 코드를 제공하는 것은 아니다                              | 실제 코드와 데이터로 구성된다                                               | 실제 코드와 실행 환경을 제공한다                                       | 실제 재사용 가능한 코드를 제공한다                                   | 기본적으로 개념이며 구현 코드는 개발자가 작성한다              |
| **변경 시 영향 범위** | 변경 시 시스템 전체에 큰 영향을 줄 수 있다                                       | 해당 모듈과 직접 의존하는 영역에 영향을 준다                                      | 프레임워크 버전이나 규약 변경 시 이를 사용하는 여러 코드에 영향을 줄 수 있다             | API 변경 시 해당 라이브러리를 호출하는 코드에 영향을 준다                    | 패턴 구조를 변경하면 참여하는 클래스와 객체 관계에 영향을 준다      |
| **핵심 질문**      | 시스템 전체를 어떻게 나누고 연결할 것인가?                                        | 이 기능을 어떤 경계 안에 묶을 것인가?                                         | 애플리케이션을 어떤 규칙과 흐름으로 개발하게 할 것인가?                          | 이 기능을 어떻게 쉽게 재사용할 것인가?                                | 이 반복적인 설계 문제를 어떤 객체 구조로 해결할 것인가?         |

## 관계 정리

```text
아키텍처
 └── 시스템 전체의 구조와 의존 방향을 정의한다.
      │
      ├── 여러 모듈로 시스템을 분리한다.
      │
      ├── 프레임워크를 개발 기반으로 사용할 수 있다.
      │
      ├── 라이브러리를 필요한 기능에 활용할 수 있다.
      │
      └── 내부 클래스 설계에 디자인 패턴을 적용할 수 있다.
```

Unity 게임 프로젝트를 예로 들면 다음과 같이 표현할 수 있다.

```text
게임 아키텍처
├── 전투 모듈
│   ├── 상태 패턴
│   ├── 전략 패턴
│   └── 수학 라이브러리
│
├── UI 모듈
│   ├── MVP 패턴
│   └── UI 프레임워크
│
├── 네트워크 모듈
│   ├── Photon Fusion 프레임워크
│   └── MessagePack 라이브러리
│
└── 저장 모듈
    ├── Repository 패턴
    └── JSON 라이브러리
```

## 핵심 차이

| 개념         | 핵심 표현                         |
| ---------- | ----------------------------- |
| **아키텍처**   | 시스템 전체를 어떻게 나눌 것인가            |
| **모듈**     | 특정 책임을 어디까지 하나로 묶을 것인가        |
| **프레임워크**  | 어떤 구조와 실행 흐름 안에서 개발할 것인가      |
| **라이브러리**  | 필요한 기능을 어떤 코드로 가져다 쓸 것인가      |
| **디자인 패턴** | 반복되는 설계 문제를 어떤 객체 관계로 해결할 것인가 |

가장 간단하게 표현하면 다음과 같다.

```text
아키텍처는 전체 설계도이다.

모듈은 설계도 안에서 구분된 기능 구역이다.

프레임워크는 개발 구조와 실행 규칙을 제공하는 기반이다.

라이브러리는 필요한 기능을 호출해서 사용하는 도구 모음이다.

디자인 패턴은 반복되는 설계 문제를 해결하는 방법이다.
```
