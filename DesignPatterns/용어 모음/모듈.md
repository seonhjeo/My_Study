# 모듈 (Module)

## 모듈이란

모듈이란 소프트웨어 설계에서 기능 단위로 분해해하고 추상회되어 재사용 및 공유 가능한 수준으로 만들어진 단위이다.  
모듈은 그 자체로서 컴파이이 가능한 단위이며, 동시에 여러 다른 모듈의 개발에 사용될 수 있다.

독립성이 높은 모듈일수록모듈을 수정하더라도 다른 모듈들에게는 거의 영향을 미치지 않으며, 오류가 발생해도 쉽게 발견하고 해결할 수 있다.

## 모듈화

모듈화란, 이러한 분해를 강조하여 유지 보수와 타 프로그램에서의 코드 재사용을 손쉽게 하는 소프트웨어 설계 기법을 말한다.  
모듈화를 통해 설계하면 프로그램의 효율적인 관리 및 성능 향상, 전체적인 소프트웨어 이해 용이성 증대 및 복잡성이 감소하는 장점이 있다.  
모듈화의 목표는 모듈 간의 결합도를 최소화하고, 응집도의 최대화를 목표로 한다.


## 하위 모듈과 상위 모듈

상위 모듈
- 전체 시스템의 큰 흐름이나 핵심 비즈니스 규칙(상위 정책)을 다루는 모듈이다.
- 개념적, 비즈니스적 규칙을 바탕으로 한 높은 추상화 정도를 가진다.
- 예시 : 주문 및 결제 처리

하위 모듈
- 상위 정책을 실행하기 위한 구체적인 기능이나 기술적인 세부사항을 다루는 모듈이다.
- 구체적, 기술 중심을 바탕으로 한 낮은 추상화 정도를 가진다.
- 예시 : 데이터베이스에 연결한다. 카드 API에 결제를 요청한다

# 결합도와 응집도

결합도와 응집도는 모듈의 독립성을 측정하는 방식이다.

## 결합도(Coupling)

결합도는 모듈 내부가 아닌 외부의 모듈과의 연관도 또는 모듈 간의 상호의존성을 나타내는 정도로, 소프트웨어 구조에서 모듈 간의 관련성을 측정하는 척도이다.  
결합도는 약할수록 모듈의 독립성이 높아진다.

약한 결합도에서 강한 결합도로 정리된 것은 다음과 같다.
- 자료(Data) 결합도 : 어떤 모듈이 다른 모듈을 호출하면서 매개 변수나 인수로 데이터를 넘겨주고, 호출 받은 모듈은 받은 데이터에 대해 처리 결과를 다시 돌려주는 방식
- 스탬프(Stamp) 결합도 : 두 모듈이 동일한 자료 구조를 조회하는 경우의 결합도이며, 자료 구조의 어떠한 변화, 즉 포멧이나 구조의 변화는 그것을 조회화는 모든 모듈 및 변화되는 필드를 실제로 조회하지 않느 모듈에까지 영향을 미친다.
- 제어(Control) 결합도 : 한 모듈이 다른 모듈의 상세한 처리 절차를 알고 있어 이를 통제하는 경우나 처리 기능이 두 모듈에 분리되어 설계된 경우에 발생한다.
- 외부(External) 결합도 : 어떤 모듈에서 선언한 데이터(변수)를 외부의 다른 모듈에서 참조할 때의 결합도이다.
- 공통(Common) 결합도 : 공유되는 공통 데이터 영역을 여러 모듈이 사용할 때의 결합도이다.
- 내용(Content) 결합도 : 한 모듈이 다른 모듈의 내부 기능 및 그 내부 자료를 직접 참조하거나 수정할 때의 결합도이다.


## 응집도(Cohesion)

응집도는 정보 은닉 개념을 확장한 것으로, 명령어나 호출문 등 모듈의 내부 요소들의 서로 관련되어 있는 정도, 즉 모듈이 독립적인 기능으로 정의되어 있는 정도를 의미한다.  
응집도가 강할 수록 모듈의 품질이 높고, 약할수록 품질이 낮다고 불 수 있다.

응집도가 강한 것부터 약한 것으로 정리된 것은 다음과 같다.
- 기능적(Functional) 응집도 : 모듈 내부의 모든 기능 요소들이 단일 문제와 연관되어 수행될 경우의 응집도
- 순차적(Sequential) 응집도 : 모듈 내 하나의 활동으로부터 나온 출력 데이터를 그 다음 활동의 입력 데이터로 사용할 경우의 응집도
- 교환적(Communication) 응집도 : 동일한 입력과 출력을 사용하여 서로 다른 기능을 수행하는 구성 요소들이 모였을 경우의 응집도
- 절차적(Procedural) 응집도 : 모듈이 다수의 관련 기능을 가질 때 모듈 안의 구성 요소들이 그 기능을 순차적으로 수행할 경우의 응집도
- 시간적(Temporal) 응집도 : 특정 시간에 처리되는 몇 개의 기능을 모아 하나의 모듈로 작성할 경우의 응집도
- 논리적(Logical) 응집도 : 유사한 성격을 갖거나 특정 형태로 분류되는 처리 요소들로 하나의 모듈이 형성되는 경우의 응집도
- 우연적(Coincidential) 응집도 : 모듈 내부의 각 구성 요소들이 서로 관련 없는 요소로만 구성된 경우의 응집도

## 게임을 통한 예시

### 1. 내용 결합(Content Coupling) - 가장 나쁨

한 모듈이 다른 모듈의 **내부 구현이나 데이터를 직접 수정**하는 경우이다.

#### 예시

```csharp
public class Player
{
    public int hp = 100;
}

public class Enemy
{
    public void Attack(Player player)
    {
        player.hp -= 10;
    }
}
```

더 심한 경우에는 Player의 내부 상태를 모두 직접 변경하기도 한다.

```csharp
player.hp = 0;
player.isDead = true;
player.animState = Die;
player.invincible = false;
player.inventory.Clear();
```

#### 문제점

- Player 내부 구현에 강하게 의존한다.
- Player 구조가 변경되면 Enemy도 함께 수정해야 한다.
- 유지보수가 매우 어렵다.

---

### 2. 공통 결합(Common Coupling)

여러 모듈이 **전역 데이터나 Static 데이터를 함께 사용하는 경우**이다.

#### 게임 예시

```csharp
public static class GameData
{
    public static int PlayerHp = 100;
}
```

Enemy

```csharp
GameData.PlayerHp -= 10;
```

Player

```csharp
if (GameData.PlayerHp <= 0)
    Die();
```

#### 문제점

- 누가 데이터를 변경했는지 추적하기 어렵다.
- 버그 발생 시 원인을 찾기 힘들다.
- 전역 데이터가 많아질수록 프로그램이 복잡해진다.

---

### 3. 외부 결합(External Coupling)

여러 모듈이 **같은 외부 시스템이나 라이브러리에 의존하는 경우**이다.

#### 게임 예시

Player와 Enemy가 모두 네트워크 시스템을 사용하는 경우

```csharp
NetworkManager.SendPacket(...);
```

또는 저장 시스템을 사용하는 경우

```csharp
SaveSystem.Save(...);
```

#### 문제점

- 외부 API가 변경되면 모든 모듈을 수정해야 한다.
- 외부 시스템의 영향을 크게 받는다.

---

### 4. 제어 결합(Control Coupling)

한 모듈이 **다른 모듈의 동작을 결정하는 값을 전달하는 경우**이다.

#### 게임 예시

```csharp
player.TakeDamage(10, true);
```

```csharp
public void TakeDamage(int damage, bool playAnimation)
{
    if (playAnimation)
        PlayHitAnimation();
}
```

Enemy가

- 애니메이션 재생 여부
- 무적시간 적용 여부
- 피격 이펙트 여부

등을 결정하게 된다.

#### 문제점

- Enemy가 Player 내부 동작까지 제어하게 된다.
- Player의 책임이 Enemy로 일부 이동한다.

---

### 5. 스탬프 결합(Stamp Coupling)

필요하지 않은 **큰 객체 전체를 전달**하는 경우이다.

#### 게임 예시

```csharp
public class PlayerInfo
{
    public int HP;
    public int MP;
    public int Level;
    public Inventory Inventory;
    public Equipment Equipment;
}
```

```csharp
Attack(PlayerInfo info);
```

Enemy는 HP만 필요한데도 PlayerInfo 전체를 전달받는다.

#### 문제점

- 필요 없는 데이터에도 의존하게 된다.
- PlayerInfo 구조가 변경되면 Enemy도 영향을 받는다.

---

### 6. 자료 결합(Data Coupling) - 가장 좋음

필요한 데이터만 전달하는 방식이다.

#### 게임 예시

```csharp
public interface IDamageable
{
    void TakeDamage(int damage);
}

public class Enemy
{
    public void Attack(IDamageable target)
    {
        target.TakeDamage(10);
    }
}
```

또는

```csharp
TakeDamage(10);
```

처럼 필요한 데이터만 전달한다.

#### 장점

- 모듈 간 의존성이 매우 낮다.
- 내부 구현을 서로 알 필요가 없다.
- 유지보수가 쉽다.
- 객체지향 설계에서 가장 권장되는 방식이다.

---

## 결합도 정리

|결합도|설명|게임 예시|좋은 정도|
|---|---|---|---|
|내용 결합|내부 구현 직접 접근|HP, Inventory 직접 수정|❌ 최악|
|공통 결합|전역 데이터 공유|GameData.PlayerHp|❌|
|외부 결합|외부 시스템 공유|NetworkManager, SaveSystem|△|
|제어 결합|플래그로 동작 제어|TakeDamage(10, true)|△|
|스탬프 결합|큰 객체 전달|PlayerInfo 전달|○|
|자료 결합|필요한 데이터만 전달|TakeDamage(10)|✅ 최고|

---

# 응집도(Cohesion)

> 하나의 모듈이 하나의 책임을 얼마나 잘 수행하는가

응집도는 높을수록 좋은 설계이다.

일반적으로 아래 순서대로 응집도가 높아진다.

```
우연적 응집
↓
논리적 응집
↓
시간적 응집
↓
절차적 응집
↓
통신적 응집
↓
순차적 응집
↓
기능적 응집
```

### 1. 우연적 응집(Coincidental Cohesion) - 가장 나쁨

관련 없는 기능들이 하나의 클래스에 모두 들어있는 경우이다.

#### 게임 예시

```csharp
PlayerManager
{
    Move();
    SaveGame();
    ConnectServer();
    DrawUI();
    PlayBGM();
}
```

#### 문제점

- 클래스 내 메서드들이 서로 아무 관련이 없다.
- 하나의 클래스가 너무 많은 책임을 가진다.
- 수정 시 다른 기능에 영향을 줄 가능성이 높다.

---

### 2. 논리적 응집(Logical Cohesion)

비슷한 성격의 기능들을 하나로 묶은 경우이다.

#### 게임 예시

```csharp
InputManager
{
    HandleKeyboard();
    HandleMouse();
    HandleGamepad();
}
```

#### 특징

- 모두 입력 처리라는 공통점이 있다.
- 하지만 각각의 기능은 서로 독립적이다.

---

### 3. 시간적 응집(Temporal Cohesion)

같은 시점에 실행되는 기능들을 묶은 경우이다.

#### 게임 예시

```csharp
GameStart()
{
    LoadPlayer();
    LoadEnemy();
    LoadMap();
    PlayOpening();
}
```

#### 특징

- 게임 시작 시 실행된다는 공통점으로 묶여 있다.

---

### 4. 절차적 응집(Procedural Cohesion)

실행 순서 때문에 함께 묶여 있는 경우이다.

#### 게임 예시

```csharp
EnemyAI()
{
    FindPlayer();
    Rotate();
    Move();
}
```

#### 특징

- 각 기능은 순차적으로 실행된다.
- 기능 간 데이터 의존성은 크지 않을 수도 있다.

---

### 5. 통신적 응집(Communicational Cohesion)

같은 데이터를 처리하기 때문에 묶여 있는 경우이다.

#### 게임 예시

```csharp
PlayerStatus
{
    Heal();
    TakeDamage();
    RecoverMana();
}
```

#### 특징

- 모두 PlayerStatus 데이터를 사용한다.
- 동일한 데이터를 중심으로 기능이 모여 있다.

---

### 6. 순차적 응집(Sequential Cohesion)

앞 단계의 결과가 다음 단계의 입력이 되는 경우이다.

#### 게임 예시

```csharp
DetectPlayer();

CalculatePath();

Move();
```

#### 특징

- AI 시스템에서 자주 볼 수 있는 구조이다.
- 데이터가 순차적으로 전달된다.

---

### 7. 기능적 응집(Functional Cohesion) - 가장 좋음

하나의 클래스가 하나의 책임만 수행하는 경우이다.

#### 게임 예시

```csharp
Health
```

- 체력 관리만 담당

```csharp
Inventory
```

- 아이템 관리만 담당

```csharp
Movement
```

- 이동만 담당

Player는 이러한 기능들을 조합해서 사용한다.

#### 장점

- 유지보수가 쉽다.
- 테스트하기 쉽다.
- 재사용성이 높다.
- 객체지향 설계에서 가장 권장되는 구조이다.

---

### 응집도 정리

|응집도|설명|게임 예시|좋은 정도|
|---|---|---|---|
|우연적 응집|관련 없는 기능을 한 클래스에 작성|PlayerManager에 모든 기능|❌ 최악|
|논리적 응집|비슷한 종류의 기능을 묶음|InputManager|△|
|시간적 응집|같은 시점에 실행|GameStart()|△|
|절차적 응집|실행 순서 때문에 묶음|EnemyAI()|○|
|통신적 응집|같은 데이터를 처리|PlayerStatus|○|
|순차적 응집|앞 결과가 다음 입력|AI 탐색 → 이동|◎|
|기능적 응집|하나의 책임만 수행|Health, Inventory, Movement|✅ 최고|

---

### 가장 이상적인 게임 전투 구조

```text
Enemy
   │
   ▼
IDamageable
   ▲
   │
PlayerHealth
```

Enemy는 단순히 데미지만 전달한다.

```csharp
target.TakeDamage(10);
```

PlayerHealth는

- 체력 감소
- 피격 애니메이션
- 무적시간
- 사망 처리
- 사운드 재생
- 이펙트 출력

등을 자신의 내부에서 모두 처리한다.

이 구조는

- **자료 결합(Data Coupling)**을 사용하여 결합도가 낮고,
- **기능적 응집(Functional Cohesion)**을 통해 응집도가 높다.

따라서 유지보수와 확장성이 뛰어난 객체지향 설계라고 할 수 있다.
