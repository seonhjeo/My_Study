# 의존성(Dependency)

## 의존성이란?

의존성(Dependency)이란 **하나의 객체가 다른 객체를 사용하거나 필요로 하는 관계**를 의미한다.

쉽게 말해, **A 객체가 B 객체 없이는 자신의 기능을 수행할 수 있다면 A는 B에 의존한다**고 한다.

예를 들어 게임에서 플레이어가 총을 사용한다고 가정해 보자.

```csharp
public class Gun
{
    public void Fire()
    {
        Debug.Log("총 발사");
    }
}

public class Player
{
    private Gun gun = new Gun();

    public void Attack()
    {
        gun.Fire();
    }
}
```

위 코드에서는

- `Player`가 `Gun` 객체를 직접 생성한다.
- `Attack()`을 수행하려면 `Gun`이 반드시 필요하다.

즉, 다음과 같은 의존 관계가 존재한다.

```text
Player ─────▶ Gun
```


### 의존성이 문제가 되는 이유

현재는 문제가 없어 보이지만, 나중에 무기가 다양해지면 Player도 계속 수정해야 한다.

예를 들어 새로운 무기가 추가된다면

```text
권총
샷건
활
레이저건
```

Player 코드도 함께 변경된다.

```csharp
private ShotGun gun = new ShotGun();
```

또는

```csharp
private Bow gun = new Bow();
```

처럼 구현을 수정해야 한다.

이러한 구조에서는

- Player가 무기의 구현을 알아야 한다.
- 새로운 무기가 추가될 때마다 Player를 수정해야 한다.
- Player와 Weapon의 결합도가 높아진다.

즉, **구현에 직접 의존하는 구조는 유지보수성과 확장성이 떨어진다.**


## 의존성 주입(Dependency Injection, DI)

### 의존성 주입이란?

의존성 주입(Dependency Injection, DI)은

> **객체가 필요한 객체를 직접 생성하지 않고 외부에서 전달받는 설계 방식**이다.

즉,

> **"내가 만들지 말고, 필요한 객체를 다른 곳에서 넣어 달라."**

라는 개념이다.


### 일반적인 방식

```csharp
public class Player
{
    private Gun gun = new Gun();

    public void Attack()
    {
        gun.Fire();
    }
}
```

Player가 직접 Gun을 생성한다.

```text
Player
   │
new Gun()
```

Player는 Gun과 강하게 결합된다.


### 의존성 주입 방식

먼저 무기의 공통 인터페이스를 정의한다.

```csharp
public interface IWeapon
{
    void Fire();
}
```

총 구현

```csharp
public class Gun : IWeapon
{
    public void Fire()
    {
        Debug.Log("총 발사");
    }
}
```

활 구현

```csharp
public class Bow : IWeapon
{
    public void Fire()
    {
        Debug.Log("화살 발사");
    }
}
```

Player는 구체 클래스가 아닌 인터페이스에 의존한다.

```csharp
public class Player
{
    private IWeapon weapon;

    public Player(IWeapon weapon)
    {
        this.weapon = weapon;
    }

    public void Attack()
    {
        weapon.Fire();
    }
}
```

생성 시 필요한 무기를 주입한다.

```csharp
Player player = new Player(new Gun());
```

또는

```csharp
Player player = new Player(new Bow());
```

Player는 Gun인지 Bow인지 알 필요가 없으며,

```csharp
weapon.Fire();
```

만 호출하면 된다.

---

### 구조 비교

기존 방식

```text
Player
   │
new Gun()
```

의존성 주입 방식

```text
Gun
   │
   ▼
Player
```

객체 생성 책임이 Player에서 외부로 이동하였다.

---

### Unity에서의 DI

Unity에서는 **Zenject**나 **VContainer** 같은 DI 프레임워크를 많이 사용한다.

예를 들어

```csharp
public class Player
{
    [Inject]
    private IWeapon weapon;
}
```

Installer에서

```csharp
builder.Register<Gun>(Lifetime.Singleton);
builder.Register<IWeapon, Gun>();
```

처럼 등록하면 Player가 직접 객체를 생성하지 않아도 자동으로 주입된다.

---

### 의존성 주입의 장점

- 객체 간 결합도를 낮출 수 있다.
- 구현체를 쉽게 교체할 수 있다.
- 테스트(Mock 객체 사용)가 쉬워진다.
- 유지보수성이 향상된다.
- 객체 생성 책임을 분리할 수 있다.

---

## 의존성 역전 원칙(DIP)

의존성 주입과 함께 자주 등장하는 개념이 **의존성 역전 원칙(Dependency Inversion Principle, DIP)**이다.

DIP는 SOLID 원칙의 마지막 원칙으로,

> **상위 모듈은 하위 모듈에 의존해서는 안 되며, 둘 다 추상화에 의존해야 한다.**

를 의미한다.

나쁜 구조

```text
Player
   │
   ▼
Gun
```

좋은 구조

```text
Player
   │
   ▼
IWeapon
   ▲
   │
Gun
Bow
LaserGun
```

Player는 Gun이 아니라 **IWeapon이라는 추상화**만 알고 있으므로 새로운 무기가 추가되어도 Player를 수정할 필요가 없다.

---

## 의존성 부패(Dependency Rot)

### 의존성 부패란?

의존성 부패(Dependency Rot)는 **객체 간 의존 관계가 시간이 지날수록 복잡하게 얽혀 유지보수가 어려워지는 현상**을 말한다.

정식 디자인 패턴 용어라기보다는 소프트웨어 개발에서 자주 사용하는 표현이다.

처음에는

```text
Player
   │
   ▼
Weapon
```

정도의 단순한 구조였지만,

기능이 계속 추가되면서

```text
Player
 ├── Weapon
 ├── Inventory
 ├── UI
 ├── Sound
 ├── Save
 ├── Network
 ├── Quest
 ├── Achievement
 ├── Ranking
 ├── Analytics
 ├── Effect
 └── Input
```

처럼 모든 시스템을 직접 참조하게 되는 경우가 발생한다.

이러한 상태를 흔히 **God Object** 또는 **의존성 부패**라고 부른다.

---

### 게임 예시

```csharp
public class Player : MonoBehaviour
{
    public UIManager ui;
    public SoundManager sound;
    public Inventory inventory;
    public SaveManager save;
    public QuestManager quest;
    public AchievementManager achievement;
    public NetworkManager network;
    public Analytics analytics;
    public RankingManager ranking;
    public EffectManager effect;
}
```

Player 하나를 수정하려 해도

- UI
- 사운드
- 퀘스트
- 네트워크
- 저장
- 랭킹

등 여러 시스템에 영향을 줄 수 있다.

---

### 의존성 부패의 문제점

- 클래스가 지나치게 커진다.
- 변경 범위를 예측하기 어렵다.
- 테스트가 어려워진다.
- 재사용성이 떨어진다.
- 순환 참조(Circular Dependency)가 발생하기 쉽다.
- 작은 수정도 예상치 못한 버그를 유발할 수 있다.

---

### 의존성 부패를 방지하는 방법

#### 1. 인터페이스 사용

```csharp
public interface IDamageable
{
    void TakeDamage(int damage);
}
```

구체 클래스가 아닌 추상화에 의존하도록 만든다.

---

#### 2. 의존성 주입(DI)

```csharp
Player(IWeapon weapon)
```

객체를 직접 생성하지 않고 외부에서 주입받는다.

---

#### 3. 단일 책임 원칙(SRP)

Player가 모든 기능을 담당하지 않도록 기능을 분리한다.

```text
PlayerMovement
PlayerHealth
PlayerInventory
PlayerAnimation
PlayerInput
```

---

#### 4. 이벤트(Pub/Sub) 사용

직접 호출 대신 이벤트를 활용한다.

```csharp
OnPlayerDead?.Invoke();
```

그러면

- UI
- 사운드
- 퀘스트
- 업적

등이 이벤트를 구독하여 필요한 작업만 수행할 수 있다.

---

#### 5. 컴포넌트 기반 설계

Unity에서는 하나의 Player 클래스에 모든 기능을 넣기보다 여러 컴포넌트로 분리하는 것이 일반적이다.

```text
Player(GameObject)
 ├── PlayerMovement
 ├── PlayerHealth
 ├── PlayerAttack
 ├── PlayerAnimation
 ├── PlayerInput
 └── PlayerInventory
```

각 컴포넌트는 하나의 책임만 담당하므로 응집도는 높아지고 결합도는 낮아진다.

---

## 정리

| 개념 | 설명 | 게임 예시 |
|------|------|----------|
| **의존성(Dependency)** | 하나의 객체가 다른 객체를 필요로 하는 관계 | `Player`가 `Weapon`을 사용 |
| **의존성 주입(DI)** | 필요한 객체를 직접 생성하지 않고 외부에서 전달받는 방식 | `Player(IWeapon weapon)` |
| **의존성 역전 원칙(DIP)** | 구체 클래스가 아니라 추상화에 의존하는 원칙 | `Player → IWeapon ← Gun` |
| **의존성 부패(Dependency Rot)** | 의존 관계가 과도하게 얽혀 유지보수가 어려워진 상태 | `Player`가 UI, 사운드, 네트워크 등을 모두 직접 참조 |

게임 개발에서는 **낮은 결합도와 높은 응집도**를 유지하기 위해 **인터페이스**, **의존성 주입(DI)**, **이벤트(Pub/Sub)**, **컴포넌트 기반 설계**를 함께 사용하는 것이 가장 일반적인 설계 방식이다.
