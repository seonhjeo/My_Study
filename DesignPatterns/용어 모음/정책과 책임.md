# 정책과 책임

소프트웨어 설계에서 **정책(Policy)**과 **책임(Responsibility)**은 객체와 모듈의 역할을 구분하고, 변경에 강한 구조를 만들기 위한 중요한 개념이다.

두 개념은 서로 밀접하게 연결되어 있지만 의미는 다르다.

* **정책**은 시스템이 어떤 기준과 규칙에 따라 동작할지를 결정한다.
* **책임**은 특정 객체나 모듈이 어떤 일을 맡아 수행할지를 의미한다.

간단하게 표현하면 다음과 같다.

> 정책은 **무엇을 해야 하는지와 어떤 규칙을 적용할지**를 결정하고, 책임은 **누가 그 일을 수행할지**를 결정한다.

게임 시스템을 예로 들면 다음과 같다.

```text
정책: 플레이어의 체력이 0 이하가 되면 사망 처리한다.
책임: PlayerHealth가 체력을 관리하고 PlayerDeathHandler가 사망 처리를 수행한다.
```

---

## 1. 책임(Responsibility)

### 책임이란?

책임은 객체나 모듈이 시스템 안에서 맡고 있는 역할과 수행해야 하는 작업을 의미한다.

객체지향 설계에서는 각 객체가 자신의 상태와 행동을 관리해야 하며, 다른 객체의 내부 상태를 함부로 제어해서는 안 된다.

객체의 책임은 크게 다음 두 가지로 구분할 수 있다.

* 자신이 알고 있는 정보를 제공하는 책임
* 자신이 수행해야 하는 행동을 처리하는 책임

예를 들어 플레이어의 체력을 관리하는 객체가 있다고 가정해 보자.

```csharp
public class PlayerHealth
{
    private int currentHealth;
    private int maxHealth;

    public int CurrentHealth => currentHealth;

    public PlayerHealth(int maxHealth)
    {
        this.maxHealth = maxHealth;
        currentHealth = maxHealth;
    }

    public void TakeDamage(int damage)
    {
        currentHealth -= damage;

        if (currentHealth < 0)
            currentHealth = 0;
    }

    public void Heal(int amount)
    {
        currentHealth += amount;

        if (currentHealth > maxHealth)
            currentHealth = maxHealth;
    }

    public bool IsDead()
    {
        return currentHealth <= 0;
    }
}
```

`PlayerHealth`의 책임은 다음과 같다.

* 현재 체력을 저장한다.
* 피해를 적용한다.
* 체력을 회복한다.
* 최대 체력을 초과하지 않도록 제한한다.
* 사망 여부를 판단한다.

이러한 기능들은 모두 체력 관리라는 하나의 책임에 포함된다.

---

### 책임은 메서드 하나를 의미하지 않는다

책임을 클래스당 메서드 하나로 오해해서는 안 된다.

하나의 클래스가 여러 메서드를 가지고 있더라도, 모든 메서드가 같은 목적과 변경 이유를 가지고 있다면 하나의 책임을 가진 것으로 볼 수 있다.

예를 들어 다음 클래스는 여러 메서드를 가지고 있다.

```csharp
public class Inventory
{
    public void AddItem(Item item)
    {
    }

    public void RemoveItem(Item item)
    {
    }

    public bool Contains(Item item)
    {
        return false;
    }

    public void Clear()
    {
    }
}
```

이 메서드들은 모두 인벤토리 관리라는 동일한 책임을 수행한다.

반면 다음 클래스는 여러 종류의 책임을 함께 가지고 있다.

```csharp
public class Player
{
    public void Move()
    {
    }

    public void TakeDamage()
    {
    }

    public void SaveGame()
    {
    }

    public void SendNetworkPacket()
    {
    }

    public void PlayBackgroundMusic()
    {
    }
}
```

이 클래스는 다음 책임을 동시에 가지고 있다.

* 이동
* 체력
* 저장
* 네트워크
* 사운드

따라서 책임이 명확하게 분리되어 있지 않다.

---

### 객체가 가져야 하는 대표적인 책임

객체의 책임은 일반적으로 다음과 같은 형태로 나타난다.

#### 상태 관리 책임

객체가 자신의 데이터를 저장하고 올바른 상태를 유지한다.

```csharp
public class Health
{
    private int currentHealth;

    public void TakeDamage(int damage)
    {
        currentHealth = Math.Max(0, currentHealth - damage);
    }
}
```

#### 계산 책임

주어진 정보를 바탕으로 결과를 계산한다.

```csharp
public class DamageCalculator
{
    public int Calculate(int attack, int defense)
    {
        return Math.Max(1, attack - defense);
    }
}
```

#### 흐름 제어 책임

여러 객체의 동작 순서를 조정한다.

```csharp
public class BattleController
{
    public void ExecuteTurn(Character attacker, Character target)
    {
        attacker.Attack(target);
        target.CheckDeath();
    }
}
```

#### 외부 시스템 연동 책임

파일, 데이터베이스, 네트워크 또는 외부 API와 통신한다.

```csharp
public class SaveService
{
    public void Save(PlayerData data)
    {
        // 파일 또는 서버에 저장
    }
}
```

#### 객체 생성 책임

필요한 객체를 생성하고 초기화한다.

```csharp
public class EnemyFactory
{
    public Enemy Create(EnemyType type)
    {
        return type switch
        {
            EnemyType.Slime => new Slime(),
            EnemyType.Goblin => new Goblin(),
            _ => throw new ArgumentOutOfRangeException(nameof(type))
        };
    }
}
```

---

### 책임 할당

책임 할당은 특정 기능을 어떤 객체에게 맡길지를 결정하는 과정이다.

좋은 책임 할당은 객체의 응집도를 높이고 객체 간 결합도를 낮춘다.

예를 들어 적이 플레이어에게 피해를 주는 전투 시스템을 생각해 보자.

나쁜 구조에서는 `EnemyAttack`이 플레이어의 체력을 직접 수정할 수 있다.

```csharp
public class EnemyAttack
{
    public void Attack(Player player)
    {
        player.Health -= 10;

        if (player.Health <= 0)
        {
            player.IsDead = true;
            player.PlayDeathAnimation();
        }
    }
}
```

`EnemyAttack`이 다음 책임까지 알고 있다.

* 플레이어 체력 감소
* 사망 여부 판단
* 사망 상태 변경
* 사망 애니메이션 재생

이는 다른 객체의 책임을 침범한 구조이다.

더 좋은 구조에서는 공격자는 피해만 전달한다.

```csharp
public interface IDamageable
{
    void TakeDamage(int damage);
}
```

```csharp
public class EnemyAttack
{
    private readonly int attackDamage;

    public EnemyAttack(int attackDamage)
    {
        this.attackDamage = attackDamage;
    }

    public void Attack(IDamageable target)
    {
        target.TakeDamage(attackDamage);
    }
}
```

```csharp
public class PlayerHealth : IDamageable
{
    private int currentHealth;

    public void TakeDamage(int damage)
    {
        currentHealth -= damage;

        if (currentHealth <= 0)
            Die();
    }

    private void Die()
    {
        // 플레이어 사망 처리
    }
}
```

이 구조에서 책임은 다음처럼 나뉜다.

```text
EnemyAttack
 └── 피해를 전달하는 책임

PlayerHealth
 ├── 피해를 적용하는 책임
 ├── 체력을 관리하는 책임
 └── 사망 여부를 판단하는 책임
```

---

### 정보 전문가 원칙

책임은 일반적으로 해당 작업에 필요한 정보를 가장 많이 가지고 있는 객체에게 할당하는 것이 좋다.

이를 **정보 전문가 원칙(Information Expert)**이라고 한다.

예를 들어 인벤토리에 특정 아이템이 존재하는지 확인하는 책임은 `Player`가 아니라 `Inventory`가 가지는 것이 자연스럽다.

```csharp
public class Inventory
{
    private readonly List<Item> items = new();

    public bool Contains(Item item)
    {
        return items.Contains(item);
    }
}
```

```csharp
public class Player
{
    private readonly Inventory inventory;

    public bool HasItem(Item item)
    {
        return inventory.Contains(item);
    }
}
```

실제 아이템 목록을 알고 있는 객체는 `Inventory`이므로, 검색과 관리 책임도 `Inventory`가 가지는 것이 적절하다.

---

### 책임 주도 설계

책임 주도 설계(Responsibility-Driven Design)는 클래스를 먼저 만들고 기능을 채우는 방식이 아니라, 시스템에서 필요한 책임을 먼저 찾고 그 책임을 수행할 객체를 결정하는 설계 방식이다.

예를 들어 턴제 전투 시스템을 설계한다고 가정해 보자.

필요한 책임은 다음과 같다.

```text
공격 대상을 선택한다.
공격 데미지를 계산한다.
피해를 적용한다.
사망 여부를 판단한다.
턴을 다음 캐릭터에게 넘긴다.
```

이 책임을 객체에 할당하면 다음과 같이 설계할 수 있다.

```text
TargetSelector
 └── 공격 대상 선택

DamageCalculator
 └── 최종 데미지 계산

Health
 ├── 피해 적용
 └── 사망 여부 판단

TurnManager
 └── 턴 순서 관리
```

책임을 먼저 분리하면 각 객체의 역할이 명확해지고, 하나의 객체가 너무 많은 일을 맡는 것을 방지할 수 있다.

## 2. 정책(Policy)

### 정책이란?

정책은 시스템이 어떤 기준, 규칙 또는 전략에 따라 동작할지를 정의하는 것이다.

책임이 **누가 수행하는가**를 다룬다면, 정책은 **어떤 규칙으로 수행하는가**를 다룬다.

게임에서는 다음과 같은 내용이 정책에 해당한다.

* 데미지를 어떤 공식으로 계산할 것인가?
* 적이 어떤 대상을 우선 공격할 것인가?
* 아이템 드롭 확률을 어떻게 결정할 것인가?
* 플레이어가 언제 사망하는가?
* 경험치가 어떤 기준으로 증가하는가?
* 어떤 조건에서 스킬을 사용할 수 있는가?
* 매치메이킹에서 어떤 상대를 선택할 것인가?

예를 들어 다음 규칙은 모두 전투 정책이다.

```text
최종 데미지는 공격력에서 방어력을 뺀 값이다.
치명타가 발생하면 최종 데미지를 2배로 한다.
최소 데미지는 1이다.
체력이 0 이하가 되면 사망한다.
```

---

### 정책과 구현의 차이

정책은 시스템의 규칙을 의미하고, 구현은 그 규칙을 코드로 표현한 것이다.

다음은 데미지 계산 정책을 코드로 구현한 예시이다.

```csharp
public class DamageCalculator
{
    public int Calculate(int attack, int defense)
    {
        int damage = attack - defense;
        return Math.Max(1, damage);
    }
}
```

이 코드에는 다음 정책이 포함되어 있다.

```text
기본 데미지 = 공격력 - 방어력
최소 데미지 = 1
```

정책이 변경되면 계산 방식도 달라진다.

예를 들어 방어력을 퍼센트 감소 방식으로 변경할 수 있다.

```csharp
public class DamageCalculator
{
    public int Calculate(int attack, float damageReductionRate)
    {
        float damage = attack * (1f - damageReductionRate);
        return Math.Max(1, (int)damage);
    }
}
```

이 경우 책임은 여전히 데미지 계산이지만, 적용하는 정책이 변경된 것이다.

---

### 상위 수준 정책과 하위 수준 정책

소프트웨어의 정책은 추상화 수준에 따라 상위 수준 정책과 하위 수준 정책으로 구분할 수 있다.

#### 상위 수준 정책

시스템의 핵심 규칙과 목적을 정의한다.

게임에서는 다음과 같은 규칙이 상위 수준 정책에 해당한다.

```text
플레이어는 적을 공격할 수 있다.
체력이 0이 되면 캐릭터는 사망한다.
전투에서 승리하면 보상을 획득한다.
턴제 전투에서는 한 캐릭터씩 행동한다.
```

상위 수준 정책은 게임의 핵심 동작을 정의하며, 플랫폼이나 데이터 저장 방식과 같은 기술적 세부 사항과 분리되는 것이 좋다.

#### 하위 수준 정책 또는 세부 구현

상위 수준 규칙을 실제로 수행하기 위한 기술적 방법이다.

```text
데이터를 JSON 파일에 저장한다.
사망 효과음을 AudioSource로 재생한다.
체력 UI를 Slider로 표시한다.
서버 통신에 HTTP를 사용한다.
```

예를 들어 다음 구조는 상위 정책이 하위 구현에 직접 의존한다.

```csharp
public class PlayerDeathHandler
{
    private readonly JsonSaveService saveService =
        new JsonSaveService();

    public void HandleDeath()
    {
        saveService.Save();
    }
}
```

`PlayerDeathHandler`의 핵심 정책은 플레이어가 사망했을 때 필요한 처리를 수행하는 것이다.

하지만 구체적인 JSON 저장 방식까지 직접 알고 있다.

더 좋은 구조에서는 상위 정책이 추상화에 의존한다.

```csharp
public interface ISaveService
{
    void Save();
}
```

```csharp
public class PlayerDeathHandler
{
    private readonly ISaveService saveService;

    public PlayerDeathHandler(ISaveService saveService)
    {
        this.saveService = saveService;
    }

    public void HandleDeath()
    {
        saveService.Save();
    }
}
```

이제 저장 정책을 로컬 파일, 서버 또는 클라우드 방식으로 교체할 수 있다.

---

### 정책을 분리해야 하는 이유

정책이 클래스 내부에 하드코딩되어 있으면 규칙이 바뀔 때마다 기존 코드를 수정해야 한다.

예를 들어 적의 공격 대상 선택 정책을 다음처럼 직접 작성했다고 가정해 보자.

```csharp
public class EnemyAI
{
    public Character SelectTarget(List<Character> targets)
    {
        Character target = null;
        int lowestHealth = int.MaxValue;

        foreach (var candidate in targets)
        {
            if (candidate.Health < lowestHealth)
            {
                lowestHealth = candidate.Health;
                target = candidate;
            }
        }

        return target;
    }
}
```

현재 정책은 체력이 가장 낮은 대상을 공격하는 것이다.

하지만 이후 다음 정책들이 추가될 수 있다.

* 가장 가까운 대상 공격
* 체력이 가장 낮은 대상 공격
* 공격력이 가장 높은 대상 공격
* 무작위 대상 공격
* 힐러 우선 공격
* 플레이어 우선 공격

모든 정책을 `EnemyAI` 내부 조건문으로 처리하면 클래스가 계속 변경된다.

```csharp
public Character SelectTarget(
    List<Character> targets,
    TargetPolicyType policyType)
{
    switch (policyType)
    {
        case TargetPolicyType.Nearest:
            // 가장 가까운 대상 선택
            break;

        case TargetPolicyType.LowestHealth:
            // 체력이 가장 낮은 대상 선택
            break;

        case TargetPolicyType.Random:
            // 무작위 대상 선택
            break;
    }

    return null;
}
```

새로운 정책이 추가될 때마다 기존 코드를 수정해야 한다.

이를 별도의 정책 객체로 분리할 수 있다.

```csharp
public interface ITargetSelectionPolicy
{
    Character SelectTarget(
        Character owner,
        IReadOnlyList<Character> targets);
}
```

체력이 가장 낮은 대상을 선택하는 정책

```csharp
public class LowestHealthTargetPolicy
    : ITargetSelectionPolicy
{
    public Character SelectTarget(
        Character owner,
        IReadOnlyList<Character> targets)
    {
        Character selected = null;
        int lowestHealth = int.MaxValue;

        foreach (var target in targets)
        {
            if (target.Health >= lowestHealth)
                continue;

            lowestHealth = target.Health;
            selected = target;
        }

        return selected;
    }
}
```

가장 가까운 대상을 선택하는 정책

```csharp
public class NearestTargetPolicy
    : ITargetSelectionPolicy
{
    public Character SelectTarget(
        Character owner,
        IReadOnlyList<Character> targets)
    {
        Character selected = null;
        float shortestDistance = float.MaxValue;

        foreach (var target in targets)
        {
            float distance = Vector3.Distance(
                owner.Position,
                target.Position);

            if (distance >= shortestDistance)
                continue;

            shortestDistance = distance;
            selected = target;
        }

        return selected;
    }
}
```

무작위 대상을 선택하는 정책

```csharp
public class RandomTargetPolicy
    : ITargetSelectionPolicy
{
    public Character SelectTarget(
        Character owner,
        IReadOnlyList<Character> targets)
    {
        if (targets.Count == 0)
            return null;

        int index = UnityEngine.Random.Range(
            0,
            targets.Count);

        return targets[index];
    }
}
```

`EnemyAI`는 선택된 정책을 사용한다.

```csharp
public class EnemyAI
{
    private readonly ITargetSelectionPolicy targetPolicy;

    public EnemyAI(ITargetSelectionPolicy targetPolicy)
    {
        this.targetPolicy = targetPolicy;
    }

    public Character SelectTarget(
        Character owner,
        IReadOnlyList<Character> targets)
    {
        return targetPolicy.SelectTarget(owner, targets);
    }
}
```

이 구조에서는 `EnemyAI`가 대상을 선택하는 책임을 조정하지만, 실제 선택 기준은 정책 객체가 결정한다.

---

## 3. 정책과 책임의 차이

정책과 책임은 비슷해 보이지만 초점이 다르다.

| 구분     | 정책                    | 책임                           |
| ------ | --------------------- | ---------------------------- |
| 핵심 질문  | 어떤 규칙으로 동작하는가?        | 누가 이 작업을 수행하는가?              |
| 의미     | 판단 기준, 규칙, 전략         | 역할, 행동, 의무                   |
| 변경 원인  | 게임 규칙이나 요구사항 변경       | 객체 역할이나 구조 변경                |
| 게임 예시  | 가장 가까운 적을 공격한다.       | TargetSelector가 공격 대상을 선택한다. |
| 구현 예시  | `NearestTargetPolicy` | `EnemyAI`, `TargetSelector`  |
| 주요 관심사 | 동작 기준의 변경 가능성         | 역할 분리와 책임 할당                 |

다음 문장을 비교하면 차이를 쉽게 이해할 수 있다.

```text
책임:
EnemyAI는 공격 대상을 선택할 책임이 있다.

정책:
EnemyAI는 가장 가까운 대상을 선택한다.
```

`공격 대상을 선택한다`는 것은 책임이고, `가장 가까운 대상을 고른다`는 것은 정책이다.

---

## 4. 하나의 책임 안에 여러 정책이 존재할 수 있다

하나의 책임은 여러 정책으로 수행될 수 있다.

예를 들어 데미지 계산이라는 책임이 있다고 가정해 보자.

```text
책임:
공격자와 방어자의 능력치를 이용해 최종 데미지를 계산한다.
```

이 책임에는 여러 정책을 적용할 수 있다.

```text
정책 1:
공격력 - 방어력

정책 2:
공격력 × 스킬 배율 - 방어력

정책 3:
공격력 × (1 - 피해 감소율)

정책 4:
최소 데미지는 항상 1

정책 5:
치명타 발생 시 데미지를 2배로 적용
```

정책을 인터페이스로 분리하면 계산 책임은 유지하면서 계산 규칙만 교체할 수 있다.

```csharp
public interface IDamagePolicy
{
    int Calculate(DamageContext context);
}
```

```csharp
public readonly struct DamageContext
{
    public int Attack { get; }
    public int Defense { get; }
    public float SkillMultiplier { get; }
    public bool IsCritical { get; }

    public DamageContext(
        int attack,
        int defense,
        float skillMultiplier,
        bool isCritical)
    {
        Attack = attack;
        Defense = defense;
        SkillMultiplier = skillMultiplier;
        IsCritical = isCritical;
    }
}
```

기본 데미지 정책

```csharp
public class BasicDamagePolicy : IDamagePolicy
{
    public int Calculate(DamageContext context)
    {
        int damage = context.Attack - context.Defense;
        return Math.Max(1, damage);
    }
}
```

스킬 데미지 정책

```csharp
public class SkillDamagePolicy : IDamagePolicy
{
    public int Calculate(DamageContext context)
    {
        int attackDamage =
            (int)(context.Attack * context.SkillMultiplier);

        int damage = attackDamage - context.Defense;

        if (context.IsCritical)
            damage *= 2;

        return Math.Max(1, damage);
    }
}
```

데미지 계산기는 정책을 이용하여 자신의 책임을 수행한다.

```csharp
public class DamageCalculator
{
    private readonly IDamagePolicy damagePolicy;

    public DamageCalculator(IDamagePolicy damagePolicy)
    {
        this.damagePolicy = damagePolicy;
    }

    public int Calculate(DamageContext context)
    {
        return damagePolicy.Calculate(context);
    }
}
```

## 5. 정책 객체와 전략 패턴

정책을 별도의 객체로 분리하는 대표적인 방법이 전략 패턴(Strategy Pattern)이다.

전략 패턴은 변화 가능한 알고리즘이나 규칙을 인터페이스로 추상화하고, 실행 중 필요한 구현체를 선택해 사용하는 방식이다.

구조는 다음과 같다.

```text
Context
   │
   ▼
Strategy Interface
   ▲
   │
 ┌─┼────────────┐
 │ │            │
A정책          B정책
```

게임의 이동 시스템을 예로 들면 다음과 같다.

```csharp
public interface IMovementPolicy
{
    void Move(Transform transform, Vector3 direction);
}
```

걷기 정책

```csharp
public class WalkMovementPolicy : IMovementPolicy
{
    private readonly float speed;

    public WalkMovementPolicy(float speed)
    {
        this.speed = speed;
    }

    public void Move(
        Transform transform,
        Vector3 direction)
    {
        transform.position +=
            direction * speed * Time.deltaTime;
    }
}
```

비행 정책

```csharp
public class FlyMovementPolicy : IMovementPolicy
{
    private readonly float speed;

    public FlyMovementPolicy(float speed)
    {
        this.speed = speed;
    }

    public void Move(
        Transform transform,
        Vector3 direction)
    {
        transform.position +=
            direction.normalized * speed * Time.deltaTime;
    }
}
```

캐릭터 이동 객체

```csharp
public class CharacterMovement
{
    private IMovementPolicy movementPolicy;

    public CharacterMovement(
        IMovementPolicy movementPolicy)
    {
        this.movementPolicy = movementPolicy;
    }

    public void ChangePolicy(
        IMovementPolicy movementPolicy)
    {
        this.movementPolicy = movementPolicy;
    }

    public void Move(
        Transform transform,
        Vector3 direction)
    {
        movementPolicy.Move(transform, direction);
    }
}
```

이 구조에서 책임과 정책은 다음처럼 나뉜다.

```text
CharacterMovement
 └── 캐릭터 이동 요청을 처리하는 책임

WalkMovementPolicy
 └── 걷기 방식으로 이동하는 정책

FlyMovementPolicy
 └── 비행 방식으로 이동하는 정책
```

## 6. 게임 전투 시스템에서의 정책과 책임

게임 전투 시스템에는 여러 책임과 정책이 함께 존재한다.

### 공격 시스템

#### 책임

* 공격 가능 여부를 확인한다.
* 공격 대상을 결정한다.
* 데미지를 계산한다.
* 대상에게 피해를 전달한다.
* 공격 후 쿨타임을 적용한다.

#### 정책

* 사거리 안의 대상만 공격할 수 있다.
* 마나가 충분해야 스킬을 사용할 수 있다.
* 가장 가까운 적을 우선 공격한다.
* 방어력을 적용한 뒤 최소 1의 피해를 준다.
* 치명타 확률에 따라 데미지를 증가시킨다.

이를 객체별로 분리하면 다음과 같다.

```text
AttackController
 └── 전체 공격 흐름을 조정하는 책임

IAttackConditionPolicy
 └── 공격 가능 여부를 결정하는 정책

ITargetSelectionPolicy
 └── 공격 대상을 선택하는 정책

IDamagePolicy
 └── 최종 데미지를 계산하는 정책

IDamageable
 └── 피해를 받는 책임

Cooldown
 └── 재사용 대기시간을 관리하는 책임
```

---

### 예시 코드

```csharp
public interface IAttackConditionPolicy
{
    bool CanAttack(AttackContext context);
}
```

```csharp
public interface ITargetSelectionPolicy
{
    IDamageable SelectTarget(
        AttackContext context);
}
```

```csharp
public interface IDamagePolicy
{
    int CalculateDamage(
        AttackContext context);
}
```

```csharp
public class AttackController
{
    private readonly IAttackConditionPolicy conditionPolicy;
    private readonly ITargetSelectionPolicy targetPolicy;
    private readonly IDamagePolicy damagePolicy;

    public AttackController(
        IAttackConditionPolicy conditionPolicy,
        ITargetSelectionPolicy targetPolicy,
        IDamagePolicy damagePolicy)
    {
        this.conditionPolicy = conditionPolicy;
        this.targetPolicy = targetPolicy;
        this.damagePolicy = damagePolicy;
    }

    public void Attack(AttackContext context)
    {
        if (!conditionPolicy.CanAttack(context))
            return;

        IDamageable target =
            targetPolicy.SelectTarget(context);

        if (target == null)
            return;

        int damage =
            damagePolicy.CalculateDamage(context);

        target.TakeDamage(damage);
    }
}
```

`AttackController`는 공격 흐름을 조정할 책임을 가진다.

하지만 다음 규칙을 직접 결정하지 않는다.

* 공격 가능 조건
* 대상 선택 기준
* 데미지 계산 공식

이러한 규칙들은 각각 정책 객체가 담당한다.

## 7. 게임 AI에서의 정책과 책임

게임 AI에서도 정책과 책임을 구분할 수 있다.

### AI의 책임

* 주변 상황을 감지한다.
* 현재 상태를 판단한다.
* 행동을 선택한다.
* 선택한 행동을 실행한다.

### AI의 정책

* 체력이 30% 미만이면 도망친다.
* 플레이어가 공격 범위 안에 있으면 공격한다.
* 플레이어를 발견하지 못하면 순찰한다.
* 아군 수가 적보다 적으면 후퇴한다.
* 가장 위협도가 높은 대상을 공격한다.

예를 들어 다음 클래스가 모든 규칙을 직접 가지고 있다고 가정해 보자.

```csharp
public class EnemyAI
{
    public void UpdateAI(Enemy enemy, Player player)
    {
        if (enemy.HealthRate < 0.3f)
        {
            enemy.RunAway();
        }
        else if (enemy.IsInAttackRange(player))
        {
            enemy.Attack(player);
        }
        else if (enemy.CanSee(player))
        {
            enemy.Chase(player);
        }
        else
        {
            enemy.Patrol();
        }
    }
}
```

이 코드는 AI 행동을 선택하는 책임과 행동 선택 정책이 하나의 클래스에 하드코딩되어 있다.

정책을 별도 객체로 분리할 수 있다.

```csharp
public interface IEnemyDecisionPolicy
{
    EnemyAction Decide(EnemyContext context);
}
```

```csharp
public class AggressiveDecisionPolicy
    : IEnemyDecisionPolicy
{
    public EnemyAction Decide(EnemyContext context)
    {
        if (context.CanAttackTarget)
            return EnemyAction.Attack;

        if (context.CanSeeTarget)
            return EnemyAction.Chase;

        return EnemyAction.Patrol;
    }
}
```

```csharp
public class CowardDecisionPolicy
    : IEnemyDecisionPolicy
{
    public EnemyAction Decide(EnemyContext context)
    {
        if (context.HealthRate < 0.5f)
            return EnemyAction.RunAway;

        if (context.CanAttackTarget)
            return EnemyAction.Attack;

        return EnemyAction.Patrol;
    }
}
```

```csharp
public class EnemyAI
{
    private readonly IEnemyDecisionPolicy decisionPolicy;

    public EnemyAI(
        IEnemyDecisionPolicy decisionPolicy)
    {
        this.decisionPolicy = decisionPolicy;
    }

    public EnemyAction Decide(EnemyContext context)
    {
        return decisionPolicy.Decide(context);
    }
}
```

같은 AI 책임을 유지하면서도 성격에 따라 다른 정책을 적용할 수 있다.

```text
고블린
 └── AggressiveDecisionPolicy

겁쟁이 슬라임
 └── CowardDecisionPolicy

보스
 └── BossPhaseDecisionPolicy
```

## 8. 게임 보상 시스템에서의 정책과 책임

보상 시스템에서도 정책과 책임을 분리할 수 있다.

### 책임

* 보상 목록을 생성한다.
* 아이템을 지급한다.
* 경험치를 지급한다.
* 지급 결과를 기록한다.

### 정책

* 일반 몬스터는 골드와 낮은 등급 아이템을 지급한다.
* 보스는 최소 하나의 희귀 아이템을 지급한다.
* 파티원 수에 따라 경험치를 분배한다.
* 플레이어 레벨 차이에 따라 획득 경험치를 감소시킨다.
* 이벤트 기간에는 보상을 두 배로 지급한다.

예를 들어 드롭 정책을 인터페이스로 분리할 수 있다.

```csharp
public interface IRewardPolicy
{
    RewardResult CreateReward(
        RewardContext context);
}
```

```csharp
public class NormalEnemyRewardPolicy
    : IRewardPolicy
{
    public RewardResult CreateReward(
        RewardContext context)
    {
        return new RewardResult(
            gold: 10,
            experience: 20,
            items: Array.Empty<Item>());
    }
}
```

```csharp
public class BossRewardPolicy
    : IRewardPolicy
{
    public RewardResult CreateReward(
        RewardContext context)
    {
        return new RewardResult(
            gold: 1000,
            experience: 500,
            items: new[] { context.RareItem });
    }
}
```

보상 지급 객체는 실제 지급 책임을 가진다.

```csharp
public class RewardService
{
    private readonly IRewardPolicy rewardPolicy;

    public RewardService(IRewardPolicy rewardPolicy)
    {
        this.rewardPolicy = rewardPolicy;
    }

    public void GiveReward(
        Player player,
        RewardContext context)
    {
        RewardResult result =
            rewardPolicy.CreateReward(context);

        player.AddGold(result.Gold);
        player.AddExperience(result.Experience);
        player.Inventory.AddItems(result.Items);
    }
}
```

## 9. 정책을 데이터로 분리하는 방법

게임에서는 정책을 코드뿐 아니라 데이터로 분리하기도 한다.

Unity에서는 `ScriptableObject`를 사용해 밸런스 정책을 데이터로 만들 수 있다.

```csharp
[CreateAssetMenu(
    menuName = "Game/Damage Policy")]
public class DamagePolicyData : ScriptableObject
{
    [SerializeField]
    private float attackMultiplier = 1f;

    [SerializeField]
    private float criticalMultiplier = 2f;

    [SerializeField]
    private int minimumDamage = 1;

    public int Calculate(
        int attack,
        int defense,
        bool isCritical)
    {
        float damage =
            attack * attackMultiplier - defense;

        if (isCritical)
            damage *= criticalMultiplier;

        return Mathf.Max(
            minimumDamage,
            Mathf.FloorToInt(damage));
    }
}
```

이 방식의 장점은 다음과 같다.

* 코드 수정 없이 수치를 변경할 수 있다.
* 기획자가 인스펙터에서 값을 조정할 수 있다.
* 적이나 스킬마다 다른 정책 데이터를 사용할 수 있다.
* 프리팹과 정책 데이터를 쉽게 조합할 수 있다.

다만 모든 정책을 데이터로 표현할 수 있는 것은 아니다.

복잡한 판단 로직이나 외부 시스템 연동은 코드 정책 객체가 더 적절할 수 있다.

---

## 10. 정책 분리의 장점

정책을 별도 객체나 데이터로 분리하면 다음과 같은 장점을 얻을 수 있다.

### 변경 범위가 줄어든다

데미지 공식이 변경되어도 전투 흐름 전체를 수정할 필요가 없다.

```text
AttackController 수정 없음
DamagePolicy만 교체
```

### 확장하기 쉬워진다

새로운 정책을 기존 코드 변경 없이 추가할 수 있다.

```text
BasicDamagePolicy
CriticalDamagePolicy
PvPDamagePolicy
BossDamagePolicy
```

### 테스트하기 쉬워진다

각 정책을 독립적으로 테스트할 수 있다.

```csharp
[Test]
public void BasicDamagePolicy_ReturnsMinimumOne()
{
    var policy = new BasicDamagePolicy();

    var context = new DamageContext(
        attack: 5,
        defense: 100,
        skillMultiplier: 1f,
        isCritical: false);

    int damage = policy.Calculate(context);

    Assert.AreEqual(1, damage);
}
```

### 실행 중 교체할 수 있다

캐릭터 상태나 게임 모드에 따라 정책을 변경할 수 있다.

```text
평상시
 └── NormalMovementPolicy

빙결 상태
 └── SlowedMovementPolicy

비행 버프
 └── FlyMovementPolicy
```

### 상위 로직과 세부 규칙을 분리할 수 있다

전투 시스템의 전체 흐름은 유지하면서 세부 밸런스 규칙만 변경할 수 있다.

---

## 11. 책임 분리의 장점

책임을 적절히 분리하면 다음과 같은 장점을 얻을 수 있다.

### 응집도가 높아진다

각 클래스가 하나의 명확한 역할에 집중한다.

```text
Health
 └── 체력 관리

Inventory
 └── 아이템 관리

Movement
 └── 이동 처리
```

### 결합도가 낮아진다

공격 객체가 대상의 내부 체력 구조를 알 필요가 없다.

```csharp
target.TakeDamage(damage);
```

### 유지보수가 쉬워진다

저장 방식 변경이 이동 시스템에 영향을 주지 않는다.

### 재사용성이 높아진다

`Health` 컴포넌트를 플레이어, 적, 오브젝트, 건물 등에 재사용할 수 있다.

### 테스트하기 쉬워진다

클래스의 역할이 작고 명확하므로 독립적인 단위 테스트가 가능하다.

---

## 12. 정책과 책임을 잘못 분리한 예시

정책을 지나치게 분리하거나 책임을 너무 작게 나누면 오히려 구조가 복잡해질 수 있다.

예를 들어 단순한 데미지 계산을 위해 다음처럼 지나치게 많은 객체를 만들 수 있다.

```text
AttackValueReader
DefenseValueReader
SubtractDamagePolicy
MinimumDamagePolicy
CriticalCheckPolicy
CriticalMultiplierPolicy
DamageRoundPolicy
DamageResultFactory
```

게임 규모가 작고 데미지 공식이 거의 바뀌지 않는다면 이러한 구조는 과도할 수 있다.

또한 책임을 너무 잘게 나누면 하나의 기능을 이해하기 위해 여러 파일을 이동해야 한다.

따라서 정책과 책임을 분리할 때는 다음을 고려해야 한다.

* 해당 규칙이 자주 변경되는가?
* 여러 구현이 필요한가?
* 독립적으로 테스트할 가치가 있는가?
* 다른 시스템에서도 재사용되는가?
* 런타임에 교체해야 하는가?
* 클래스가 서로 다른 이유로 변경되고 있는가?

변경 가능성이 낮고 매우 단순한 규칙은 한 클래스 안에 두어도 문제가 없을 수 있다.

## 13. 정책, 책임, 메커니즘의 차이

정책과 책임을 이해할 때 메커니즘이라는 개념도 함께 구분하면 좋다.

* **정책**: 어떤 규칙을 적용할 것인가?
* **책임**: 누가 그 작업을 수행할 것인가?
* **메커니즘**: 실제로 어떤 기술과 절차로 수행할 것인가?

플레이어 사망 시스템을 예로 들면 다음과 같다.

```text
정책:
체력이 0 이하가 되면 사망한다.

책임:
PlayerHealth가 사망 여부를 판단한다.
PlayerDeathHandler가 사망 후 처리를 수행한다.

메커니즘:
Animator에 Die 트리거를 전달한다.
AudioSource로 사망 사운드를 재생한다.
서버에 HTTP 요청을 보낸다.
```

정책과 메커니즘이 강하게 결합되면 기술적 구현이 바뀔 때 핵심 게임 규칙까지 수정해야 할 수 있다.

따라서 핵심 정책은 가능한 한 Unity API, 데이터베이스, 네트워크 라이브러리 같은 세부 기술과 분리하는 것이 좋다.

## 14. SOLID 원칙과의 관계

정책과 책임은 SOLID 원칙과도 밀접한 관계가 있다.

### SRP와 책임

단일 책임 원칙은 클래스가 하나의 변경 이유와 명확한 책임을 가지도록 한다.

```text
PlayerHealth
 └── 체력 관리 책임

PlayerMovement
 └── 이동 책임
```

### OCP와 정책

변경 가능한 정책을 추상화하면 기존 코드를 수정하지 않고 새로운 정책을 추가할 수 있다.

```text
IDamagePolicy
 ├── BasicDamagePolicy
 ├── CriticalDamagePolicy
 └── PvPDamagePolicy
```

### LSP와 정책 구현

모든 정책 구현체는 공통 인터페이스가 약속한 동작을 지켜야 한다.

```csharp
public interface IDamagePolicy
{
    int Calculate(DamageContext context);
}
```

어떤 정책을 사용해도 호출자는 유효한 데미지 결과를 받을 수 있어야 한다.

### ISP와 책임 분리

하나의 거대한 정책 인터페이스보다 목적별로 작은 인터페이스를 만드는 것이 좋다.

```text
ITargetSelectionPolicy
IDamagePolicy
IAttackConditionPolicy
IRewardPolicy
```

### DIP와 상위 정책

상위 수준의 게임 규칙은 구체적인 하위 구현이 아니라 추상화에 의존해야 한다.

```text
BattleController → IDamagePolicy ← BasicDamagePolicy
```

## 15. 게임 시스템 전체 예시

다음은 전투 시스템에서 정책과 책임을 분리한 구조이다.

```text
BattleController
 ├── 전투 순서 조정 책임
 ├── IAttackConditionPolicy 사용
 ├── ITargetSelectionPolicy 사용
 └── IDamagePolicy 사용

CharacterHealth
 ├── 체력 관리 책임
 ├── 피해 적용 책임
 └── 사망 여부 판단 책임

NearestTargetPolicy
 └── 가장 가까운 대상을 선택하는 정책

BasicDamagePolicy
 └── 공격력과 방어력으로 데미지를 계산하는 정책

ManaAttackConditionPolicy
 └── 마나가 충분한지 확인하는 정책

BattleUI
 └── 전투 상태를 화면에 표시하는 책임

BattleSound
 └── 전투 효과음을 재생하는 책임
```

호출 흐름은 다음과 같다.

```text
1. BattleController가 공격 명령을 받는다.
2. IAttackConditionPolicy로 공격 가능 여부를 확인한다.
3. ITargetSelectionPolicy로 공격 대상을 선택한다.
4. IDamagePolicy로 최종 데미지를 계산한다.
5. CharacterHealth에 피해를 전달한다.
6. CharacterHealth가 사망 여부를 판단한다.
7. 이벤트를 통해 UI와 사운드가 갱신된다.
```

이 구조에서 전투의 흐름, 대상 선택, 데미지 계산, 체력 관리, UI 및 사운드의 책임과 정책이 명확하게 분리된다.

## 정리

| 개념       | 설명                 | 핵심 질문          | 게임 예시                           |
| -------- | ------------------ | -------------- | ------------------------------- |
| **정책**   | 시스템이 따르는 규칙과 판단 기준 | 어떤 규칙으로 동작하는가? | 가장 가까운 적을 공격한다.                 |
| **책임**   | 객체가 맡아 수행하는 역할과 작업 | 누가 이 일을 수행하는가? | TargetSelector가 대상을 선택한다.       |
| **메커니즘** | 실제 작업을 수행하는 기술적 방법 | 어떻게 구현하는가?     | Physics.OverlapSphere로 적을 탐색한다. |

정책과 책임을 잘 분리하면 다음과 같은 구조를 만들 수 있다.

```text
책임
 └── 기능을 수행할 객체를 결정한다.

정책
 └── 기능을 수행할 기준과 규칙을 결정한다.

메커니즘
 └── 기능을 실제 기술로 구현한다.
```

게임 개발에서는 변동 가능성이 높은 규칙을 정책 객체나 데이터로 분리하고, 각 객체가 명확한 책임만 가지도록 설계하는 것이 좋다.

이를 통해 다음과 같은 장점을 얻을 수 있다.

* 낮은 결합도
* 높은 응집도
* 쉬운 기능 확장
* 독립적인 테스트
* 정책 교체 가능성
* 밸런스 변경에 대한 유연한 대응
* 유지보수하기 쉬운 게임 시스템
