# 소프트웨어 프레임워크

소프트웨어 프레임워크(Software Framework)는 애플리케이션을 개발할 때 반복적으로 필요한 구조, 실행 흐름, 공통 기능과 확장 지점을 미리 제공하는 소프트웨어 기반이다.

개발자는 프로그램 전체를 처음부터 만드는 대신 프레임워크가 제공하는 구조와 규칙 안에서 필요한 기능을 구현한다.

간단하게 표현하면 다음과 같다.

> 프레임워크는 프로그램의 기본 구조와 실행 흐름을 제공하고, 개발자는 프레임워크가 허용하는 위치에 애플리케이션의 구체적인 기능을 작성한다.

Unity 역시 게임 개발을 위한 대표적인 프레임워크이자 게임 엔진으로 볼 수 있다.

Unity는 개발자에게 다음과 같은 기능과 구조를 제공한다.

* 게임 루프
* 씬 관리
* GameObject와 Component 구조
* 물리 엔진
* 렌더링 시스템
* 입력 시스템
* 애니메이션 시스템
* 오디오 시스템
* 에디터
* 빌드 시스템
* 플랫폼 추상화
* 생명주기 메서드

개발자는 Unity의 실행 구조를 직접 만들지 않고, Unity가 호출하는 `Awake()`, `Start()`, `Update()` 등의 메서드에 게임 기능을 작성한다.

---

## 1. 프레임워크란?

프레임워크는 특정 종류의 소프트웨어를 개발하기 위해 필요한 공통 구조와 기능을 제공하는 재사용 가능한 소프트웨어 환경이다.

프레임워크는 일반적으로 다음 요소를 포함한다.

* 프로그램의 기본 실행 흐름
* 공통 기능을 제공하는 클래스와 API
* 개발자가 구현해야 하는 확장 지점
* 객체의 생성과 생명주기 관리
* 모듈 간 통신 규칙
* 설정과 초기화 방식
* 오류 처리 방식
* 폴더 및 프로젝트 구조에 대한 규칙
* 외부 시스템과 연결하기 위한 추상화

예를 들어 Unity에서는 개발자가 직접 다음과 같은 게임 루프를 작성하지 않는다.

```csharp
while (gameIsRunning)
{
    ProcessInput();
    UpdateGameLogic();
    SimulatePhysics();
    RenderFrame();
}
```

Unity가 내부적으로 게임 루프를 실행하고, 적절한 시점에 개발자가 작성한 메서드를 호출한다.

```csharp
public class PlayerMovement : MonoBehaviour
{
    private void Update()
    {
        // Unity가 매 프레임 호출한다.
        Move();
    }

    private void Move()
    {
        // 플레이어 이동 처리
    }
}
```

즉, 프로그램의 전체 실행 흐름은 Unity가 관리하고 개발자는 지정된 확장 지점에 코드를 작성한다.

## 2. 프레임워크가 제공하는 것

프레임워크가 제공하는 기능은 종류에 따라 다르지만 일반적으로 다음과 같은 내용을 포함한다.

### 기본 구조

프레임워크는 프로그램을 어떤 구조로 작성해야 하는지에 대한 기본 형태를 제공한다.

Unity에서는 다음과 같은 구조를 사용한다.

```text
Scene
 └── GameObject
      ├── Transform
      ├── Renderer
      ├── Collider
      └── 사용자 정의 MonoBehaviour
```

플레이어 오브젝트는 여러 컴포넌트의 조합으로 구성할 수 있다.

```text
Player
 ├── Transform
 ├── Rigidbody
 ├── CapsuleCollider
 ├── PlayerMovement
 ├── PlayerHealth
 └── PlayerAttack
```

개발자는 Unity의 `GameObject-Component` 구조에 맞춰 기능을 구현한다.

---

### 실행 흐름

프레임워크는 애플리케이션이 어떤 순서로 실행되는지를 정의한다.

Unity의 대표적인 생명주기는 다음과 같다.

```text
Awake
 ↓
OnEnable
 ↓
Start
 ↓
Update
 ↓
LateUpdate
 ↓
OnDisable
 ↓
OnDestroy
```

개발자는 각 시점에 맞는 기능을 구현한다.

```csharp
public class Enemy : MonoBehaviour
{
    private void Awake()
    {
        // 내부 변수와 참조 초기화
    }

    private void Start()
    {
        // 다른 객체 초기화 이후 시작해야 하는 작업
    }

    private void Update()
    {
        // 매 프레임 AI 갱신
    }

    private void OnDestroy()
    {
        // 이벤트 해제와 리소스 정리
    }
}
```

---

### 공통 기능

프레임워크는 여러 프로젝트에서 반복적으로 필요한 기능을 제공한다.

Unity가 제공하는 대표적인 공통 기능은 다음과 같다.

```text
Physics
Animation
Audio
Input
UI
Scene Management
Navigation
Rendering
Serialization
Asset Management
```

예를 들어 물리 충돌 처리를 직접 구현하지 않고 Unity의 물리 시스템을 사용할 수 있다.

```csharp
public class Projectile : MonoBehaviour
{
    private void OnCollisionEnter(Collision collision)
    {
        if (collision.gameObject.TryGetComponent<IDamageable>(
                out var damageable))
        {
            damageable.TakeDamage(10);
        }

        Destroy(gameObject);
    }
}
```

---

### 확장 지점

프레임워크는 개발자가 자신의 코드를 추가할 수 있는 위치를 제공한다.

Unity에서는 다음 요소들이 확장 지점에 해당한다.

* `MonoBehaviour` 상속
* 생명주기 메서드
* `ScriptableObject` 상속
* 사용자 정의 에디터
* 커스텀 에디터 윈도우
* 이벤트 시스템
* 렌더 파이프라인 확장
* 패키지 및 플러그인
* 인터페이스 구현

예를 들어 Unity의 `MonoBehaviour`를 상속하여 새로운 컴포넌트를 만들 수 있다.

```csharp
public class PlayerHealth : MonoBehaviour
{
    [SerializeField]
    private int maximumHealth = 100;

    private int currentHealth;

    private void Awake()
    {
        currentHealth = maximumHealth;
    }

    public void TakeDamage(int damage)
    {
        currentHealth = Mathf.Max(0, currentHealth - damage);
    }
}
```

## 3. 라이브러리와 프레임워크의 차이

프레임워크와 라이브러리는 모두 재사용 가능한 코드를 제공하지만 실행 흐름의 제어권에 차이가 있다.

### 라이브러리

라이브러리는 개발자가 필요할 때 직접 호출한다.

```csharp
int value = Mathf.Max(0, health);
```

호출 흐름은 개발자가 제어한다.

```text
개발자 코드
   ↓
라이브러리 호출
   ↓
결과 반환
```

### 프레임워크

프레임워크는 애플리케이션의 전체 흐름을 제어하고, 필요한 시점에 개발자의 코드를 호출한다.

```csharp
private void Update()
{
    // Unity가 이 메서드를 호출한다.
}
```

호출 흐름은 다음과 같다.

```text
프레임워크
   ↓
개발자 코드 호출
   ↓
프레임워크로 제어 반환
```

이를 **제어의 역전(Inversion of Control, IoC)**이라고 한다.

---

### 라이브러리와 프레임워크 비교

| 구분         | 라이브러리                        | 프레임워크                        |
| ---------- | ---------------------------- | ---------------------------- |
| 실행 흐름의 주도권 | 개발자 코드                       | 프레임워크                        |
| 호출 관계      | 개발자가 라이브러리를 호출               | 프레임워크가 개발자 코드를 호출            |
| 구조 강제성     | 낮음                           | 상대적으로 높음                     |
| 사용 범위      | 특정 기능 제공                     | 애플리케이션 전체 구조 제공              |
| 확장 방식      | 함수와 클래스 호출                   | 상속, 인터페이스, 콜백, 이벤트           |
| Unity 예시   | Newtonsoft.Json, MessagePack | Unity, Zenject, VContainer   |
| 일반 예시      | 수학 라이브러리, 압축 라이브러리           | ASP.NET Core, Spring, Django |

Unity 안에서도 어떤 기능은 라이브러리처럼 사용되고, 어떤 기능은 프레임워크처럼 동작한다.

예를 들어 `Mathf`는 개발자가 직접 호출하므로 라이브러리에 가깝다.

```csharp
float distance = Vector3.Distance(
    transform.position,
    target.position);
```

반면 `MonoBehaviour` 생명주기는 Unity가 호출하므로 프레임워크에 해당한다.

```csharp
private void FixedUpdate()
{
    // Unity의 물리 업데이트 시점에 호출된다.
}
```

## 4. 제어의 역전

제어의 역전(Inversion of Control, IoC)은 프로그램의 실행 흐름과 객체 관리의 제어권이 개발자 코드에서 프레임워크로 넘어가는 것을 의미한다.

일반적인 코드에서는 개발자가 직접 실행 순서를 결정한다.

```csharp
public void Run()
{
    Initialize();
    Update();
    Dispose();
}
```

프레임워크에서는 프레임워크가 실행 순서를 결정한다.

```csharp
public class Player : MonoBehaviour
{
    private void Awake()
    {
        // Unity가 호출한다.
    }

    private void Update()
    {
        // Unity가 호출한다.
    }

    private void OnDestroy()
    {
        // Unity가 호출한다.
    }
}
```

개발자는 `Update()`를 언제 호출할지 결정하지 않는다.

Unity가 게임 루프의 적절한 시점에 호출한다.

```text
Unity 게임 루프
 ├── Awake 호출
 ├── Start 호출
 ├── Update 반복 호출
 ├── 렌더링
 └── OnDestroy 호출
```

이처럼 프레임워크가 전체 흐름을 제어하고 개발자가 특정 부분만 구현하는 구조를 흔히 **할리우드 원칙(Hollywood Principle)**으로 설명한다.

> 우리에게 전화하지 마세요. 우리가 당신에게 전화하겠습니다.

즉, 개발자가 프레임워크를 직접 계속 호출하는 것이 아니라 프레임워크가 필요할 때 개발자의 코드를 호출한다.

## 5. 프레임워크와 아키텍처의 차이

프레임워크와 아키텍처는 서로 관련되어 있지만 같은 개념은 아니다.

### 아키텍처

아키텍처는 시스템의 전체 구조와 설계 원칙을 의미한다.

```text
Presentation
     ↓
Application
     ↓
Domain
```

아키텍처는 다음을 결정한다.

* 모듈을 어떻게 분리할 것인가?
* 각 모듈의 책임은 무엇인가?
* 의존성은 어떤 방향을 가져야 하는가?
* 데이터는 어떤 흐름으로 이동하는가?
* 외부 시스템과 핵심 로직을 어떻게 분리하는가?

### 프레임워크

프레임워크는 특정 구조와 실행 흐름을 코드로 제공하는 개발 기반이다.

Unity는 다음을 제공한다.

```text
GameObject
Component
Scene
MonoBehaviour
게임 루프
물리
렌더링
입력
에디터
```

즉 다음과 같이 정리할 수 있다.

> 아키텍처는 시스템을 어떻게 구성할지에 대한 설계이고, 프레임워크는 그 설계를 구현할 때 사용할 수 있는 구조와 실행 환경이다.

---

### 비교

| 구분     | 아키텍처                  | 프레임워크                       |
| ------ | --------------------- | --------------------------- |
| 의미     | 시스템의 전체적인 설계 구조       | 개발에 필요한 구조와 기능을 제공하는 기반     |
| 형태     | 개념, 규칙, 관계, 원칙        | 실제 코드, API, 실행 환경           |
| 주요 관심사 | 책임, 경계, 의존성, 데이터 흐름   | 실행 흐름, 공통 기능, 확장 지점         |
| 예시     | 계층형, 클린, MVC, 이벤트 기반  | Unity, ASP.NET Core, Spring |
| 적용 방식  | 개발자가 설계하고 결정          | 제공된 규칙과 API를 사용             |
| 관계     | 프레임워크 사용 방법을 결정할 수 있음 | 아키텍처를 구현하는 수단이 될 수 있음       |

Unity를 사용한다고 해서 자동으로 좋은 아키텍처가 만들어지는 것은 아니다.

다음 두 프로젝트는 모두 Unity를 사용하지만 구조는 완전히 다를 수 있다.

```text
프로젝트 A
 └── 모든 기능이 GameManager에 집중됨
```

```text
프로젝트 B
 ├── Presentation
 ├── Application
 ├── Domain
 └── Infrastructure
```

같은 프레임워크를 사용하더라도 개발자가 어떤 아키텍처를 선택하는지에 따라 유지보수성과 확장성이 달라진다.

## 6. 프레임워크와 디자인 패턴의 차이

디자인 패턴은 반복적으로 발생하는 설계 문제에 대한 일반적인 해결 방법이다.

프레임워크는 여러 디자인 패턴과 공통 기능을 실제 코드로 구현한 기반이다.

예를 들어 Unity는 다음과 같은 설계 개념을 포함한다.

* 컴포넌트 패턴
* 이벤트 패턴
* 객체 생명주기
* 직렬화
* 오브젝트 풀링 지원 구조
* 데이터 중심 설계
* 에디터 확장 구조

### 비교

| 구분    | 디자인 패턴              | 프레임워크                      |
| ----- | ------------------- | -------------------------- |
| 의미    | 반복되는 설계 문제의 해결 방법   | 애플리케이션 개발을 위한 코드 기반        |
| 형태    | 개념과 설계 방법           | 실제 클래스, API, 실행 환경         |
| 범위    | 특정 문제               | 시스템의 넓은 영역                 |
| 예시    | 전략, 옵저버, 팩토리, 상태 패턴 | Unity, VContainer, Zenject |
| 구현 여부 | 개발자가 직접 구현          | 프레임워크가 기본 구현 제공            |

예를 들어 전략 패턴은 다음과 같이 직접 구현할 수 있다.

```csharp
public interface IAttackStrategy
{
    void Attack();
}
```

```csharp
public class MeleeAttackStrategy : IAttackStrategy
{
    public void Attack()
    {
        Debug.Log("근접 공격");
    }
}
```

```csharp
public class RangedAttackStrategy : IAttackStrategy
{
    public void Attack()
    {
        Debug.Log("원거리 공격");
    }
}
```

```csharp
public class PlayerAttack
{
    private IAttackStrategy strategy;

    public PlayerAttack(IAttackStrategy strategy)
    {
        this.strategy = strategy;
    }

    public void Attack()
    {
        strategy.Attack();
    }
}
```

반면 프레임워크는 이러한 객체들을 생성하고 연결하거나 생명주기를 관리하는 기능까지 제공할 수 있다.

## 7. 프레임워크의 핵심 특징

### 재사용성

여러 프로젝트에서 공통적으로 필요한 기능을 재사용할 수 있다.

예를 들어 게임마다 다음 기능을 처음부터 개발할 필요가 없다.

```text

```

Unity가 이러한 기능을 제공한다.

### 규약 제공

프레임워크는 개발자가 따라야 하는 규칙과 사용 방식을 제공한다.

Unity에서는 다음과 같은 규약이 있다.

* 컴포넌트는 일반적으로 `MonoBehaviour`를 상속한다.
* 씬 오브젝트는 `GameObject`로 구성한다.
* 인스펙터에서 보이려는 필드는 직렬화해야 한다.
* 물리 처리는 주로 `FixedUpdate()`에서 수행한다.
* 오브젝트 제거는 `Destroy()`를 사용한다.
* 코루틴은 `IEnumerator`를 사용한다.

```csharp
public class PlayerMovement : MonoBehaviour
{
    [SerializeField]
    private float speed = 5f;

    private Rigidbody rigidbodyComponent;

    private void Awake()
    {
        rigidbodyComponent = GetComponent<Rigidbody>();
    }

    private void FixedUpdate()
    {
        rigidbodyComponent.MovePosition(
            rigidbodyComponent.position +
            transform.forward * speed * Time.fixedDeltaTime);
    }
}
```

## 8. 프레임워크의 동작 방식

일반적인 프레임워크는 다음과 같은 흐름으로 동작한다.

```text
1. 프레임워크가 애플리케이션을 시작한다.
2. 설정 파일이나 등록 정보를 읽는다.
3. 필요한 객체를 생성한다.
4. 객체의 생명주기를 관리한다.
5. 특정 이벤트나 시점에 개발자의 코드를 호출한다.
6. 개발자 코드가 결과를 프레임워크에 반환한다.
7. 프레임워크가 다음 실행 흐름을 계속 진행한다.
```

Unity에서는 다음과 같이 표현할 수 있다.

```text
Unity Player 실행
 ↓
씬 로드
 ↓
GameObject 및 Component 생성
 ↓
Awake 호출
 ↓
OnEnable 호출
 ↓
Start 호출
 ↓
게임 루프 실행
 ├── Update
 ├── FixedUpdate
 ├── LateUpdate
 └── 렌더링
 ↓
오브젝트 제거 시 OnDestroy 호출
```

## 11. 게임 시스템용 커스텀 프레임워크

Unity 프로젝트에서 반복적으로 사용하는 기능을 모아 자체 프레임워크를 만들 수도 있다.

예를 들어 여러 게임에서 공통으로 사용할 UI 프레임워크를 만들 수 있다.

```text
UI Framework
 ├── UIManager
 ├── UIView
 ├── UIPage
 ├── UIPopup
 ├── UITransition
 └── UIEvent
```

### 기본 UI 클래스

```csharp
public abstract class UIBase : MonoBehaviour
{
    public bool IsOpen { get; private set; }

    public virtual void Open()
    {
        if (IsOpen)
            return;

        IsOpen = true;
        gameObject.SetActive(true);
        OnOpened();
    }

    public virtual void Close()
    {
        if (!IsOpen)
            return;

        IsOpen = false;
        OnClosed();
        gameObject.SetActive(false);
    }

    protected virtual void OnOpened()
    {
    }

    protected virtual void OnClosed()
    {
    }
}
```

### 페이지 UI

```csharp
public abstract class UIPage : UIBase
{
    public virtual bool CanGoBack => true;
}
```

### 팝업 UI

```csharp
public abstract class UIPopup : UIBase
{
    public virtual bool CloseOnBackgroundClick => true;
}
```

### UI 관리자

```csharp
public class UIManager : MonoBehaviour
{
    [SerializeField]
    private Transform pageRoot;

    [SerializeField]
    private Transform popupRoot;

    private UIPage currentPage;
    private readonly Stack<UIPopup> popupStack = new();

    public void OpenPage(UIPage page)
    {
        if (currentPage != null)
            currentPage.Close();

        currentPage = page;
        page.transform.SetParent(pageRoot, false);
        page.Open();
    }

    public void OpenPopup(UIPopup popup)
    {
        popup.transform.SetParent(popupRoot, false);
        popupStack.Push(popup);
        popup.Open();
    }

    public void CloseTopPopup()
    {
        if (popupStack.Count == 0)
            return;

        UIPopup popup = popupStack.Pop();
        popup.Close();
    }
}
```

이 구조는 다음 규칙을 제공한다.

* 화면에는 하나의 페이지 UI만 표시한다.
* 팝업은 여러 개 중첩할 수 있다.
* 팝업은 스택 순서로 닫힌다.
* 모든 UI는 동일한 열기와 닫기 생명주기를 사용한다.
* 페이지와 팝업은 지정된 부모 Transform 아래에 배치된다.

개발자는 이 규칙을 따라 구체적인 UI를 작성한다.

```csharp
public class InventoryPage : UIPage
{
    protected override void OnOpened()
    {
        RefreshInventory();
    }

    private void RefreshInventory()
    {
        Debug.Log("인벤토리 UI 갱신");
    }
}
```

이처럼 커스텀 프레임워크는 단순한 유틸리티 모음이 아니라 다음을 함께 제공해야 한다.

* 일관된 구조
* 실행 흐름
* 확장 지점
* 생명주기
* 사용 규칙
* 공통 구현

```text
Windows
Android
iOS
PlayStation
Xbox
```

하지만 플랫폼별 기능이 필요하면 조건부 컴파일을 사용할 수도 있다.

```csharp
#if UNITY_ANDROID
    Debug.Log("Android 전용 처리");
#elif UNITY_IOS
    Debug.Log("iOS 전용 처리");
#endif
```

일반적으로 엔진은 특정 문제 영역의 핵심 실행 기능을 제공하며, 프레임워크는 애플리케이션의 구조와 확장 방식을 제공한다.

* 오디오
* 애니메이션
* 씬 관리
* 게임 루프
* 에셋 관리

| 목적    | 게임 실행           | 게임 코드의 구조화와 개발 지원              |

## 14. 프레임워크 사용의 장점

### 개발 속도가 빨라진다

반복적으로 필요한 기능을 다시 구현하지 않아도 된다.

Unity를 사용하지 않고 게임을 만든다면 다음 기능을 직접 개발해야 할 수 있다.

```text
윈도우 생성
그래픽 API 초기화
렌더링 루프
키보드 및 마우스 입력
물리 충돌
오디오 출력
리소스 로딩
플랫폼별 빌드
```

프레임워크는 이러한 기능을 이미 제공한다.

---

### 코드의 일관성이 높아진다

같은 프레임워크를 사용하는 개발자들은 비슷한 구조와 규칙을 따른다.

```text
Awake에서 참조 초기화
Update에서 프레임 단위 처리
FixedUpdate에서 물리 처리
OnDestroy에서 정리
```

팀원이 코드를 이해하기 쉬워진다.

---

### 검증된 기능을 사용할 수 있다

널리 사용되는 프레임워크는 다양한 프로젝트에서 테스트되고 개선된다.

직접 물리 엔진이나 네트워크 프레임워크를 구현하는 것보다 검증된 프레임워크를 사용하는 편이 안정적인 경우가 많다.

---

### 유지보수가 쉬워진다

공통 기능과 실행 방식이 통일되므로 코드의 위치와 동작을 예측하기 쉽다.

---

### 확장성이 높아진다

프레임워크가 적절한 추상화와 확장 지점을 제공하면 기존 구조를 크게 수정하지 않고 기능을 추가할 수 있다.

```text
IWeapon
 ├── Sword
 ├── Bow
 └── MagicStaff
```

---

### 생산성이 높아진다

에디터, 디버거, 프로파일러, 테스트 도구와 빌드 시스템 등을 함께 사용할 수 있다.

Unity는 다음 도구를 제공한다.

```text
Inspector
Profiler
Frame Debugger
Package Manager
Test Runner
Build Settings
Memory Profiler
```

---

## 15. 프레임워크 사용의 단점

### 학습 비용이 발생한다

프레임워크의 구조와 생명주기, 규약을 이해해야 한다.

Unity에서는 다음 내용을 학습해야 한다.

* `MonoBehaviour` 생명주기
* 직렬화 규칙
* 프리팹
* 씬
* 물리 업데이트
* 코루틴
* 에셋 관리
* 플랫폼별 차이

프레임워크를 제대로 이해하지 못하면 잘못된 사용으로 버그가 발생할 수 있다.

---

### 프레임워크의 규칙에 제약받는다

개발자는 프레임워크가 제공하는 구조 안에서 기능을 구현해야 한다.

예를 들어 Unity의 `MonoBehaviour`는 일반적인 생성자를 원하는 방식으로 사용하기 어렵다.

```csharp
// MonoBehaviour는 일반적으로 다음처럼 직접 생성할 수 없다.
var player = new PlayerMovement();
```

대신 `GameObject`에 컴포넌트를 추가해야 한다.

```csharp
PlayerMovement movement =
    gameObject.AddComponent<PlayerMovement>();
```

---

### 내부 동작을 완전히 제어하기 어렵다

프레임워크가 많은 기능을 자동으로 처리하면 편리하지만 내부 동작이 숨겨져 문제를 추적하기 어려울 수 있다.

예를 들어 Unity의 직렬화, 물리 이벤트 순서, 렌더링 파이프라인과 도메인 리로드를 정확히 이해하지 못하면 예상하지 못한 문제가 발생할 수 있다.

---

### 프레임워크 의존성이 커질 수 있다

핵심 게임 로직이 Unity API에 강하게 의존하면 Unity 외부에서 테스트하거나 다른 환경으로 옮기기 어렵다.

다음 코드는 Unity에 강하게 의존한다.

```csharp
public class DamageCalculator : MonoBehaviour
{
    public int Calculate(int attack, int defense)
    {
        return Mathf.Max(1, attack - defense);
    }
}
```

순수 C#으로 작성하면 의존성을 줄일 수 있다.

```csharp
public class DamageCalculator
{
    public int Calculate(int attack, int defense)
    {
        return Math.Max(1, attack - defense);
    }
}
```

---

### 버전 변경의 영향을 받을 수 있다

프레임워크가 업데이트되면서 다음 문제가 발생할 수 있다.

* API 변경
* 사용 중단된 기능
* 패키지 충돌
* 플랫폼 지원 변경
* 기존 플러그인 비호환
* 빌드 시스템 변경

---

### 프레임워크 종속

특정 프레임워크의 고유 기능을 지나치게 사용하면 다른 프레임워크로 이전하기 어려워진다.

이를 프레임워크 종속 또는 벤더 종속이라고 할 수 있다.

예를 들어 게임 규칙이 모두 `MonoBehaviour`와 `ScriptableObject`에 강하게 연결되어 있다면 Unity가 아닌 서버 환경에서 동일한 규칙을 재사용하기 어려울 수 있다.

---

## 16. 프레임워크를 잘못 사용한 예시

프레임워크를 사용한다고 해서 자동으로 좋은 설계가 만들어지는 것은 아니다.

### 모든 기능을 MonoBehaviour에 작성

```csharp
public class Player : MonoBehaviour
{
    public void Move()
    {
    }

    public void Attack()
    {
    }

    public void Save()
    {
    }

    public void SendNetworkMessage()
    {
    }

    public void UpdateUI()
    {
    }
}
```

Unity가 `MonoBehaviour`를 제공한다고 해서 모든 기능을 하나의 컴포넌트에 작성해야 하는 것은 아니다.

---

### 생명주기 메서드 남용

```csharp
private void Update()
{
    FindPlayer();
    LoadSaveData();
    SearchAllEnemies();
    UpdateInventory();
    SendServerRequest();
    RefreshAllUI();
}
```

모든 기능을 매 프레임 처리하면 성능과 구조에 문제가 생긴다.

기능별로 적절한 실행 시점을 선택해야 한다.

```text
입력과 이동
 └── Update 또는 FixedUpdate

저장
 └── 저장 요청 시 실행

서버 요청
 └── 필요한 이벤트 발생 시 실행

UI 갱신
 └── 데이터 변경 시 실행
```

---

### 프레임워크 API가 도메인 전체에 침투

```csharp
public class CharacterStats : MonoBehaviour
{
    public int Health;
    public int Attack;

    public void TakeDamage(int damage)
    {
        Health = Mathf.Max(0, Health - damage);
        GetComponent<Animator>().SetTrigger("Hit");
        AudioSource.PlayClipAtPoint(...);
    }
}
```

체력 규칙, 애니메이션과 오디오 처리가 한 클래스에 혼합되어 있다.

더 좋은 구조에서는 핵심 규칙과 Unity 표현을 분리할 수 있다.

```csharp
public class Health
{
    public int Current { get; private set; }

    public Health(int maximum)
    {
        Current = maximum;
    }

    public void TakeDamage(int damage)
    {
        Current = Math.Max(0, Current - damage);
    }
}
```

```csharp
public class CharacterView : MonoBehaviour
{
    [SerializeField]
    private Animator animatorComponent;

    [SerializeField]
    private AudioSource audioSource;

    public void PlayHitPresentation()
    {
        animatorComponent.SetTrigger("Hit");
        audioSource.Play();
    }
}
```

## 17. 프레임워크 설계 원칙

자체 프레임워크를 만들 때는 단순히 공통 코드를 모아 놓는 것만으로는 부족하다.

좋은 프레임워크는 다음 원칙을 고려해야 한다.

### 명확한 목적

프레임워크가 어떤 문제를 해결하는지 명확해야 한다.

```text
UI 화면 전환을 통일한다.
적 생성과 재사용 방식을 통일한다.
저장 데이터 처리 방식을 통일한다.
네트워크 요청 흐름을 통일한다.
```

목적이 불명확한 `CommonFramework`나 `UtilityFramework`는 관련 없는 기능이 모이기 쉽다.

---

### 적절한 추상화

사용자가 알아야 하는 개념은 단순해야 하며 내부 구현은 숨겨야 한다.

예를 들어 UI 사용자가 다음 정도만 알면 되도록 만들 수 있다.

```csharp
uiManager.OpenPage<InventoryPage>();
uiManager.OpenPopup<ConfirmPopup>();
uiManager.CloseTopPopup();
```

내부적으로 프리팹 로딩, 부모 설정, 스택 관리와 애니메이션을 처리할 수 있다.

---

### 확장에는 열려 있어야 한다

새로운 기능을 추가할 때 핵심 코드를 계속 수정하지 않도록 확장 지점을 제공해야 한다.

```csharp
public abstract class UITransition
{
    public abstract Task PlayOpenAsync(
        GameObject target);

    public abstract Task PlayCloseAsync(
        GameObject target);
}
```

새로운 전환 효과는 구현체를 추가하여 확장할 수 있다.

---

### 최소한의 강제

프레임워크가 너무 많은 규칙을 강제하면 사용하기 어려워진다.

사용자가 반드시 필요한 규칙만 따르도록 하고, 선택 가능한 기능은 선택적으로 사용할 수 있게 하는 것이 좋다.

---

### 예측 가능한 생명주기

객체가 언제 생성되고 초기화되며 제거되는지 명확해야 한다.

```text
Create
 ↓
Initialize
 ↓
Open
 ↓
Close
 ↓
Dispose
```

생명주기가 불명확하면 이벤트 중복 등록과 리소스 누수가 발생하기 쉽다.

---

### 오류를 빠르게 발견

잘못된 사용은 가능한 한 빠르게 발견되어야 한다.

```csharp
public void OpenPage(UIPage page)
{
    if (page == null)
        throw new ArgumentNullException(nameof(page));

    // 페이지 열기
}
```

Unity 에디터에서는 `OnValidate()`를 이용해 설정 오류를 사전에 확인할 수도 있다.

```csharp
private void OnValidate()
{
    if (pageRoot == null)
        Debug.LogError("Page Root가 설정되지 않았습니다.");
}
```

---

### 문서화와 예제

프레임워크는 기능만큼 사용법이 중요하다.

다음 내용을 제공하는 것이 좋다.

* 설치 방법
* 빠른 시작
* 핵심 개념
* 생명주기
* 예제 코드
* 샘플 씬과 프리팹
* 확장 방법
* 주의사항
* API 문서
* 버전 변경 내용

## 18. 프레임워크와 SOLID 원칙

### SRP

프레임워크의 각 구성 요소가 명확한 책임을 가져야 한다.

```text
UIManager
 └── UI 흐름 관리

UIFactory
 └── UI 생성

UITransition
 └── 전환 효과

UIInputBlocker
 └── 입력 차단
```

---

### OCP

새로운 구현을 추가할 때 기존 핵심 코드를 수정하지 않아야 한다.

```text
UITransition
 ├── FadeTransition
 ├── ScaleTransition
 └── SlideTransition
```

---

### LSP

하위 구현체는 기본 타입 대신 사용해도 정상적으로 동작해야 한다.

```csharp
public abstract class UITransition
{
    public abstract void Play();
}
```

어떤 전환 구현체를 전달해도 호출자가 동일한 방식으로 사용할 수 있어야 한다.

---

### ISP

사용하지 않는 기능까지 구현하도록 강요하는 거대한 인터페이스를 피해야 한다.

나쁜 예시

```csharp
public interface IUI
{
    void Open();
    void Close();
    void Pause();
    void Resume();
    void Push();
    void Pop();
    void Refresh();
    void LoadAsync();
}
```

필요에 따라 인터페이스를 분리할 수 있다.

```csharp
public interface IOpenable
{
    void Open();
}

public interface IClosable
{
    void Close();
}

public interface IRefreshable
{
    void Refresh();
}
```

---

### DIP

프레임워크의 상위 흐름이 구체 구현보다 추상화에 의존하도록 설계한다.

```csharp
public class UIManager
{
    private readonly IUIFactory factory;

    public UIManager(IUIFactory factory)
    {
        this.factory = factory;
    }
}
```

`UIManager`가 Addressables나 Resources API에 직접 의존하지 않으면 로딩 방식을 교체하기 쉽다.

```text
UIManager → IUIFactory ← AddressableUIFactory
                     ← ResourcesUIFactory
```

## 19. 프레임워크와 비본질적 어려움

프레임워크는 반복적인 구현과 기술적 복잡성을 감춰 비본질적 어려움을 줄일 수 있다.

Unity는 다음 복잡성을 대신 처리한다.

```text
플랫폼별 그래픽 API 초기화
입력 장치 차이
물리 충돌 계산
오디오 장치 제어
씬과 오브젝트 직렬화
리소스 임포트
플랫폼별 빌드
```

하지만 프레임워크를 과도하게 사용하거나 잘못 설계하면 오히려 비본질적 어려움이 증가할 수 있다.

```text
과도한 추상화
복잡한 생명주기
숨겨진 자동 처리
지나치게 많은 규약
어려운 디버깅
불필요한 클래스 계층
```

예를 들어 단순히 팝업 하나를 열기 위해 다음처럼 지나치게 많은 계층을 거쳐야 한다면 과도한 설계일 수 있다.

```text
PopupRequest
 ↓
PopupCommand
 ↓
PopupCommandHandler
 ↓
PopupCoordinator
 ↓
PopupFactory
 ↓
PopupPresenter
 ↓
PopupView
```

프레임워크의 목적은 복잡성을 추가하는 것이 아니라 반복되는 복잡성을 관리하고 줄이는 것이다.

## 20. 프레임워크를 선택할 때 고려할 사항

### 해결하려는 문제가 명확한가?

프레임워크를 도입하기 전에 현재 문제를 명확히 해야 한다.

```text
객체 생성이 복잡하다.
UI 화면 관리 규칙이 일관되지 않다.
네트워크 동기화가 필요하다.
반응형 이벤트 처리가 필요하다.
```

문제가 불분명한 상태에서 프레임워크를 먼저 도입하면 구조만 복잡해질 수 있다.

---

### 프로젝트 규모에 적합한가?

작은 프로토타입에서 대규모 DI 프레임워크나 복잡한 아키텍처 프레임워크를 도입하면 개발 속도가 떨어질 수 있다.

반대로 대규모 프로젝트에서 객체 연결과 생명주기를 모두 수동으로 관리하면 유지보수가 어려워질 수 있다.

---

### 학습 비용은 적절한가?

팀원 모두가 프레임워크를 이해하고 사용할 수 있어야 한다.

특정 개발자만 이해하는 자체 프레임워크는 팀 전체의 병목이 될 수 있다.

---

### Unity 버전과 호환되는가?

다음을 확인해야 한다.

* 지원하는 Unity 버전
* .NET 및 C# 버전
* IL2CPP 지원
* 모바일과 콘솔 지원
* 에디터와 빌드 환경 차이
* 다른 패키지와 충돌 여부

---

### 유지보수가 계속되고 있는가?

외부 프레임워크를 선택할 때는 다음을 살펴보는 것이 좋다.

* 최근 업데이트 여부
* 버그 대응
* 문서 품질
* 사용자 수
* 라이선스
* 장기 지원 가능성
* 업그레이드 난이도

---

### 제거하거나 교체할 수 있는가?

핵심 게임 로직이 프레임워크에 직접 의존하면 나중에 제거하기 어렵다.

가능하면 인터페이스나 어댑터를 통해 외부 프레임워크를 감싸는 것이 좋다.

```csharp
public interface IMessagePublisher
{
    void Publish<T>(T message);
}
```

구체적인 메시지 프레임워크는 이 인터페이스 뒤에서 사용할 수 있다.

---

### 디버깅이 가능한가?

자동 처리와 코드 생성이 많은 프레임워크는 편리하지만 호출 흐름을 추적하기 어려울 수 있다.

다음 사항을 확인하는 것이 좋다.

* 오류 메시지가 명확한가?
* 객체 생성 과정을 확인할 수 있는가?
* 로그를 제공하는가?
* 소스 코드를 볼 수 있는가?
* Unity Profiler와 함께 사용할 수 있는가?

---

## 21. 프레임워크를 직접 만들어야 하는 경우

다음과 같은 경우 자체 프레임워크를 만드는 것이 유용할 수 있다.

* 여러 프로젝트에서 동일한 기능을 반복해서 사용한다.
* 팀 전체에서 통일된 규칙이 필요하다.
* 기존 프레임워크가 프로젝트 요구사항과 맞지 않는다.
* 특정 장르나 회사 프로젝트에 특화된 기능이 필요하다.
* 반복되는 실수와 중복 코드를 줄이고 싶다.
* 기능의 생명주기와 확장 방식을 표준화해야 한다.

Unity에서는 다음과 같은 커스텀 프레임워크를 만들 수 있다.

```text
UI 관리 프레임워크
상태 머신 프레임워크
오브젝트 풀 프레임워크
이벤트 및 메시징 프레임워크
저장 프레임워크
Addressables 로딩 프레임워크
네트워크 요청 프레임워크
게임 상태 관리 프레임워크
```

---

## 22. 직접 만들지 않는 것이 좋은 경우

다음 상황에서는 직접 만들기보다 기존 기능이나 단순한 구현을 사용하는 것이 좋을 수 있다.

* 한 번만 사용할 기능이다.
* 요구사항이 아직 명확하지 않다.
* 단순한 유틸리티 함수로 충분하다.
* 기존 프레임워크가 요구사항을 충분히 만족한다.
* 유지보수할 인력과 시간이 부족하다.
* 구조보다 빠른 프로토타이핑이 중요한 단계이다.
* 아직 반복되는 패턴이 확인되지 않았다.

프레임워크는 미래에 필요할 것이라는 예상만으로 만드는 것보다, 실제 프로젝트에서 반복되는 구조가 확인된 뒤 추출하는 편이 안전하다.

이를 다음과 같이 표현할 수 있다.

> 프레임워크를 먼저 만들고 프로젝트에 적용하기보다, 여러 프로젝트에서 검증된 공통 구조를 프레임워크로 추출한다.

---

## 23. 프레임워크 개발 단계

자체 프레임워크는 다음 순서로 개발할 수 있다.

### 1단계: 반복되는 문제 확인

```text
각 UI가 서로 다른 방식으로 열린다.
팝업 닫기 순서가 일관되지 않다.
UI마다 이벤트 해제 방식이 다르다.
프리팹 생성 코드가 중복된다.
```

---

### 2단계: 공통 규칙 정의

```text
페이지는 한 번에 하나만 연다.
팝업은 스택으로 관리한다.
UI는 Open과 Close 생명주기를 가진다.
UI 생성은 Factory가 담당한다.
```

---

### 3단계: 최소한의 추상화 작성

```csharp
public interface IUIView
{
    void Open();
    void Close();
}
```

---

### 4단계: 실제 프로젝트에서 검증

여러 UI와 씬에 적용하여 다음을 확인한다.

* 사용하기 쉬운가?
* 요구사항을 충분히 표현할 수 있는가?
* 예외 상황을 처리할 수 있는가?
* 불필요한 규칙을 강제하지 않는가?

---

### 5단계: 확장 지점 제공

```text
UI 로딩 방식 교체
전환 애니메이션 교체
페이지 정책 교체
팝업 중복 정책 교체
```

---

### 6단계: 패키지와 샘플 제공

Unity Package Manager 패키지라면 다음과 같은 구조로 만들 수 있다.

```text
Packages/
└── com.company.gameframework/
    ├── package.json
    ├── Runtime/
    ├── Editor/
    ├── Tests/
    ├── Documentation~/
    └── Samples~/
```

`Runtime`에는 실제 게임에서 사용하는 코드를 넣는다.

`Editor`에는 Unity 에디터 확장 코드를 넣는다.

`Tests`에는 테스트 코드를 넣는다.

`Documentation~`에는 사용 설명서를 넣는다.

`Samples~`에는 사용 방법을 보여주는 예제 씬과 프리팹을 넣는다.

## 25. 프레임워크 품질을 평가하는 질문

프레임워크가 적절하게 설계되었는지 다음 질문으로 확인할 수 있다.

* 프레임워크가 해결하는 문제가 명확한가?
* 기본 사용법이 간단한가?
* 실행 흐름과 생명주기가 명확한가?
* 확장 지점이 잘 정의되어 있는가?
* 사용자가 내부 구현을 몰라도 사용할 수 있는가?
* 필요하지 않은 기능을 강제하지 않는가?
* 오류를 빠르고 명확하게 알려주는가?
* 단위 테스트와 통합 테스트가 가능한가?
* 문서와 샘플이 충분한가?
* 외부 프레임워크와 Unity 버전 변화에 대응할 수 있는가?
* 프레임워크를 사용하지 않았을 때보다 실제 복잡성이 줄어드는가?
* 프로젝트의 핵심 게임 로직이 프레임워크에 지나치게 종속되지 않는가?

```text
Unity 기본 기능 중심
간단한 공통 베이스 클래스
소수의 유틸리티
수동 의존성 연결
```

작은 프로젝트에서는 복잡한 프레임워크보다 단순한 구조가 효과적일 수 있다.

```text
Addressables 로더
이벤트 시스템
```

반복되는 기능을 중심으로 프레임워크를 적용할 수 있다.

```text
모듈별 프레임워크
```

대규모 프로젝트에서는 팀 전체가 동일한 규칙을 따르도록 프레임워크를 표준화할 필요가 있다.

## 27. 프레임워크의 핵심 가치

프레임워크의 핵심 가치는 단순히 코드를 재사용하는 데 있지 않다.

프레임워크는 다음을 재사용하게 한다.

```text
코드
구조
실행 흐름
생명주기
확장 방식
오류 처리 방식
팀의 개발 규칙
```

라이브러리가 주로 기능을 재사용하게 한다면, 프레임워크는 기능과 함께 애플리케이션을 만드는 방식을 재사용하게 한다.

---

## 정리

소프트웨어 프레임워크는 특정 종류의 애플리케이션을 개발하기 위해 반복적으로 필요한 구조, 실행 흐름, 공통 기능, 생명주기와 확장 지점을 제공하는 소프트웨어 기반이다.

프레임워크의 가장 중요한 특징은 **제어의 역전**이다.

```text
라이브러리
개발자 코드 → 라이브러리 호출

프레임워크
프레임워크 → 개발자 코드 호출
```

Unity에서는 다음과 같은 구조가 프레임워크의 특징을 보여준다.

```text
Unity 게임 루프
 ├── Awake 호출
 ├── Start 호출
 ├── Update 호출
 ├── 물리 처리
 ├── 렌더링
 └── OnDestroy 호출
```

프레임워크를 사용하면 다음과 같은 장점을 얻을 수 있다.

* 반복적인 기능을 다시 개발하지 않아도 된다.
* 개발 속도와 생산성이 높아진다.
* 프로젝트 전체에 일관된 구조를 적용할 수 있다.
* 검증된 실행 흐름과 공통 기능을 사용할 수 있다.
* 새로운 기능을 정의된 확장 지점을 통해 추가할 수 있다.
* 여러 개발자가 동일한 규칙으로 작업할 수 있다.

반면 다음 사항에 주의해야 한다.

* 프레임워크 학습 비용
* 프레임워크 규칙에 대한 제약
* 내부 동작이 숨겨지는 문제
* 버전과 패키지 호환성
* 특정 프레임워크에 대한 과도한 종속
* 작은 프로젝트에 대한 과도한 설계

Unity 프로젝트에서 프레임워크를 설계하거나 도입할 때는 다음 원칙이 중요하다.

```text
반복되는 문제를 해결한다.
기본 사용법은 단순하게 만든다.
생명주기와 실행 흐름을 명확하게 한다.
필요한 확장 지점을 제공한다.
핵심 게임 로직과 외부 프레임워크를 분리한다.
문서와 샘플을 함께 제공한다.
프로젝트 규모에 필요한 만큼만 적용한다.
```

프레임워크의 목적은 클래스와 추상화를 많이 만드는 것이 아니다.

> 프레임워크의 목적은 반복되는 기술적 복잡성과 개발 규칙을 한곳에서 관리하여, 개발자가 실제 게임의 본질적인 기능과 규칙에 집중할 수 있도록 만드는 것이다.
