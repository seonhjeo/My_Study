아래는 소프트웨어 공학에서 라이브러리의 의미, 특징, 동작 방식, 프레임워크 및 모듈과의 차이, Unity에서의 활용 방법을 정리한 마크다운 문서이다.

# 소프트웨어 라이브러리

소프트웨어 라이브러리(Software Library)는 프로그램을 개발할 때 반복적으로 필요한 기능을 재사용할 수 있도록 만들어 놓은 함수, 클래스, 인터페이스 및 데이터의 집합이다.

개발자는 필요한 기능을 처음부터 직접 구현하는 대신 라이브러리가 제공하는 API를 호출하여 사용할 수 있다.

간단하게 표현하면 다음과 같다.

> 라이브러리는 특정 기능을 수행하는 재사용 가능한 코드의 모음이며, 개발자가 필요한 시점에 직접 호출해서 사용한다.

Unity 게임 개발에서는 다음과 같은 기능을 라이브러리로 사용할 수 있다.

* JSON 직렬화 및 역직렬화
* 바이너리 직렬화
* 수학 계산
* 컬렉션 처리
* 비동기 프로그래밍
* 트윈 애니메이션
* 반응형 프로그래밍
* 로깅
* 암호화
* 압축
* 네트워크 통신
* 데이터베이스 접근

대표적인 예시는 다음과 같다.

```text
MessagePack
Newtonsoft.Json
UniTask
R3
DOTween
LINQ
System.Text.Json
System.IO.Compression
```

---

## 1. 라이브러리란?

라이브러리는 특정 기능을 쉽게 사용할 수 있도록 미리 구현된 코드의 집합이다.

예를 들어 두 값 중 더 큰 값을 구하는 기능이 필요하다면 직접 조건문을 작성할 수 있다.

```csharp
public int GetMaximum(int first, int second)
{
    if (first > second)
        return first;

    return second;
}
```

하지만 C# 표준 라이브러리의 `Math.Max()`를 사용하면 더 간단하게 구현할 수 있다.

```csharp
int maximum = Math.Max(first, second);
```

Unity에서는 `Mathf.Max()`를 사용할 수도 있다.

```csharp
int maximum = Mathf.Max(first, second);
```

개발자는 최대값을 비교하는 알고리즘을 매번 직접 구현하지 않고 라이브러리가 제공하는 기능을 호출한다.

라이브러리를 사용하는 일반적인 구조는 다음과 같다.

```text
개발자 코드
    ↓
라이브러리 API 호출
    ↓
라이브러리 내부 기능 실행
    ↓
결과 반환
```

## 2. 라이브러리의 목적

라이브러리의 가장 기본적인 목적은 코드 재사용이다.

여러 프로젝트에서 반복적으로 필요한 기능을 매번 다시 개발하면 다음과 같은 문제가 발생한다.

* 개발 시간이 증가한다.
* 비슷한 코드가 여러 곳에 중복된다.
* 프로젝트마다 구현 방식이 달라진다.
* 동일한 오류가 반복될 수 있다.
* 테스트와 유지보수 비용이 증가한다.
* 이미 해결된 기술적 문제를 다시 해결해야 한다.

라이브러리를 사용하면 검증된 기능을 여러 프로젝트에서 재사용할 수 있다.

예를 들어 JSON 데이터를 직접 분석하려면 문자열의 구조를 해석하고 자료형을 변환해야 한다.

하지만 JSON 라이브러리를 사용하면 다음처럼 객체와 문자열을 변환할 수 있다.

```csharp
[Serializable]
public class PlayerData
{
    public string playerName;
    public int level;
    public int gold;
}
```

```csharp
PlayerData playerData = new PlayerData
{
    playerName = "Player01",
    level = 10,
    gold = 500
};

string json = JsonUtility.ToJson(playerData);
```

역직렬화도 간단하게 처리할 수 있다.

```csharp
PlayerData loadedData =
    JsonUtility.FromJson<PlayerData>(json);
```

라이브러리가 JSON 문법 분석, 문자열 생성 및 자료형 변환을 대신 수행한다.

## 3. 라이브러리의 구성 요소

라이브러리는 일반적으로 다음 요소들로 구성된다.

### 함수와 메서드

특정 연산이나 작업을 수행한다.

```csharp
float distance = Vector3.Distance(
    transform.position,
    target.position);
```

`Vector3.Distance()`는 두 위치 사이의 거리를 계산하는 라이브러리 메서드이다.

---

### 클래스와 구조체

특정 데이터와 동작을 하나의 자료형으로 제공한다.

```csharp
List<int> scores = new List<int>();
```

`List<T>`는 크기가 동적으로 변하는 목록을 제공하는 표준 라이브러리 클래스이다.

Unity의 `Vector3`는 3차원 벡터 계산을 제공하는 구조체이다.

```csharp
Vector3 direction = target.position - transform.position;
```

---

### 인터페이스

라이브러리를 사용하는 코드가 구현하거나 따라야 하는 계약을 제공할 수 있다.

```csharp
public class ScoreComparer : IComparer<int>
{
    public int Compare(int first, int second)
    {
        return second.CompareTo(first);
    }
}
```

`IComparer<T>`는 .NET 라이브러리가 제공하는 인터페이스이며, 개발자가 비교 규칙을 구현할 수 있게 한다.

---

### 열거형과 상수

라이브러리의 동작 방식을 선택하거나 설정하는 값을 제공한다.

```csharp
FileMode mode = FileMode.Create;
```

```csharp
LoadSceneMode loadMode = LoadSceneMode.Additive;
```

---

### 예외 타입

잘못된 사용이나 오류 상황을 표현한다.

```csharp
throw new ArgumentNullException(nameof(target));
```

---

### 확장 메서드

기존 클래스에 새로운 기능을 추가하는 것처럼 사용할 수 있다.

```csharp
public static class CollectionExtensions
{
    public static bool IsNullOrEmpty<T>(
        this ICollection<T> collection)
    {
        return collection == null || collection.Count == 0;
    }
}
```

사용 예시는 다음과 같다.

```csharp
List<int> scores = new();

if (scores.IsNullOrEmpty())
{
    Debug.Log("점수가 없습니다.");
}
```

## 4. 라이브러리의 핵심 특징

### 재사용 가능한 기능을 제공한다

라이브러리는 여러 프로젝트나 시스템에서 사용할 수 있는 기능을 제공한다.

예를 들어 저장 기능을 위한 라이브러리는 여러 게임에서 동일하게 사용할 수 있다.

```csharp
public static class FileUtility
{
    public static void SaveText(
        string path,
        string content)
    {
        string directory =
            Path.GetDirectoryName(path);

        if (!string.IsNullOrEmpty(directory))
            Directory.CreateDirectory(directory);

        File.WriteAllText(path, content);
    }

    public static string LoadText(string path)
    {
        if (!File.Exists(path))
            return string.Empty;

        return File.ReadAllText(path);
    }
}
```

---

### 특정 문제에 집중한다

라이브러리는 일반적으로 하나의 특정 기능 영역을 해결한다.

```text
JSON 라이브러리
 └── JSON 직렬화와 역직렬화

압축 라이브러리
 └── 데이터 압축과 해제

수학 라이브러리
 └── 수치 및 벡터 계산

트윈 라이브러리
 └── 값과 애니메이션 보간

로깅 라이브러리
 └── 로그 기록과 출력
```

---

### 개발자가 직접 호출한다

라이브러리의 가장 중요한 특징 중 하나는 개발자 코드가 호출 흐름을 제어한다는 점이다.

```csharp
string json = JsonUtility.ToJson(data);
```

개발자가 필요한 시점에 `ToJson()`을 호출한다.

```text
개발자 코드
   ↓
JsonUtility.ToJson()
   ↓
결과 사용
```

라이브러리는 일반적으로 프로그램 전체의 실행 흐름을 통제하지 않는다.

---

### 내부 구현을 숨긴다

개발자는 라이브러리의 내부 알고리즘을 몰라도 공개된 API를 통해 사용할 수 있다.

```csharp
int result = Math.Max(10, 20);
```

`Math.Max()` 내부가 어떤 명령어와 비교 알고리즘으로 동작하는지 몰라도 사용할 수 있다.

이를 정보 은닉과 추상화라고 볼 수 있다.

---

### 공개 API를 제공한다

라이브러리는 외부에서 사용할 수 있는 공개 인터페이스를 제공한다.

```csharp
public interface IDataSerializer
{
    string Serialize<T>(T data);
    T Deserialize<T>(string value);
}
```

사용자는 내부 구현 대신 이 API에 의존한다.

---

## 5. 라이브러리의 동작 방식

일반적인 라이브러리는 다음 순서로 사용된다.

```text
1. 라이브러리를 프로젝트에 설치하거나 참조한다.
2. 필요한 네임스페이스를 불러온다.
3. 라이브러리의 클래스나 객체를 생성한다.
4. 필요한 메서드를 호출한다.
5. 결과값이나 발생한 이벤트를 처리한다.
6. 필요한 경우 객체나 리소스를 해제한다.
```

예를 들어 파일을 압축하는 라이브러리를 사용한다고 가정해 보자.

```csharp
using System.IO;
using System.IO.Compression;
```

```csharp
public static class CompressionUtility
{
    public static void CompressDirectory(
        string sourceDirectory,
        string destinationFile)
    {
        if (!Directory.Exists(sourceDirectory))
        {
            throw new DirectoryNotFoundException(
                sourceDirectory);
        }

        ZipFile.CreateFromDirectory(
            sourceDirectory,
            destinationFile);
    }
}
```

개발자가 필요할 때 직접 호출한다.

```csharp
CompressionUtility.CompressDirectory(
    sourceDirectory,
    destinationFile);
```

## 6. 라이브러리와 프레임워크의 차이

라이브러리와 프레임워크는 모두 재사용 가능한 코드를 제공하지만, 가장 큰 차이는 실행 흐름의 제어권이다.

### 라이브러리

개발자가 라이브러리를 호출한다.

```text
개발자 코드
    ↓
라이브러리
```

```csharp
string json = JsonUtility.ToJson(data);
```

개발자가 호출 시점과 실행 순서를 결정한다.

---

### 프레임워크

프레임워크가 개발자의 코드를 호출한다.

```text
프레임워크
    ↓
개발자 코드
```

```csharp
public class PlayerMovement : MonoBehaviour
{
    private void Update()
    {
        // Unity 프레임워크가 호출한다.
    }
}
```

개발자가 `Update()`를 직접 반복 호출하는 것이 아니라 Unity가 적절한 시점에 호출한다.

이러한 차이를 제어의 역전(Inversion of Control)이라고 한다.

---

### 라이브러리와 프레임워크 비교

| 구분         | 라이브러리                              | 프레임워크                            |
| ---------- | ---------------------------------- | -------------------------------- |
| **의미**     | 특정 기능을 제공하는 재사용 가능한 코드 모음          | 애플리케이션의 기본 구조와 실행 흐름을 제공하는 개발 기반 |
| **제어권**    | 개발자 코드가 가진다.                       | 프레임워크가 가진다.                      |
| **호출 방향**  | 개발자가 라이브러리를 호출한다.                  | 프레임워크가 개발자 코드를 호출한다.             |
| **적용 범위**  | 특정 기능이나 기술 영역                      | 애플리케이션 전체 또는 넓은 기능 영역            |
| **구조 강제성** | 낮다.                                | 상대적으로 높다.                        |
| **예시**     | MessagePack, Newtonsoft.Json, LINQ | Unity, ASP.NET Core, VContainer  |
| **사용 방법**  | 필요한 위치에서 API를 직접 호출한다.             | 프레임워크의 규약과 생명주기를 따른다.            |

## 7. 라이브러리와 모듈의 차이

모듈은 특정 책임이나 기능을 하나의 경계로 묶은 소프트웨어 단위이다.

라이브러리는 외부 코드에서 재사용할 수 있도록 기능을 제공하는 코드의 집합이다.

두 개념은 겹칠 수 있지만 관점이 다르다.

```text
모듈
 └── 시스템 내부를 어떤 책임 단위로 나눌 것인가?

라이브러리
 └── 특정 기능을 다른 코드에서 어떻게 재사용하게 할 것인가?
```

예를 들어 Unity 게임의 전투 모듈은 다음과 같이 구성될 수 있다.

```text
Combat Module
 ├── Character
 ├── DamageCalculator
 ├── AttackController
 ├── IDamageable
 └── StatusEffect
```

이 전투 모듈을 UPM 패키지나 DLL로 만들어 여러 프로젝트에 배포하면 라이브러리로 사용할 수도 있다.

따라서 하나의 코드 집합이 프로젝트 내부에서는 모듈이고, 외부 프로젝트에 재사용되면 라이브러리 역할을 할 수 있다.

## 8. 라이브러리와 API의 차이

API(Application Programming Interface)는 다른 코드가 특정 기능을 사용할 수 있도록 공개한 인터페이스이다.

라이브러리는 기능을 실제로 제공하는 코드의 집합이고, API는 라이브러리를 사용하는 방법과 접점을 의미한다.

예를 들어 다음 클래스가 라이브러리의 일부라고 가정해 보자.

```csharp
public class DamageCalculator
{
    public int Calculate(int attack, int defense)
    {
        return Math.Max(1, attack - defense);
    }
}
```

외부에서 사용할 수 있는 다음 부분이 API에 해당한다.

```csharp
public int Calculate(int attack, int defense)
```

내부 계산 방식은 구현 세부 사항이다.

```text
라이브러리
 ├── 공개 API
 └── 내부 구현
```

좋은 라이브러리는 사용하기 쉽고 일관된 API를 제공해야 한다.

## 9. 라이브러리와 SDK의 차이

SDK(Software Development Kit)는 특정 플랫폼이나 서비스를 개발하기 위한 도구 모음이다.

SDK에는 라이브러리뿐 아니라 다음과 같은 요소가 포함될 수 있다.

* 라이브러리
* API
* 컴파일 도구
* 디버깅 도구
* 예제 프로젝트
* 문서
* 에뮬레이터
* 빌드 도구
* 설정 파일
* 개발용 유틸리티

구조는 다음과 같다.

```text
SDK
 ├── Library
 ├── Documentation
 ├── Samples
 ├── Build Tools
 ├── Debug Tools
 └── Configuration
```

예를 들어 플랫폼 SDK에는 플랫폼 기능을 호출하는 라이브러리와 함께 빌드 및 테스트 도구가 포함될 수 있다.

따라서 SDK는 일반적으로 라이브러리보다 더 넓은 개념이다.

## 10. 라이브러리의 종류

### 표준 라이브러리

프로그래밍 언어나 실행 환경에 기본적으로 포함된 라이브러리이다.

C#과 .NET에서는 다음 기능이 제공된다.

```text
System
System.Collections.Generic
System.IO
System.Linq
System.Net.Http
System.Threading
System.Threading.Tasks
```

예시:

```csharp
List<int> scores = new();
Dictionary<string, int> itemCounts = new();
```

```csharp
int highestScore = scores.Max();
```

---

### Unity 기본 라이브러리

Unity에서 기본으로 제공하는 기능이다.

```text
UnityEngine
UnityEngine.UI
UnityEngine.SceneManagement
UnityEngine.AI
UnityEngine.Events
```

### 정적 라이브러리와 동적 라이브러리

일반적인 소프트웨어 환경에서는 라이브러리의 연결 방식에 따라 정적 라이브러리와 동적 라이브러리로 나눌 수 있다.

#### 정적 라이브러리

빌드할 때 라이브러리 코드가 실행 파일에 포함된다.

```text
애플리케이션 코드
       +
정적 라이브러리
       ↓
하나의 실행 파일
```

장점:

* 실행 시 별도의 라이브러리 파일이 필요하지 않을 수 있다.
* 배포가 단순해질 수 있다.

단점:

* 실행 파일 크기가 커질 수 있다.
* 라이브러리를 업데이트하려면 다시 빌드해야 한다.

#### 동적 라이브러리

실행 시 별도의 라이브러리 파일을 불러온다.

Windows의 `.dll` 등이 대표적이다.

```text
애플리케이션
    ↓
외부 DLL 로드
```

장점:

* 여러 프로그램이 라이브러리를 공유할 수 있다.
* 라이브러리만 교체할 수 있는 경우가 있다.

단점:

* 라이브러리 파일 누락이나 버전 충돌이 발생할 수 있다.
* 플랫폼별 바이너리 호환성을 고려해야 한다.

Unity에서는 관리 코드 DLL과 네이티브 플러그인을 모두 사용할 수 있다.

## 11. Unity에서 라이브러리를 사용하는 방법

Unity에서는 여러 방법으로 라이브러리를 설치하거나 참조할 수 있다.

### Unity Package Manager

패키지를 `Packages/manifest.json`에 등록하거나 Package Manager 창에서 설치할 수 있다.

일반적인 패키지 구조는 다음과 같다.

```text

└── com.company.library/
    ├── package.json
    ├── Runtime/
    ├── Editor/
    ├── Tests/
    ├── Documentation~/
    └── Samples~/
```

---

### Git URL

Git 저장소에 UPM 패키지 구조가 있다면 Git URL로 설치할 수 있다.

```json
{
  "dependencies": {
    "com.company.library":
      "https://github.com/company/library.git?path=/Package"
  }
}
```

실제 URL과 브랜치, 태그 및 패키지 경로는 해당 라이브러리의 문서를 따라야 한다.

---

### DLL 파일

컴파일된 `.dll` 파일을 Unity 프로젝트에 추가할 수 있다.

일반적으로 다음 위치를 사용한다.

```text

└── Plugins/
    └── SomeLibrary.dll
```

Unity의 Plugin Inspector에서 지원 플랫폼과 CPU 아키텍처를 설정할 수 있다.

---

### NuGet

Unity는 기본적으로 NuGet 패키지를 직접 관리하지 않기 때문에 별도의 도구를 사용할 수 있다.

```text
NuGetForUnity
직접 DLL 추출
UPM 변환 패키지
```

NuGet 패키지가 Unity의 런타임 및 IL2CPP 환경과 호환되는지 확인해야 한다.

---

### 소스 코드 직접 포함

라이브러리 소스 코드를 프로젝트의 `Assets` 폴더에 직접 추가할 수도 있다.

```text
Assets/
└── ThirdParty/
    └── SomeLibrary/
```

간단하지만 라이브러리 업데이트와 버전 관리가 어려워질 수 있다.

## 12. Unity에서의 라이브러리 사용 예시

### LINQ를 이용한 적 검색

```csharp
using System.Collections.Generic;
using System.Linq;
using UnityEngine;

public class EnemySelector : MonoBehaviour
{
    public Enemy FindNearestEnemy(
        IReadOnlyList<Enemy> enemies)
    {
        if (enemies == null || enemies.Count == 0)
            return null;

        Vector3 currentPosition = transform.position;

        return enemies
            .Where(enemy => enemy != null && enemy.IsAlive)
            .OrderBy(enemy =>
                (enemy.transform.position - currentPosition)
                .sqrMagnitude)
            .FirstOrDefault();
    }
}
```

LINQ 라이브러리가 필터링, 정렬 및 첫 번째 항목 선택 기능을 제공한다.

다만 매 프레임 대량의 데이터를 처리할 때는 할당과 성능 비용을 확인해야 한다.

---

### JSON 저장 라이브러리 사용

```csharp
using System;
using System.IO;
using UnityEngine;

[Serializable]
public class GameSaveData
{
    public string playerName;
    public int level;
    public int gold;
}
```

```csharp
public class JsonSaveService
{
    private readonly string filePath;

    public JsonSaveService(string fileName)
    {
        filePath = Path.Combine(
            Application.persistentDataPath,
            fileName);
    }

    public void Save(GameSaveData data)
    {
        if (data == null)
            throw new ArgumentNullException(nameof(data));

        string json =
            JsonUtility.ToJson(data, prettyPrint: true);

        File.WriteAllText(filePath, json);
    }

    public GameSaveData Load()
    {
        if (!File.Exists(filePath))
            return null;

        string json = File.ReadAllText(filePath);

        return JsonUtility.FromJson<GameSaveData>(json);
    }
}
```

`JsonUtility`와 `System.IO` 라이브러리를 함께 사용한 예시이다.

### 비동기 라이브러리를 감싸는 구조

이렇게 하면 로딩 라이브러리를 교체할 때 핵심 게임 로직의 변경을 줄일 수 있다.

## 13. 좋은 라이브러리의 특징

### 목적이 명확하다

라이브러리가 해결하는 문제가 명확해야 한다.

좋은 예:

```text

UI 트윈 애니메이션을 제공한다.
메시지를 직렬화한다.

```

불명확한 예:

```text
모든 공통 기능을 제공한다.
게임 개발에 필요한 모든 것을 처리한다.
```

목적이 너무 넓으면 라이브러리가 거대해지고 내부 응집도가 낮아질 수 있다.

### 유지보수 비용을 줄일 수 있다

## 15. 라이브러리 사용의 단점

### 외부 코드에 의존하게 된다

라이브러리에 문제가 발생하거나 유지보수가 중단되면 프로젝트도 영향을 받을 수 있다.

---

### 버전 충돌이 발생할 수 있다

서로 다른 패키지가 같은 라이브러리의 서로 다른 버전을 요구할 수 있다.

```text
Package A → Library 1.0 필요
Package B → Library 2.0 필요
```

Unity에서는 어셈블리 충돌이나 중복 클래스 오류가 발생할 수도 있다.

---

### 프로젝트 크기가 증가할 수 있다

사용하지 않는 기능까지 포함된 큰 라이브러리를 추가하면 빌드 크기와 컴파일 시간이 증가할 수 있다.

---

### 성능 비용이 숨겨질 수 있다

간단한 API 뒤에서 많은 할당, 리플렉션, 파일 접근 또는 복잡한 연산이 발생할 수 있다.

```csharp
var nearest = enemies
    .Where(enemy => enemy.IsAlive)
    .OrderBy(enemy => enemy.Distance)
    .FirstOrDefault();
```

코드는 간단하지만 호출 빈도와 데이터 크기에 따라 성능 비용이 커질 수 있다.

---

### 내부 동작을 이해하기 어려울 수 있다

오류가 라이브러리 내부에서 발생하면 호출 흐름을 추적하기 어려울 수 있다.

소스 코드가 공개되지 않은 바이너리 라이브러리는 문제 해결이 더 어려울 수 있다.

---

### 보안 문제가 포함될 수 있다

외부 라이브러리에는 보안 취약점이나 악성 코드가 포함될 가능성이 있다.

라이브러리의 출처, 유지보수 상태 및 배포 경로를 확인해야 한다.

---

### 플랫폼 호환성 문제가 발생할 수 있다

Unity에서는 특히 다음 환경과의 호환성을 확인해야 한다.

* Mono
* IL2CPP
* Android
* iOS
* WebGL
* Windows
* macOS
* 콘솔
* AOT 컴파일
* 코드 스트리핑

에디터에서는 정상 동작하지만 실제 빌드에서는 실패할 수도 있다.

---

### 라이선스 제약이 있을 수 있다

라이브러리마다 사용, 수정 및 배포 조건이 다르다.

다음 내용을 확인해야 한다.

* 상업적 사용 가능 여부
* 저작권 표시 의무
* 소스 코드 공개 의무
* 수정 및 재배포 가능 여부
* 유료 라이선스 필요 여부

## 16. 라이브러리를 선택할 때 확인할 사항

### 프로젝트 요구사항을 충족하는가?

필요하지 않은 기능이 많은 유명 라이브러리보다 현재 문제를 정확하게 해결하는 라이브러리가 더 적합할 수 있다.

---

### 지원하는 Unity 버전은 무엇인가?

라이브러리가 현재 사용하는 Unity 버전과 호환되는지 확인해야 한다.

---

### IL2CPP와 AOT를 지원하는가?

리플렉션, 런타임 코드 생성 및 제네릭 사용 방식에 따라 IL2CPP 빌드에서 문제가 발생할 수 있다.

---

### 대상 플랫폼을 지원하는가?

에디터와 Windows에서만 동작하고 모바일이나 WebGL에서는 동작하지 않을 수도 있다.

---

### 유지보수가 계속되는가?

다음 항목을 확인하는 것이 좋다.

* 최근 업데이트 날짜
* 버그 보고에 대한 대응
* 최신 Unity 버전 지원
* 문서 상태
* 릴리스 주기
* 커뮤니티 활동

---

### 라이선스가 적합한가?

프로젝트의 상업적 배포와 소스 공개 정책에 맞는지 확인해야 한다.

---

### 성능이 요구사항에 맞는가?

다음 사항을 직접 측정하는 것이 좋다.

* 메모리 할당
* 실행 시간
* GC 발생
* 직렬화 크기
* 로딩 속도
* 빌드 크기

---

### 의존성이 과도하지 않은가?

작은 기능 하나를 위해 여러 패키지를 추가해야 한다면 도입 비용이 더 커질 수 있다.

---

### 제거하거나 교체하기 쉬운가?

라이브러리 API를 프로젝트 전체에서 직접 사용하면 나중에 교체하기 어렵다.

외부 라이브러리를 인터페이스 뒤에서 감싸는 방식을 고려할 수 있다.

## 17. 외부 라이브러리 의존성을 격리하는 방법

외부 라이브러리를 프로젝트 전체에서 직접 호출하면 라이브러리 교체 시 수정 범위가 커진다.

예를 들어 모든 클래스가 특정 직렬화 라이브러리를 직접 사용한다고 가정해 보자.

```csharp
string json = SpecificJsonLibrary.Serialize(data);
```

프로젝트 전체에 이 코드가 퍼져 있으면 다른 직렬화 방식으로 변경하기 어렵다.

인터페이스를 정의할 수 있다.

```csharp
public interface IDataSerializer
{
    string Serialize<T>(T data);
    T Deserialize<T>(string value);
}
```

Unity의 `JsonUtility`를 사용하는 구현체는 다음과 같다.

```csharp
using System;
using UnityEngine;

public class UnityJsonSerializer : IDataSerializer
{
    public string Serialize<T>(T data)
    {
        if (data == null)
            throw new ArgumentNullException(nameof(data));

        return JsonUtility.ToJson(data);
    }

    public T Deserialize<T>(string value)
    {
        if (string.IsNullOrWhiteSpace(value))
        {
            throw new ArgumentException(
                "역직렬화할 문자열이 비어 있습니다.",
                nameof(value));
        }

        return JsonUtility.FromJson<T>(value);
    }
}
```

저장 시스템은 구체 라이브러리가 아닌 인터페이스에 의존한다.

```csharp
using System;
using System.IO;

public class SaveService
{
    private readonly IDataSerializer serializer;
    private readonly string filePath;

    public SaveService(
        IDataSerializer serializer,
        string filePath)
    {
        this.serializer = serializer
            ?? throw new ArgumentNullException(
                nameof(serializer));

        this.filePath = filePath;
    }

    public void Save<T>(T data)
    {
        string serialized =
            serializer.Serialize(data);

        File.WriteAllText(filePath, serialized);
    }

    public T Load<T>()
    {
        string serialized =
            File.ReadAllText(filePath);

        return serializer.Deserialize<T>(serialized);
    }
}
```

객체를 연결하는 위치에서 실제 구현을 선택한다.

```csharp
IDataSerializer serializer =
    new UnityJsonSerializer();

var saveService = new SaveService(
    serializer,
    saveFilePath);
```

이 구조에서는 다른 라이브러리 기반의 구현체를 추가해도 `SaveService`를 수정할 필요가 없다.

```text
SaveService
     ↓
IDataSerializer
     ↑
 ┌───┴──────────────────┐
UnityJsonSerializer   다른 구현체
```

## 19. 간단한 Unity 라이브러리 제작 예시

게임에서 확률 계산을 공통으로 사용한다고 가정해 보자.

```csharp
using System;
using UnityEngine;

namespace GameLibrary.Random
{
    public static class ProbabilityUtility
    {
        public static bool IsSuccess(float probability)
        {
            if (probability < 0f || probability > 1f)
            {
                throw new ArgumentOutOfRangeException(
                    nameof(probability),
                    "확률은 0과 1 사이여야 합니다.");
            }

            return UnityEngine.Random.value < probability;
        }

        public static bool IsPercentSuccess(
            float percentage)
        {
            if (percentage < 0f || percentage > 100f)
            {
                throw new ArgumentOutOfRangeException(
                    nameof(percentage),
                    "확률은 0과 100 사이여야 합니다.");
            }

            return IsSuccess(percentage / 100f);
        }
    }
}
```

사용 코드는 다음과 같다.

```csharp
using GameLibrary.Random;
using UnityEngine;

public class CriticalAttack
{
    private readonly float criticalChance;

    public CriticalAttack(float criticalChance)
    {
        this.criticalChance = criticalChance;
    }

    public int CalculateDamage(int baseDamage)
    {
        bool isCritical =
            ProbabilityUtility.IsPercentSuccess(
                criticalChance);

        return isCritical
            ? baseDamage * 2
            : baseDamage;
    }
}
```

이 라이브러리는 확률 판정이라는 특정 기능만 담당한다.

## 21. 라이브러리 API 설계 예시

```csharp
var parser = new CsvParser();

parser.SetDelimiter(',');
parser.SetEncoding("UTF-8");
parser.SetIgnoreEmptyLine(true);
parser.SetHeaderMode(1);
parser.Initialize();

CsvResult result = parser.Run(

설정 과정이 지나치게 복잡하다.

CsvResult result =

CsvOptions options = new CsvOptions

CsvResult result =
    CsvSerializer.Deserialize(
        File.ReadAllText(path),
        options);
```

기본 사용법은 단순하게 하고 고급 설정은 선택적으로 제공하는 것이 좋다.

## 22. 라이브러리의 버전 관리

여러 프로젝트에서 라이브러리를 사용하려면 버전을 명확하게 관리해야 한다.

일반적으로 시맨틱 버저닝(Semantic Versioning)을 사용할 수 있다.

```text
MAJOR.MINOR.PATCH
```

예시:

```text
2.4.1
```

각 숫자의 의미는 다음과 같다.

| 구분        | 의미                | 예시              |
| --------- | ----------------- | --------------- |
| **MAJOR** | 기존 코드와 호환되지 않는 변경 | `1.5.0 → 2.0.0` |
| **MINOR** | 기존 코드와 호환되는 기능 추가 | `1.5.0 → 1.6.0` |
| **PATCH** | 기존 코드와 호환되는 버그 수정 | `1.5.0 → 1.5.1` |

공개 API를 제거하거나 의미를 변경하면 일반적으로 주요 버전을 올리는 것이 적절하다.

## 23. 라이브러리 변경 시 호환성

라이브러리를 수정할 때 기존 사용자의 코드를 깨뜨리지 않는 것이 중요하다.

기존 API:

```csharp
public void Save(string path)
{
}
```

변경된 API:

```csharp
public void Save(
    string path,
    SaveOptions options)
{
}
```

기존 메서드를 바로 제거하면 모든 사용 코드가 컴파일되지 않는다.

기존 API를 유지하면서 새로운 오버로드를 추가할 수 있다.

```csharp
public void Save(string path)
{
    Save(path, SaveOptions.Default);
}

public void Save(
    string path,
    SaveOptions options)
{
    // 저장 처리
}
```

기존 API를 제거해야 한다면 일정 기간 사용 중단 표시를 제공할 수 있다.

```csharp
[Obsolete(
    "Save(string)은 이후 버전에서 제거됩니다. " +
    "Save(string, SaveOptions)을 사용하세요.")]
public void Save(string path)
{
    Save(path, SaveOptions.Default);
}
```

using NUnit.Framework;

public class ProbabilityUtilityTests

Unity API, 파일 시스템 및 다른 라이브러리와 함께 사용할 때 정상 동작하는지 검증한다.

## 25. 라이브러리 사용 시 흔한 실수

### 유명하다는 이유만으로 도입

현재 프로젝트에 필요하지 않은 라이브러리를 추가하면 의존성과 복잡성만 증가할 수 있다.

---

### 프로젝트 전체에서 외부 API 직접 사용

라이브러리 교체가 어려워지고 외부 구현이 핵심 로직에 침투한다.

---

### 버전을 고정하지 않음

업데이트 시 예상하지 못한 API 변경과 빌드 오류가 발생할 수 있다.

---

### 라이선스를 확인하지 않음

상업적 배포나 소스 코드 공개 의무에서 문제가 생길 수 있다.

---

### 에디터에서만 테스트

Unity 에디터에서는 동작하지만 IL2CPP나 모바일 빌드에서 실패할 수 있다.

---

### 라이브러리와 프레임워크를 혼동

단순히 API를 호출하는 도구인지, 프로젝트 전체의 실행 방식과 생명주기에 영향을 주는 도구인지 구분해야 한다.

---

### 모든 공통 코드를 하나의 라이브러리에 모음

관련 없는 기능이 하나의 패키지에 모이면 응집도가 낮아지고 작은 기능을 사용하기 위해 전체 라이브러리를 설치해야 한다.

```text
CommonLibrary
 ├── CSV
 ├── UI
 ├── Network
 ├── AI
 ├── Save
 ├── Audio
 └── Editor Tools
```

필요하다면 기능별 라이브러리나 하위 모듈로 분리하는 것이 좋다.

## 26. 라이브러리와 소프트웨어 아키텍처

라이브러리는 아키텍처를 구성하는 도구 중 하나이다.

아키텍처는 라이브러리를 시스템의 어느 영역에서 사용할지 결정한다.

예를 들어 계층형 아키텍처에서는 다음과 같이 배치할 수 있다.

```text
Presentation
 └── UI 트윈 라이브러리 사용

Application
 └── 가능하면 특정 외부 라이브러리에 대한 의존 최소화

Domain
 └── 순수 C#과 표준 라이브러리 중심

Infrastructure
 ├── JSON 라이브러리
 ├── 네트워크 라이브러리
 ├── MessagePack
 └── Addressables
```

핵심 게임 규칙인 Domain이 특정 외부 직렬화나 네트워크 라이브러리에 강하게 의존하지 않게 하는 것이 좋다.

```text
Domain
   ↓
추상 인터페이스
   ↑
외부 라이브러리 기반 구현체
```

## 27. 라이브러리와 SOLID 원칙

### SRP

라이브러리는 하나의 명확한 기능 영역에 집중해야 한다.

```text
CsvLibrary
 └── CSV 읽기와 쓰기

SaveLibrary
 └── 저장과 불러오기
```

---

### OCP

새로운 기능을 추가할 때 기존 핵심 코드를 크게 수정하지 않고 확장할 수 있어야 한다.

```text
IDataSerializer
 ├── JsonSerializer
 ├── MessagePackSerializer
 └── BinarySerializer
```

---

### LSP

같은 인터페이스의 구현체는 서로 교체해도 호출 코드가 정상적으로 동작해야 한다.

---

### ISP

사용자가 필요하지 않은 기능까지 의존하지 않도록 인터페이스를 작고 목적에 맞게 나눈다.

```csharp
public interface IDataWriter
{
    void Write<T>(T data);
}

public interface IDataReader
{
    T Read<T>();
}
```

읽기만 필요한 코드는 `IDataReader`에만 의존할 수 있다.

---

### DIP

상위 수준의 게임 로직은 구체적인 외부 라이브러리가 아니라 추상화에 의존하도록 한다.

```text
SaveUseCase
    ↓
IDataSerializer
    ↑
MessagePackSerializer
```

## 28. 라이브러리와 비본질적 어려움

라이브러리는 반복되는 기술적 문제를 대신 해결하여 비본질적 어려움을 줄인다.

예를 들어 게임 개발자가 직접 다음 기능을 구현할 필요를 줄여준다.

```text
JSON 문법 분석
압축 알고리즘
암호화 알고리즘
비동기 작업 관리
네트워크 프로토콜 처리
복잡한 수학 계산
```

그러나 라이브러리를 잘못 선택하거나 과도하게 사용하면 오히려 비본질적 어려움이 증가할 수 있다.

```text
버전 충돌
패키지 의존성 문제
플랫폼 호환성 오류
라이선스 관리
숨겨진 성능 비용
복잡한 API
업데이트에 따른 코드 수정
```

따라서 라이브러리는 코드 양을 줄이기 위해 무조건 추가하는 것이 아니라, 프로젝트 전체의 복잡성을 실제로 줄이는지 판단하고 선택해야 한다.

## 29. 라이브러리 품질을 평가하는 질문

라이브러리를 도입하거나 직접 제작할 때 다음 질문을 사용할 수 있다.

* 해결하려는 문제가 명확한가?
* 프로젝트에서 실제로 필요한 기능인가?
* API가 단순하고 일관적인가?
* 내부 구현이 외부에 불필요하게 노출되지 않는가?
* Unity 버전과 호환되는가?
* IL2CPP와 AOT 환경을 지원하는가?
* 대상 플랫폼에서 동작하는가?
* 성능과 메모리 사용량이 적절한가?
* 문서와 사용 예제가 충분한가?
* 자동화 테스트가 존재하는가?
* 외부 의존성이 과도하지 않은가?
* 유지보수가 계속되고 있는가?
* 라이선스가 프로젝트 정책에 적합한가?
* 보안 문제가 보고된 적은 없는가?
* 프로젝트에서 제거하거나 다른 구현으로 교체하기 쉬운가?
* 라이브러리 도입으로 전체 복잡성이 실제로 감소하는가?

## 정리

소프트웨어 라이브러리는 특정 기능을 재사용할 수 있도록 만들어 놓은 함수, 클래스, 인터페이스 및 데이터의 집합이다.

라이브러리의 기본적인 사용 구조는 다음과 같다.

```text
개발자 코드
    ↓
라이브러리 API 호출
    ↓
라이브러리 내부 구현 실행
    ↓
결과 반환
```

프레임워크와의 가장 큰 차이는 실행 흐름의 제어권이다.

```text
라이브러리
개발자 코드 → 라이브러리

프레임워크
프레임워크 → 개발자 코드
```

라이브러리를 사용하면 다음과 같은 장점을 얻을 수 있다.

* 반복적인 기능을 다시 구현하지 않아도 된다.
* 개발 속도를 높일 수 있다.
* 검증된 기능을 재사용할 수 있다.
* 코드 중복을 줄일 수 있다.
* 전문적인 기술을 비교적 쉽게 적용할 수 있다.
* 여러 프로젝트에서 일관된 기능을 사용할 수 있다.

반면 다음 사항에 주의해야 한다.

* 버전 충돌
* 외부 의존성
* 플랫폼 호환성
* IL2CPP와 AOT 지원
* 성능과 메모리 비용
* 보안 취약점
* 라이선스
* 유지보수 중단
* 특정 라이브러리에 대한 과도한 종속

Unity 프로젝트에서는 외부 라이브러리의 API를 핵심 게임 로직 전체에 직접 노출하기보다, 필요한 경우 인터페이스나 어댑터를 통해 격리하는 것이 좋다.

```text
게임 로직
    ↓
프로젝트 인터페이스
    ↑
외부 라이브러리 구현체
```

라이브러리의 목적은 단순히 코드의 길이를 줄이는 것이 아니다.

> 라이브러리의 목적은 이미 해결된 기술적 문제를 재사용 가능한 형태로 제공하여, 개발자가 게임의 본질적인 규칙과 기능 구현에 집중할 수 있도록 하는 것이다.
