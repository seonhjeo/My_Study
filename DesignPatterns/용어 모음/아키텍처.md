# 소프트웨어 아키텍처

소프트웨어 아키텍처(Software Architecture)는 소프트웨어 시스템을 구성하는 주요 요소와 그 요소들이 서로 관계를 맺고 협력하는 방식을 정의한 전체적인 구조이다.

단순히 클래스나 함수를 어떻게 작성하는지를 넘어 다음과 같은 사항을 결정한다.

* 시스템을 어떤 모듈로 나눌 것인가?
* 각 모듈은 어떤 책임을 가질 것인가?
* 모듈 간 의존 방향은 어떻게 구성할 것인가?
* 데이터는 어떤 경로로 이동할 것인가?
* 외부 시스템과 어떻게 통신할 것인가?
* 변경 가능성이 높은 부분을 어떻게 분리할 것인가?
* 성능, 보안, 테스트, 확장성을 어떻게 확보할 것인가?

소프트웨어 아키텍처는 건축물의 설계도와 비슷하다.

건물의 설계도가 다음을 결정하듯이,

```text
기둥의 위치
층의 구성
배관과 전기 배선
출입구
방의 용도
```

소프트웨어 아키텍처는 다음을 결정한다.

```text
모듈의 경계
책임 분배
의존 관계
데이터 흐름
통신 방식
확장 지점
```

아키텍처가 잘 설계되면 기능을 추가하거나 수정할 때 변경 범위를 예측하기 쉽다.

반대로 아키텍처가 불분명하면 하나의 기능을 수정했을 뿐인데 UI, 데이터베이스, 네트워크, 게임 로직 등 여러 부분이 함께 영향을 받을 수 있다.

---

## 1. 소프트웨어 아키텍처란?

소프트웨어 아키텍처는 시스템을 구성하는 요소들과 요소 사이의 관계, 그리고 시스템 설계를 지배하는 원칙과 제약사항을 의미한다.

다음 세 가지 관점으로 이해할 수 있다.

### 구조

시스템이 어떤 요소로 나뉘어 있는가를 나타낸다.

```text
UI
게임 로직
데이터 저장
네트워크
외부 서비스
```

### 관계

각 요소가 서로 어떻게 호출하고 데이터를 주고받는지를 나타낸다.

```text
UI
 ↓
게임 로직
 ↓
데이터 저장
```

### 원칙과 제약

각 요소가 어떤 규칙을 지켜야 하는지를 나타낸다.

```text
UI는 데이터베이스에 직접 접근하지 않는다.
도메인 로직은 Unity API에 직접 의존하지 않는다.
네트워크 코드는 인터페이스 뒤에 숨긴다.
```

즉 아키텍처는 단순히 폴더를 나누는 것이 아니다.

```text
Scripts/
 ├── UI/
 ├── Managers/
 ├── Data/
 └── Player/
```

이처럼 폴더만 나누어 놓았다고 해서 좋은 아키텍처라고 할 수는 없다.

중요한 것은 각 영역의 책임과 의존 관계가 명확한가이다.

## 2. 아키텍처가 필요한 이유

작은 프로젝트에서는 모든 기능을 몇 개의 클래스에 넣어도 문제가 없어 보일 수 있다.

```csharp
public class GameManager : MonoBehaviour
{
    public void StartGame()
    {
    }

    public void SaveGame()
    {
    }

    public void LoadGame()
    {
    }

    public void ConnectServer()
    {
    }

    public void SpawnEnemy()
    {
    }

    public void UpdateUI()
    {
    }

    public void PlaySound()
    {
    }
}
```

하지만 프로젝트가 커질수록 다음과 같은 문제가 발생한다.

* 하나의 클래스가 너무 많은 책임을 가진다.
* 기능 간 의존성이 복잡하게 얽힌다.
* 어떤 코드를 수정해야 하는지 찾기 어렵다.
* 테스트하기 어렵다.
* 작은 수정이 예상하지 못한 버그를 만든다.
* 여러 개발자가 동시에 작업하기 어렵다.
* 시스템 일부를 교체하기 어렵다.

아키텍처는 이러한 문제를 해결하기 위해 시스템의 경계를 명확히 정의한다.

예를 들어 다음과 같이 분리할 수 있다.

```text
GameFlowController
 └── 게임 진행 흐름 관리

EnemySpawner
 └── 적 생성 책임

SaveService
 └── 저장 책임

AudioService
 └── 사운드 재생 책임

GameUIController
 └── UI 표시 책임

NetworkService
 └── 서버 통신 책임
```

## 3. 아키텍처와 설계의 차이

아키텍처와 설계는 비슷해 보이지만 다루는 범위가 다르다.

| 구분    | 아키텍처            | 상세 설계           |
| ----- | --------------- | --------------- |
| 범위    | 시스템 전체          | 클래스와 함수 단위      |
| 관심사   | 모듈, 계층, 의존성, 통신 | 메서드, 자료구조, 패턴   |
| 변경 비용 | 매우 큼            | 상대적으로 작음        |
| 예시    | UI와 도메인 계층 분리   | 공격 로직에 전략 패턴 사용 |
| 결정 대상 | 시스템 경계와 방향      | 구체적인 구현 방법      |

예를 들어 다음 결정은 아키텍처에 가깝다.

```text
게임 로직은 서버 통신 코드에 직접 의존하지 않는다.
저장 시스템은 인터페이스로 추상화한다.
UI와 전투 로직을 분리한다.
```

다음 결정은 상세 설계에 가깝다.

```text
무기 교체에 전략 패턴을 사용한다.
적 생성에 팩토리 패턴을 사용한다.
인벤토리에 Dictionary를 사용한다.
```

아키텍처는 큰 방향을 정하고, 디자인 패턴과 클래스 설계는 그 방향을 실제 코드로 구현한다.

## 4. 좋은 소프트웨어 아키텍처의 특징

### 낮은 결합도

모듈 간 의존성이 낮아야 한다.

```text
PlayerUI → PlayerHealth
```

처럼 구체 클래스를 직접 참조하기보다 이벤트나 인터페이스를 사용할 수 있다.

```text
PlayerHealth
   ↓
HealthChanged Event
   ↓
PlayerUI
```

### 높은 응집도

하나의 모듈은 하나의 관련된 책임에 집중해야 한다.

```text
Inventory
 ├── AddItem
 ├── RemoveItem
 ├── ContainsItem
 └── GetItemCount
```

이 기능들은 모두 인벤토리 관리라는 하나의 목적을 가진다.

### 명확한 의존 방향

어떤 계층이 어떤 계층을 참조할 수 있는지 명확해야 한다.

```text
Presentation
     ↓
Application
     ↓
Domain
```

핵심 게임 규칙인 Domain은 UI나 Unity API에 의존하지 않는 것이 좋다.

### 변경에 대한 유연성

자주 바뀌는 구현을 쉽게 교체할 수 있어야 한다.

```text
ISaveService
 ├── JsonSaveService
 ├── CloudSaveService
 └── ServerSaveService
```

### 테스트 가능성

Unity 에디터를 실행하지 않고도 핵심 로직을 테스트할 수 있어야 한다.

```csharp
public class DamageCalculator
{
    public int Calculate(int attack, int defense)
    {
        return Mathf.Max(1, attack - defense);
    }
}
```

위 코드는 `Mathf` 때문에 Unity에 의존한다.

순수 C#으로 작성하면 테스트가 더 쉬워진다.

```csharp
public class DamageCalculator
{
    public int Calculate(int attack, int defense)
    {
        return Math.Max(1, attack - defense);
    }
}
```

## 5. 아키텍처의 핵심 요소

### 컴포넌트

시스템을 구성하는 독립적인 기능 단위이다.

```text
전투 시스템
인벤토리 시스템
퀘스트 시스템
저장 시스템
네트워크 시스템
```

### 인터페이스

컴포넌트 간 통신 규칙을 정의한다.

```csharp
public interface ISaveService
{
    void Save(GameData data);
}
```

### 의존 관계

한 컴포넌트가 다른 컴포넌트를 필요로 하는 관계이다.

```text
GameController → ISaveService
```

### 데이터 흐름

데이터가 어떤 경로로 이동하는지를 나타낸다.

```text
Input
 ↓
PlayerController
 ↓
PlayerMovement
 ↓
Rigidbody
```

### 경계

서로 다른 책임이나 변경 이유를 가진 영역을 나누는 기준이다.

```text
게임 규칙 경계
UI 경계
네트워크 경계
저장 경계
외부 SDK 경계
```

## 6. 계층형 아키텍처

계층형 아키텍처(Layered Architecture)는 시스템을 역할에 따라 여러 계층으로 분리하는 방식이다.

일반적으로 다음과 같이 나눈다.

```text
Presentation Layer
Application Layer
Domain Layer
Infrastructure Layer
```

Unity 게임에 적용하면 다음과 같이 볼 수 있다.

```text
Presentation
 └── UI, 애니메이션, 입력 표시

Application
 └── 유스케이스, 게임 흐름 조정

Domain
 └── 전투 규칙, 체력, 인벤토리 규칙

Infrastructure
 └── 저장, 네트워크, 외부 SDK
```

---

### Presentation Layer

사용자와 상호작용하는 계층이다.

Unity에서는 다음 요소가 포함된다.

* UGUI
* TextMeshPro
* 입력 처리
* 애니메이션
* 화면 전환
* HUD
* 팝업
* 연출

```csharp
public class PlayerHealthView : MonoBehaviour
{
    [SerializeField]
    private UnityEngine.UI.Slider healthSlider;

    public void SetHealth(int current, int max)
    {
        healthSlider.value = (float)current / max;
    }
}
```

Presentation 계층은 체력 계산 규칙을 직접 가지지 않고 결과를 화면에 표시하는 책임만 가지는 것이 좋다.

---

### Application Layer

사용자의 요청이나 게임 진행 흐름을 조정하는 계층이다.

예를 들어 공격 유스케이스는 다음 순서를 조정할 수 있다.

```text
공격 가능 여부 확인
대상 확인
데미지 계산
피해 적용
이벤트 발생
```

```csharp
public class AttackUseCase
{
    private readonly IDamageCalculator damageCalculator;

    public AttackUseCase(IDamageCalculator damageCalculator)
    {
        this.damageCalculator = damageCalculator;
    }

    public void Execute(
        Character attacker,
        Character target)
    {
        int damage = damageCalculator.Calculate(
            attacker.AttackPower,
            target.Defense);

        target.TakeDamage(damage);
    }
}
```

Application 계층은 흐름을 조정하지만 구체적인 UI 표시나 파일 저장 방법을 알 필요는 없다.

---

### Domain Layer

게임의 핵심 규칙과 상태를 담는 계층이다.

예를 들어 캐릭터 체력 규칙은 Domain에 속한다.

```csharp
public class Health
{
    public int Current { get; private set; }
    public int Maximum { get; }

    public bool IsDead => Current <= 0;

    public Health(int maximum)
    {
        if (maximum <= 0)
            throw new ArgumentOutOfRangeException(nameof(maximum));

        Maximum = maximum;
        Current = maximum;
    }

    public void TakeDamage(int damage)
    {
        if (damage < 0)
            throw new ArgumentOutOfRangeException(nameof(damage));

        Current = Math.Max(0, Current - damage);
    }

    public void Heal(int amount)
    {
        if (amount < 0)
            throw new ArgumentOutOfRangeException(nameof(amount));

        Current = Math.Min(Maximum, Current + amount);
    }
}
```

이 코드는 `MonoBehaviour`, `Transform`, `Animator` 등에 의존하지 않는다.

따라서 Unity 외부에서도 쉽게 테스트할 수 있다.

---

### Infrastructure Layer

외부 기술과 통신하는 계층이다.

다음과 같은 구현이 포함된다.

* 파일 저장
* 서버 통신
* 데이터베이스
* Firebase
* Photon
* Addressables
* 광고 SDK
* 플랫폼 API

```csharp
public interface ISaveService
{
    void Save(GameSaveData data);
}
```

```csharp
public class JsonSaveService : ISaveService
{
    private readonly string filePath;

    public JsonSaveService(string filePath)
    {
        this.filePath = filePath;
    }

    public void Save(GameSaveData data)
    {
        string json = JsonUtility.ToJson(data);
        File.WriteAllText(filePath, json);
    }
}
```

핵심 로직은 `JsonSaveService`를 직접 알지 않고 `ISaveService`만 알도록 설계할 수 있다.

## 7. 계층 간 의존 방향

계층형 구조에서 중요한 것은 단순한 분리가 아니라 의존 방향이다.

좋은 방향은 다음과 같다.

```text
Presentation
     ↓
Application
     ↓
Domain
```

Infrastructure는 Domain이나 Application이 정의한 인터페이스를 구현한다.

```text
Application → ISaveService ← JsonSaveService
```

Domain이 Infrastructure에 직접 의존하면 안 된다.

나쁜 구조는 다음과 같다.

```csharp
public class Player
{
    private readonly JsonSaveService saveService =
        new JsonSaveService("save.json");

    public void Die()
    {
        saveService.Save(...);
    }
}
```

`Player`가 게임 규칙과 저장 기술을 동시에 알고 있다.

더 나은 구조는 다음과 같다.

```csharp
public interface IGameSaveService
{
    void Save();
}
```

```csharp
public class PlayerDeathUseCase
{
    private readonly IGameSaveService saveService;

    public PlayerDeathUseCase(
        IGameSaveService saveService)
    {
        this.saveService = saveService;
    }

    public void Execute(Player player)
    {
        player.Die();
        saveService.Save();
    }
}
```

## 8. 모놀리식 아키텍처

모놀리식 아키텍처(Monolithic Architecture)는 모든 기능이 하나의 애플리케이션이나 프로젝트 안에 통합되어 있는 구조이다.

Unity 클라이언트는 기본적으로 모놀리식 형태로 시작하는 경우가 많다.

```text
Unity Project
 ├── Player
 ├── Enemy
 ├── UI
 ├── Inventory
 ├── Network
 ├── Save
 └── Audio
```

### 장점

* 초기 개발이 빠르다.
* 배포가 단순하다.
* 디버깅이 쉽다.
* 작은 프로젝트에 적합하다.
* 모듈 간 호출 비용이 낮다.

### 단점

* 프로젝트가 커지면 의존성이 복잡해질 수 있다.
* 일부 기능만 독립적으로 배포하기 어렵다.
* 하나의 변경이 전체 빌드에 영향을 준다.
* 팀 규모가 커지면 충돌이 많아질 수 있다.

모놀리식 구조 자체가 나쁜 것은 아니다.

잘 설계된 모듈형 모놀리스는 상당히 안정적이고 유지보수하기 쉽다.

```text
Unity Client
 ├── Combat Module
 ├── Inventory Module
 ├── Quest Module
 ├── Social Module
 └── Network Module
```

각 모듈이 명확한 경계를 가지면 하나의 프로젝트 안에서도 좋은 구조를 만들 수 있다.

## 9. 모듈형 아키텍처

모듈형 아키텍처(Modular Architecture)는 시스템을 독립적인 기능 단위로 나누는 방식이다.

게임에서는 다음처럼 나눌 수 있다.

```text
Combat Module
Inventory Module
Quest Module
Character Module
Network Module
Save Module
UI Module
```

각 모듈은 자신의 내부 구현을 숨기고 외부에는 제한된 인터페이스만 제공한다.

```csharp
public interface IInventoryService
{
    bool Add(ItemData item);
    bool Remove(string itemId);
    int GetCount(string itemId);
}
```

다른 모듈은 인벤토리 내부의 `List`, `Dictionary`, 슬롯 구조를 알 필요가 없다.

### 장점

* 기능별 경계가 명확하다.
* 팀별로 나누어 개발하기 쉽다.
* 특정 기능을 교체하거나 제거하기 쉽다.
* 재사용하기 쉽다.
* 의존 관계를 관리하기 쉽다.

### Unity에서의 구현 방법

* Assembly Definition 파일 사용
* UPM 패키지 분리
* 폴더별 네임스페이스 사용
* 모듈별 인터페이스 정의
* 모듈 간 참조 방향 제한

예를 들어 다음과 같이 Assembly Definition을 나눌 수 있다.

```text
Game.Domain.asmdef
Game.Application.asmdef
Game.Presentation.asmdef
Game.Infrastructure.asmdef
```

참조 방향은 다음처럼 제한한다.

```text
Game.Presentation
 └── Game.Application 참조

Game.Application
 └── Game.Domain 참조

Game.Infrastructure
 └── Game.Application과 Game.Domain 참조

Game.Domain
 └── 다른 게임 어셈블리를 참조하지 않음
```

## 10. MVC 아키텍처

MVC는 Model, View, Controller로 시스템을 분리하는 구조이다.

```text
Model
 └── 데이터와 비즈니스 로직

View
 └── 화면 표시

Controller
 └── 입력 처리와 흐름 제어
```

Unity 게임의 체력 UI를 MVC로 구성하면 다음과 같다.

### Model

```csharp
public class HealthModel
{
    public int Current { get; private set; }
    public int Maximum { get; }

    public HealthModel(int maximum)
    {
        Maximum = maximum;
        Current = maximum;
    }

    public void TakeDamage(int damage)
    {
        Current = Math.Max(0, Current - damage);
    }
}
```

### View

```csharp
public class HealthView : MonoBehaviour
{
    [SerializeField]
    private UnityEngine.UI.Slider slider;

    public void Render(int current, int maximum)
    {
        slider.value = (float)current / maximum;
    }
}
```

### Controller

```csharp
public class HealthController : MonoBehaviour
{
    [SerializeField]
    private HealthView view;

    private HealthModel model;

    private void Awake()
    {
        model = new HealthModel(100);
        RefreshView();
    }

    public void TakeDamage(int damage)
    {
        model.TakeDamage(damage);
        RefreshView();
    }

    private void RefreshView()
    {
        view.Render(model.Current, model.Maximum);
    }
}
```

### 장점

* 데이터와 UI를 분리할 수 있다.
* UI 변경이 게임 규칙에 미치는 영향을 줄일 수 있다.
* 구조가 비교적 단순하다.

### 단점

* Controller가 커질 수 있다.
* Unity의 컴포넌트 구조와 완벽하게 일치하지 않을 수 있다.
* 복잡한 화면에서는 Controller와 View 사이 의존성이 커질 수 있다.

## 11. MVP 아키텍처

MVP는 Model, View, Presenter로 구성된다.

```text
Model
 └── 데이터와 규칙

View
 └── 화면 표시와 사용자 이벤트 전달

Presenter
 └── View와 Model을 연결
```

View를 인터페이스로 만들면 Presenter를 Unity 외부에서 테스트할 수 있다.

```csharp
public interface IHealthView
{
    void SetHealth(int current, int maximum);
    void ShowDeath();
}
```

```csharp
public class HealthPresenter
{
    private readonly HealthModel model;
    private readonly IHealthView view;

    public HealthPresenter(
        HealthModel model,
        IHealthView view)
    {
        this.model = model;
        this.view = view;
    }

    public void TakeDamage(int damage)
    {
        model.TakeDamage(damage);

        view.SetHealth(
            model.Current,
            model.Maximum);

        if (model.Current <= 0)
            view.ShowDeath();
    }
}
```

Unity View

```csharp
public class HealthView :
    MonoBehaviour,
    IHealthView
{
    [SerializeField]
    private UnityEngine.UI.Slider slider;

    [SerializeField]
    private GameObject deathPanel;

    public void SetHealth(int current, int maximum)
    {
        slider.value = (float)current / maximum;
    }

    public void ShowDeath()
    {
        deathPanel.SetActive(true);
    }
}
```

### 장점

* Presenter를 독립적으로 테스트하기 쉽다.
* View가 수동적이므로 역할이 명확하다.
* Unity UI 로직을 분리하기 좋다.

### 단점

* 화면마다 Presenter와 인터페이스가 늘어날 수 있다.
* 이벤트 연결 코드가 많아질 수 있다.
* Presenter가 많은 흐름을 맡아 비대해질 수 있다.

## 12. MVVM 아키텍처

MVVM은 Model, View, ViewModel로 구성된다.

```text
Model
 └── 데이터와 규칙

View
 └── 화면

ViewModel
 └── View에 필요한 상태와 명령 제공
```

MVVM은 데이터 바인딩과 함께 사용되는 경우가 많다.

Unity에서는 기본 UGUI만으로 완전한 자동 바인딩을 구현하기는 어렵지만 R3, UniRx, UI Toolkit 또는 커스텀 바인딩 시스템을 이용할 수 있다.

```csharp
public class HealthViewModel
{
    public int CurrentHealth { get; private set; }
    public int MaximumHealth { get; }

    public event Action<int, int> HealthChanged;

    public HealthViewModel(int maximumHealth)
    {
        MaximumHealth = maximumHealth;
        CurrentHealth = maximumHealth;
    }

    public void TakeDamage(int damage)
    {
        CurrentHealth =
            Math.Max(0, CurrentHealth - damage);

        HealthChanged?.Invoke(
            CurrentHealth,
            MaximumHealth);
    }
}
```

```csharp
public class HealthView : MonoBehaviour
{
    [SerializeField]
    private UnityEngine.UI.Slider slider;

    private HealthViewModel viewModel;

    public void Bind(HealthViewModel viewModel)
    {
        this.viewModel = viewModel;
        viewModel.HealthChanged += OnHealthChanged;

        OnHealthChanged(
            viewModel.CurrentHealth,
            viewModel.MaximumHealth);
    }

    private void OnHealthChanged(int current, int maximum)
    {
        slider.value = (float)current / maximum;
    }

    private void OnDestroy()
    {
        if (viewModel != null)
            viewModel.HealthChanged -= OnHealthChanged;
    }
}
```

## 13. 이벤트 기반 아키텍처

이벤트 기반 아키텍처(Event-Driven Architecture)는 객체들이 직접 강하게 연결되지 않고 이벤트를 통해 통신하는 구조이다.

```text
PlayerHealth
   │
   └── PlayerDied Event
          ├── UI
          ├── Sound
          ├── Quest
          └── Analytics
```

```csharp
public class PlayerHealth
{
    public event Action<int> HealthChanged;
    public event Action Died;

    private int currentHealth;

    public PlayerHealth(int maximumHealth)
    {
        currentHealth = maximumHealth;
    }

    public void TakeDamage(int damage)
    {
        currentHealth =
            Math.Max(0, currentHealth - damage);

        HealthChanged?.Invoke(currentHealth);

        if (currentHealth == 0)
            Died?.Invoke();
    }
}
```

UI 구독자

```csharp
public class PlayerHealthUI : MonoBehaviour
{
    [SerializeField]
    private UnityEngine.UI.Slider slider;

    private PlayerHealth health;

    public void Bind(PlayerHealth health)
    {
        this.health = health;
        health.HealthChanged += UpdateHealth;
    }

    private void UpdateHealth(int value)
    {
        slider.value = value;
    }

    private void OnDestroy()
    {
        if (health != null)
            health.HealthChanged -= UpdateHealth;
    }
}
```

### 장점

* 발행자와 구독자의 결합도가 낮다.
* 새로운 반응 기능을 쉽게 추가할 수 있다.
* 여러 시스템이 하나의 이벤트에 반응할 수 있다.

### 단점

* 호출 흐름을 추적하기 어려울 수 있다.
* 구독 해제를 놓치면 메모리 누수나 잘못된 호출이 생길 수 있다.
* 이벤트가 지나치게 많으면 시스템 흐름을 이해하기 어렵다.
* 실행 순서 보장이 필요할 때 문제가 될 수 있다.

## 14. 클린 아키텍처

클린 아키텍처(Clean Architecture)는 핵심 비즈니스 규칙을 외부 기술로부터 보호하는 것을 중심으로 한다.

일반적인 구조는 다음과 같다.

```text
Entities
Use Cases
Interface Adapters
Frameworks & Drivers
```

Unity에 맞춰 표현하면 다음과 같다.

```text
Domain
 └── 캐릭터, 체력, 인벤토리, 전투 규칙

Application
 └── 공격, 아이템 획득, 저장 등의 유스케이스

Adapters
 └── Presenter, Controller, Repository 구현

Infrastructure
 └── Unity, 파일, 서버, Photon, Firebase
```

가장 중요한 원칙은 의존성이 안쪽을 향해야 한다는 것이다.

```text
Unity View
    ↓
Use Case
    ↓
Domain
```

Domain은 Unity View를 알지 못한다.

---

### Domain Entity

```csharp
public class Player
```

```csharp
public class DamagePlayerUseCase

}
```

### Presenter

```csharp
public interface IPlayerHealthOutput

```

```csharp
public class PlayerHealthPresenter :
    IPlayerHealthOutput

```

### Unity View


## 15. 헥사고날 아키텍처

헥사고날 아키텍처(Hexagonal Architecture)는 포트와 어댑터 아키텍처라고도 부른다.

핵심 로직과 외부 시스템 사이에 포트라고 불리는 인터페이스를 두고, 구체 기술은 어댑터가 담당한다.

```text
              Unity UI Adapter
                    │
                    ▼
Network Adapter → Application Core ← Save Adapter
                    ▲
                    │
              Input Adapter
```

### 포트

핵심 로직이 외부에 요구하는 인터페이스이다.

```csharp
public interface IPlayerRepository
{
    PlayerData Load();
    void Save(PlayerData data);
}
```

### 어댑터

포트를 실제 기술로 구현한다.

```csharp
public class JsonPlayerRepository :
    IPlayerRepository
{
    private readonly string filePath;

    public JsonPlayerRepository(string filePath)
    {
        this.filePath = filePath;
    }

    public PlayerData Load()
    {
        string json = File.ReadAllText(filePath);
        return JsonUtility.FromJson<PlayerData>(json);
    }

    public void Save(PlayerData data)
    {
        string json = JsonUtility.ToJson(data);
        File.WriteAllText(filePath, json);
    }
}
```

서버 저장 방식도 같은 포트를 구현할 수 있다.

```csharp
public class ServerPlayerRepository :
    IPlayerRepository
{
    public PlayerData Load()
    {
        // 서버에서 플레이어 데이터 로드
        return new PlayerData();
    }

    public void Save(PlayerData data)
    {
        // 서버로 플레이어 데이터 전송
    }
}
```

Application Core는 어떤 구현이 사용되는지 알 필요가 없다.

## 16. 서비스 지향 아키텍처와 마이크로서비스

서비스 지향 아키텍처는 시스템을 독립적인 서비스 단위로 분리하는 방식이다.

온라인 게임 서버에서는 다음과 같이 분리할 수 있다.

```text
인증 서비스
유저 서비스
채팅 서비스
매치메이킹 서비스
랭킹 서비스
결제 서비스
인벤토리 서비스
```

마이크로서비스 아키텍처는 각 서비스를 더 독립적으로 배포하고 운영할 수 있도록 구성한다.

```text
Unity Client
     │
API Gateway
 ├── Auth Service
 ├── Match Service
 ├── Chat Service
 └── Inventory Service
```

### 장점

* 서비스별 독립 배포가 가능하다.
* 기능별 확장이 가능하다.
* 팀별로 독립적으로 개발하기 쉽다.
* 특정 서비스 장애를 격리할 수 있다.

### 단점

* 네트워크 통신 비용이 증가한다.
* 분산 트랜잭션이 어렵다.
* 로그 추적과 디버깅이 복잡하다.
* 배포와 운영 환경이 복잡하다.
* 작은 프로젝트에는 과도할 수 있다.

Unity 클라이언트 내부 구조에 마이크로서비스를 그대로 적용하는 것은 일반적이지 않다.

마이크로서비스는 주로 서버 아키텍처에 사용한다.

## 17. ECS와 데이터 지향 아키텍처

ECS(Entity Component System)는 객체의 상속 구조보다 데이터와 처리 시스템을 분리하는 아키텍처이다.

```text
Entity
 └── 식별자

Component
 └── 데이터

System
 └── 데이터를 처리하는 로직
```

예를 들어 적의 위치와 이동 속도를 컴포넌트로 분리할 수 있다.

```csharp
public struct Position
{
    public Vector3 Value;
}
```

```csharp
public struct MoveSpeed
{
    public float Value;
}
```

```csharp
public class MovementSystem
{
    public void Update(
        ref Position position,
        in MoveSpeed speed,
        Vector3 direction,
        float deltaTime)
    {
        position.Value +=
            direction * speed.Value * deltaTime;
    }
}
```

Unity DOTS에서는 `IComponentData`와 `ISystem` 등을 사용한다.

ECS는 대량의 유사 객체를 처리할 때 유리하다.

```text
수천 마리의 유닛
대규모 투사체
군중 시뮬레이션
파티클과 유사한 오브젝트
```

다만 일반적인 게임 UI나 복잡한 객체 상호작용에는 전통적인 GameObject 구조가 더 단순할 수 있다.

## 18. 데이터 중심 아키텍처

데이터 중심 아키텍처는 동작을 코드에 고정하기보다 데이터로 분리하는 방식이다.

Unity에서는 `ScriptableObject`가 자주 사용된다.

```csharp
[CreateAssetMenu(
    menuName = "Game/Weapon Data")]
public class WeaponData : ScriptableObject
{
    public string weaponId;
    public int damage;
    public float attackSpeed;
    public GameObject projectilePrefab;
}
```

무기 동작 객체

```csharp
public class Weapon : MonoBehaviour
{
    [SerializeField]
    private WeaponData data;

    public void Attack(IDamageable target)
    {
        target.TakeDamage(data.damage);
    }
}
```

### 장점

* 코드 수정 없이 밸런스를 조정할 수 있다.
* 기획자가 에디터에서 직접 수정할 수 있다.
* 같은 로직에 다양한 데이터를 조합할 수 있다.
* 프리팹 중복을 줄일 수 있다.

### 주의점

`ScriptableObject`에 모든 런타임 상태를 저장하면 여러 객체가 상태를 공유하는 문제가 생길 수 있다.

```csharp
[CreateAssetMenu]
public class HealthData : ScriptableObject
{
    public int currentHealth;
}
```

여러 적이 같은 `HealthData`를 참조하면 체력이 공유될 수 있다.

따라서 설정 데이터와 런타임 상태를 분리하는 것이 좋다.

```csharp
[CreateAssetMenu]
public class HealthConfig : ScriptableObject
{
    public int maximumHealth;
}
```

```csharp
public class Health
{
    public int Current { get; private set; }

    public Health(HealthConfig config)
    {
        Current = config.maximumHealth;
    }
}
```

## 20. Unity 전투 시스템 아키텍처 예시

전투 시스템을 다음과 같은 구조로 분리한다고 가정해 보자.

```text
Presentation
 ├── BattleView
 ├── HealthBarView
 └── DamageTextView

Application
 └── AttackUseCase

Domain
 ├── Character
 ├── Health
 ├── IDamagePolicy
 └── BasicDamagePolicy

Infrastructure
 └── UnityBattleEffectService
```

### Domain

```csharp
public interface IDamagePolicy
{
    int Calculate(int attack, int defense);
}
```

```csharp
public class BasicDamagePolicy : IDamagePolicy
{
    public int Calculate(int attack, int defense)
    {
        return Math.Max(1, attack - defense);
    }
}
```

```csharp
public class Character
{
    public int AttackPower { get; }
    public int Defense { get; }
    public Health Health { get; }

    public Character(
        int attackPower,
        int defense,
        int maximumHealth)
    {
        AttackPower = attackPower;
        Defense = defense;
        Health = new Health(maximumHealth);
    }
}
```

### Application

```csharp
public interface IBattleEffectService
{
    void PlayHitEffect();
    void ShowDamage(int damage);
}
```

```csharp
public class AttackUseCase
{
    private readonly IDamagePolicy damagePolicy;
    private readonly IBattleEffectService effectService;

    public AttackUseCase(
        IDamagePolicy damagePolicy,
        IBattleEffectService effectService)
    {
        this.damagePolicy = damagePolicy;
        this.effectService = effectService;
    }

    public void Execute(
        Character attacker,
        Character target)
    {
        int damage = damagePolicy.Calculate(
            attacker.AttackPower,
            target.Defense);

        target.Health.TakeDamage(damage);

        effectService.PlayHitEffect();
        effectService.ShowDamage(damage);
    }
}
```

### Infrastructure

```csharp
public class UnityBattleEffectService :
    MonoBehaviour,
    IBattleEffectService
{
    [SerializeField]
    private ParticleSystem hitEffect;

    [SerializeField]
    private DamageTextView damageTextView;

    public void PlayHitEffect()
    {
        hitEffect.Play();
    }

    public void ShowDamage(int damage)
    {
        damageTextView.Show(damage);
    }
}
```

### Composition Root

객체를 생성하고 연결하는 위치를 Composition Root라고 한다.

Unity에서는 Installer 또는 Bootstrapper가 이 역할을 할 수 있다.

```csharp
public class BattleInstaller : MonoBehaviour
{
    [SerializeField]
    private UnityBattleEffectService effectService;

    private AttackUseCase attackUseCase;
    private Character player;
    private Character enemy;

    private void Awake()
    {
        IDamagePolicy damagePolicy =
            new BasicDamagePolicy();

        attackUseCase = new AttackUseCase(
            damagePolicy,
            effectService);

        player = new Character(
            attackPower: 20,
            defense: 5,
            maximumHealth: 100);

        enemy = new Character(
            attackPower: 15,
            defense: 3,
            maximumHealth: 50);
    }

    public void AttackEnemy()
    {
        attackUseCase.Execute(player, enemy);
    }
}
```

객체 생성과 연결을 한 곳에 모으면 각 클래스 내부에서 `new`를 남발하는 것을 줄일 수 있다.

## 21. Composition Root

Composition Root는 애플리케이션의 객체들을 생성하고 의존성을 연결하는 장소이다.

```text
IWeapon → Sword
ISaveService → JsonSaveService
IDamagePolicy → BasicDamagePolicy
```

Unity에서는 다음 위치가 Composition Root 역할을 할 수 있다.

* Bootstrap Scene
* Installer MonoBehaviour
* GameEntryPoint
* VContainer LifetimeScope
* Zenject Installer

```csharp
public class GameBootstrapper : MonoBehaviour
{
    [SerializeField]
    private PlayerView playerView;

    private void Awake()
    {
        IInputService inputService =
            new UnityInputService();

        IMovementPolicy movementPolicy =
            new NormalMovementPolicy(5f);

        var movementController =
            new PlayerMovementController(
                inputService,
                movementPolicy,
                playerView);

        movementController.Initialize();
    }
}
```

Composition Root를 제외한 일반 객체는 가능하면 다른 구체 객체를 직접 생성하지 않는 것이 좋다.

## 22. 아키텍처와 의존성 주입

의존성 주입은 아키텍처의 의존 방향을 실제 코드로 구현하는 방법이다.

```csharp
public class PlayerService
{
    private readonly ISaveService saveService;

    public PlayerService(ISaveService saveService)
    {
        this.saveService = saveService;
    }
}
```

여기서 `PlayerService`는 저장 구현을 직접 생성하지 않는다.

외부에서 주입받는다.

```csharp
ISaveService saveService =
    new JsonSaveService("save.json");

var playerService =
    new PlayerService(saveService);
```

DI 컨테이너를 사용할 수도 있지만 반드시 필요한 것은 아니다.

작은 프로젝트에서는 수동 주입이 더 명확할 수 있다.

## 23. 아키텍처와 이벤트

이벤트는 계층이나 모듈 사이의 직접 참조를 줄이는 데 사용할 수 있다.

예를 들어 플레이어 사망 시 다음 시스템이 반응한다고 가정한다.

```text
UI
사운드
퀘스트
업적
통계
```

Player가 모든 시스템을 직접 호출하면 결합도가 높아진다.

```csharp
public void Die()
{
    ui.ShowDeath();
    sound.PlayDeath();
    quest.FailQuest();
    achievement.Check();
    analytics.SendDeathEvent();
}
```

이벤트를 사용하면 Player는 사망 사실만 알린다.

```csharp
public class PlayerHealth
{
    public event Action Died;

    public void Die()
    {
        Died?.Invoke();
    }
}
```

각 시스템은 독립적으로 구독한다.

```csharp
playerHealth.Died += deathUI.Show;
playerHealth.Died += deathSound.Play;
playerHealth.Died += questService.OnPlayerDied;
```

다만 이벤트를 과도하게 사용하면 흐름이 숨겨질 수 있으므로 핵심 유스케이스는 직접적인 호출 구조를 유지하는 편이 좋을 수 있다.

## 24. 동기 호출과 비동기 호출

아키텍처에서는 호출 방식도 중요하다.

### 동기 호출

호출 결과를 즉시 기다린다.

```csharp
int damage = calculator.Calculate(attack, defense);
target.TakeDamage(damage);
```

### 비동기 호출

작업 완료를 기다리는 동안 다른 작업을 수행할 수 있다.

Unity에서는 `async`, `Task`, `UniTask`, Coroutine 등을 사용할 수 있다.

```csharp
public interface IPlayerRepository
{
    Task<PlayerData> LoadAsync(
        CancellationToken cancellationToken);
}
```

```csharp
public class LoadPlayerUseCase
{
    private readonly IPlayerRepository repository;

    public LoadPlayerUseCase(
        IPlayerRepository repository)
    {
        this.repository = repository;
    }

    public async Task<PlayerData> ExecuteAsync(
        CancellationToken cancellationToken)
    {
        return await repository.LoadAsync(
            cancellationToken);
    }
}
```

네트워크, 파일, Addressables 로딩은 비동기 처리가 적절하다.

## 27. 아키텍처와 싱글턴

싱글턴은 전역 접근 지점을 제공하므로 편리하지만 의존성을 숨길 수 있다.

```csharp
AudioManager.Instance.Play("Hit");
```

겉으로는 `AudioManager`가 메서드 인자나 필드에 없지만 실제로는 강하게 의존하고 있다.

테스트에서도 교체하기 어렵다.

인터페이스를 주입하는 방식이 의존성을 더 명확하게 드러낸다.

```csharp
public class AttackUseCase
{
    private readonly IAudioService audioService;

    public AttackUseCase(
        IAudioService audioService)
    {
        this.audioService = audioService;
    }
}
```

싱글턴을 무조건 금지할 필요는 없지만 다음과 같은 경우에 제한적으로 사용하는 것이 좋다.

* 애플리케이션 전체에 하나만 존재해야 한다.
* 상태와 생명주기가 명확하다.
* 테스트에서 교체 가능하다.
* 전역 호출이 남발되지 않는다.

## 28. 아키텍처와 테스트

좋은 아키텍처는 핵심 로직을 Unity 환경과 분리한다.

예를 들어 순수 C# 데미지 계산기는 쉽게 테스트할 수 있다.

```csharp
[Test]
public void Damage_IsAtLeastOne()
{
    var policy = new BasicDamagePolicy();

    int damage = policy.Calculate(
        attack: 5,
        defense: 100);

    Assert.AreEqual(1, damage);
}
```

반면 다음 코드는 테스트하기 어렵다.

```csharp
public class PlayerAttack : MonoBehaviour
{
    public Animator animator;
    public AudioSource audioSource;
    public Enemy enemy;

    public void Attack()
    {
        animator.SetTrigger("Attack");
        audioSource.Play();
        enemy.Health -= 10;
    }
}
```

게임 규칙, Unity 연출, 대상 참조가 하나의 클래스에 섞여 있다.

이를 분리하면 다음처럼 테스트할 수 있다.

```text
AttackUseCase
 └── 게임 규칙 테스트

AttackAnimationView
 └── Play Mode 테스트

AudioService
 └── Unity 연동 테스트
```

## 29. 아키텍처를 선택할 때 고려할 요소

아키텍처는 유행이나 이름만 보고 선택하면 안 된다.

다음 요소를 고려해야 한다.

### 프로젝트 규모

작은 프로토타입에 복잡한 클린 아키텍처를 적용하면 개발 속도가 느려질 수 있다.

### 팀 규모

한 명이 개발하는 프로젝트와 수십 명이 개발하는 프로젝트는 필요한 경계 수준이 다르다.

### 변경 가능성

자주 바뀌는 부분을 중심으로 추상화해야 한다.

```text
전투 밸런스
입력 방식
저장 방식
서버 API
플랫폼 SDK
```

### 성능 요구사항

대량 객체를 처리한다면 ECS나 데이터 지향 설계를 고려할 수 있다.

### 테스트 요구사항

자동화 테스트가 중요하다면 순수 C# 도메인 계층을 분리하는 것이 유리하다.

### 배포 방식

서버가 여러 서비스로 독립 배포되어야 한다면 마이크로서비스가 필요할 수 있다.

### 개발 일정

완벽한 구조를 만드는 것보다 현재 요구사항에 맞는 최소한의 구조를 만드는 것이 중요하다.

## 30. 아키텍처의 과도한 설계

아키텍처는 복잡할수록 좋은 것이 아니다.

간단한 체력 감소 기능을 위해 다음과 같은 구조를 만들 수도 있다.

```text
DamageRequest
DamageCommand
DamageCommandHandler
DamagePolicy
DamagePolicyFactory
HealthRepository
HealthGateway
HealthPresenter
HealthOutputPort
```

대규모 프로젝트에서는 의미가 있을 수 있지만 작은 게임에서는 과도할 수 있다.

과도한 설계의 문제는 다음과 같다.

* 파일 수가 너무 많아진다.
* 기능 흐름을 이해하기 어렵다.
* 새 개발자의 학습 비용이 커진다.
* 작은 수정에도 여러 계층을 거쳐야 한다.
* 실제 요구사항보다 추상화가 앞서간다.

아키텍처는 복잡성을 제거하기 위해 존재하며, 복잡성을 추가하는 것이 목적이 아니다.

## 33. 아키텍처를 평가하는 질문

아키텍처가 적절한지 판단할 때 다음 질문을 사용할 수 있다.

* UI를 변경해도 게임 규칙 코드는 그대로 유지되는가?
* 저장 방식을 변경해도 도메인 로직을 수정하지 않아도 되는가?
* 네트워크 없이도 핵심 게임 로직을 테스트할 수 있는가?
* 한 클래스가 여러 이유로 변경되고 있지는 않은가?
* 특정 기능의 코드를 찾기 쉬운가?
* 모듈 간 의존 방향이 명확한가?
* 새로운 기능을 기존 코드 수정 없이 추가할 수 있는가?
* 이벤트 흐름을 추적할 수 있는가?
* 전역 상태가 지나치게 많지는 않은가?
* 외부 SDK가 핵심 게임 로직에 직접 노출되어 있지는 않은가?
* 객체 생성 위치가 분산되어 있지는 않은가?
* 현재 프로젝트 규모에 비해 구조가 지나치게 복잡하지는 않은가?

## 34. 아키텍처와 SOLID 원칙의 관계

### SRP

각 계층과 모듈이 하나의 명확한 책임을 가지도록 한다.

```text
UI
 └── 표시 책임

Domain
 └── 게임 규칙 책임

Infrastructure
 └── 외부 기술 연동 책임
```

### OCP

새로운 구현을 추가하면서 기존 코드를 수정하지 않도록 한다.

```text
ISaveService
 ├── JsonSaveService
 ├── CloudSaveService
 └── ServerSaveService
```

### LSP

인터페이스와 부모 타입의 구현체를 안전하게 교체할 수 있어야 한다.

### ISP

모듈이 필요하지 않은 기능에 의존하지 않도록 인터페이스를 작게 분리한다.

### DIP

핵심 정책이 구체 기술이 아니라 추상화에 의존하도록 한다.

```text
SaveGameUseCase → ISaveService ← JsonSaveService
```

## 정리

소프트웨어 아키텍처는 시스템을 구성하는 주요 요소와 요소 사이의 관계, 의존 방향, 데이터 흐름, 설계 원칙을 정의하는 전체적인 구조이다.

좋은 아키텍처는 다음 목표를 가진다.

```text
변경 범위를 줄인다.
기능별 책임을 명확히 한다.
외부 기술과 핵심 로직을 분리한다.
테스트하기 쉽게 만든다.
기능 확장 비용을 낮춘다.
팀이 시스템을 이해하기 쉽게 만든다.
```

Unity 게임에서는 다음과 같은 방향이 실용적이다.

```text
MonoBehaviour는 Unity 연동과 화면 표시를 담당한다.
핵심 게임 규칙은 순수 C# 객체로 분리한다.
게임 흐름은 Use Case 또는 Controller가 조정한다.
저장, 네트워크, 외부 SDK는 Infrastructure로 분리한다.
변경 가능성이 높은 구현은 인터페이스 뒤에 숨긴다.
객체 생성과 연결은 Composition Root에 모은다.
```

대표적인 구조는 다음과 같다.

```text
Presentation
     ↓
Application
     ↓
Domain

Infrastructure
     └── Application 또는 Domain의 인터페이스 구현
```

아키텍처의 목적은 복잡한 패턴이나 계층을 많이 사용하는 것이 아니다.

가장 중요한 목적은 다음과 같다.

> 변경이 발생했을 때 수정해야 하는 범위를 예측 가능하게 만들고, 핵심 게임 규칙을 외부 기술의 변화로부터 보호하는 것이다.

따라서 프로젝트의 규모, 팀 구성, 변경 가능성, 테스트 요구사항을 고려하여 필요한 만큼만 아키텍처를 적용하는 것이 가장 좋은 접근이다.
