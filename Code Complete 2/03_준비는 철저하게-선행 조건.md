# 3.1 선행 조건의 중요성

품질이 좋은 소프트웨어를 개발하는 개발자들은 공통적으로 자신만의 고급 실천법이 있다.  
그러한 실천법은 프로젝트의 시작과 중간, 끝 단계에서 품질을 중요시한다.
- 시작 단계에서 품질을 강조하는 경우 고급 제품을 계획하고 요구사항을 수집하고 설계한다.
- 중간 단계에서 품질을 강조하는 경우 구현 방법에 역점(심혈을 기울이거나 중점으로 둠)을 둔다.
- 마무리 단계에서 품질을 강조하는 경우 시스템 테스트에 중점을 둔다.  
하지만 테스트는 엉뚱한 제품을 개발하거나 다른 잘못된 방법으로 개발되는 것과 같은 문제점을 발견할 수 없다. 이러한 문제점은 구현을 시작하기 전에 수행해야 한다.

구현 작업은 소프트웨어 프로젝트의 중간 단계여서 구현 작업을 할 때는 이미 소프트웨어의 성패에 영향을 미치는 기초 작업이 어느 정도 진행된 상태다.  
하지만 구현하는 동안 적어도 현재 상황이 어떤지 판단할 수 있어야 하며, 실패의 조짐이 보일 시 작업을 되돌려야 한다.

## 선행 조건이 최신 소프트웨어 프로젝트에도 적용되는가?

**준비 작업의 가장 중요한 목표는 위험 축소다.** 훌륭한 프로젝트 기획자는 프로젝트가 매끄럽게 진행될 수 있도록 가능한 한 초기에 주요 위험 요소를 제거한다.  
소프트웨어 개발에서 가장 흔히 발생하는 위험 요소는 불충분한 요구사항과 잘못된 프로젝트 계획이다.  
따라서 선행 조건도 요구사항과 프로젝트 계획을 향상시키는 데 중점을 두는 경향이 있다.

## 불완전한 준비의 원인

개발자의 불완전한 선행 준비 작업의 원인들은 다음과 같다.
- 일반적인 원인은 선행 작업에 투입되는 개발자가 자신의 작업을 수행할 수 있을 정도로 전문가적인 지식을 갖고 있지 않다는 점이다.
- 선행 작업을 수행하는 방법을 알고 있지만, 코드를 작성하는 데 급급해 준비 작업을 하지 않는 개발자도 있다.
- 관리자들이 구현에 필요한 선행 조건을 수행하기 위해 시간을 투자하는 개발자들을 못마땅하게 본다.

## 구현 전에 선행 조건을 수행하기 위한 필수적 논의

기술자로서 해야 하는 일 중 주위의 비기술자에게 개발 프로세스에 대해 교육하는 것도 포함되어 있다.  
비기술자를 상대하는 데 사용되는 기법들은 다음과 같다.
- 논리적 설득
- 비유적 설득
- 데이터에 근거한 설득

프로젝트는 저마다 고유하지만 모든 프로젝트는 일반적인 개발 형태로 나뉘는 경향이 있다.

## 선행 조건에서 반복적인 접근 방법(에자일 방법)이 갖는 효과

일괄 재작업 시 대부분의 결함을 나중에 수정하기 때문에 비용이 많이 든다. 반복적인 접근 시에는 프로젝트가 진행되는 과정에서 조금씩 재작업하기 때문에 전체적으로 드는 비용이 더 적다.

선행 조건을 줄이거나 없앤 반복적인 프로젝트는 동일한 조건의 순차적 프로젝트와 두 가지 측면에서 다르다.
- 결함 발생 후 상대적으로 빨리 발견될 것이므로 평균 결함 수정 비용이 더 적게 든다.  
하지만 각 단계마다 코드 재작성 및 재테스트를 수행하므로 필요 이상으로 결함 수정 비용이 커질 수 있다.
- 반복적인 접근 방법에서의 비용은 마지막에 한꺼번에 들지 않고 전체 브로젝트 과정에서 조금씩 흡수된다.

반복적인 접근 방법은 대개는 여러 가지 면에서 더 좋은 방법이지만, 선행 조건을 무시한 반복적인 접근 방법은 선행 조건을 다른 순차적인 접근 방법보다 훨씬 많은 비용이 들 수 있다.

## 반복적 방법(애자일)과 순차적 방법(워터폴)의 선택

어떤 선행 조건들을 충족할지에 대한 범위는 프로젝트의 종류와 형식, 기술적 환경, 구성원의 능력, 사업적 목표 등에 따라 달라진다.

다음의 경우에는 순차적 접근 방법을 선호할 것이다.
- 요구사항이 상당히 안정적일 때
- 설계가 직관적이며 이해하기 쉬울 때
- 개발 팀이 해당 응용분야에 익숙할 때
- 프로젝트의 위험 부담이 적을 때
- 장기적인 계획이 중요할 때
- 요구사항, 설계, 코드 변경 비용이 높을 것 같을 때

다음의 경우에는 반복적인 접근 방법을 선호할 것이다.
- 요구사항을 제대로 이해할 수 없거나 다른 여러가지 이유 때문에 변경될 가능성이 많을 때
- 설계가 복잡하거나 어려울 때
- 개발 팀이 해당 응용 분야에 대해 잘 모를 때
- 프로젝트의 위험 부담이 높을 때
- 장기적인 계획이 중요하지 않을 때
- 요구사항, 설계, 코드 변경 비용이 높지 않을 것 같을 때

구현 시 가장 먼저 해야 할 일은 프로젝트에 가장 적합한 선행 조건이 무엇인가를 결정하는 것이다.
