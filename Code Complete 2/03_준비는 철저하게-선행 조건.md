# 3.1 선행 조건의 중요성

품질이 좋은 소프트웨어를 개발하는 개발자들은 공통적으로 자신만의 고급 실천법이 있다.  
그러한 실천법은 프로젝트의 시작과 중간, 끝 단계에서 품질을 중요시한다.
- 시작 단계에서 품질을 강조하는 경우 고급 제품을 계획하고 요구사항을 수집하고 설계한다.
- 중간 단계에서 품질을 강조하는 경우 구현 방법에 역점(심혈을 기울이거나 중점으로 둠)을 둔다.
- 마무리 단계에서 품질을 강조하는 경우 시스템 테스트에 중점을 둔다.  
하지만 테스트는 엉뚱한 제품을 개발하거나 다른 잘못된 방법으로 개발되는 것과 같은 문제점을 발견할 수 없다. 이러한 문제점은 구현을 시작하기 전에 수행해야 한다.

구현 작업은 소프트웨어 프로젝트의 중간 단계여서 구현 작업을 할 때는 이미 소프트웨어의 성패에 영향을 미치는 기초 작업이 어느 정도 진행된 상태다.  
하지만 구현하는 동안 적어도 현재 상황이 어떤지 판단할 수 있어야 하며, 실패의 조짐이 보일 시 작업을 되돌려야 한다.

## 선행 조건이 최신 소프트웨어 프로젝트에도 적용되는가?

**준비 작업의 가장 중요한 목표는 위험 축소다.** 훌륭한 프로젝트 기획자는 프로젝트가 매끄럽게 진행될 수 있도록 가능한 한 초기에 주요 위험 요소를 제거한다.  
소프트웨어 개발에서 가장 흔히 발생하는 위험 요소는 불충분한 요구사항과 잘못된 프로젝트 계획이다.  
따라서 선행 조건도 요구사항과 프로젝트 계획을 향상시키는 데 중점을 두는 경향이 있다.

## 불완전한 준비의 원인

개발자의 불완전한 선행 준비 작업의 원인들은 다음과 같다.
- 일반적인 원인은 선행 작업에 투입되는 개발자가 자신의 작업을 수행할 수 있을 정도로 전문가적인 지식을 갖고 있지 않다는 점이다.
- 선행 작업을 수행하는 방법을 알고 있지만, 코드를 작성하는 데 급급해 준비 작업을 하지 않는 개발자도 있다.
- 관리자들이 구현에 필요한 선행 조건을 수행하기 위해 시간을 투자하는 개발자들을 못마땅하게 본다.

## 구현 전에 선행 조건을 수행하기 위한 필수적 논의

기술자로서 해야 하는 일 중 주위의 비기술자에게 개발 프로세스에 대해 교육하는 것도 포함되어 있다.  
비기술자를 상대하는 데 사용되는 기법들은 다음과 같다.
- 논리적 설득
- 비유적 설득
- 데이터에 근거한 설득

## 선행 조건에서 반복적인 접근 방법(에자일 방법)이 갖는 효과

일괄 재작업 시 대부분의 결함을 나중에 수정하기 때문에 비용이 많이 든다. 반복적인 접근 시에는 프로젝트가 진행되는 과정에서 조금씩 재작업하기 때문에 전체적으로 드는 비용이 더 적다.

선행 조건을 줄이거나 없앤 반복적인 프로젝트는 동일한 조건의 순차적 프로젝트와 두 가지 측면에서 다르다.
- 결함 발생 후 상대적으로 빨리 발견될 것이므로 평균 결함 수정 비용이 더 적게 든다.  
하지만 각 단계마다 코드 재작성 및 재테스트를 수행하므로 필요 이상으로 결함 수정 비용이 커질 수 있다.
- 반복적인 접근 방법에서의 비용은 마지막에 한꺼번에 들지 않고 전체 브로젝트 과정에서 조금씩 흡수된다.

반복적인 접근 방법은 대개는 여러 가지 면에서 더 좋은 방법이지만, 선행 조건을 무시한 반복적인 접근 방법은 선행 조건을 다른 순차적인 접근 방법보다 훨씬 많은 비용이 들 수 있다.

## 반복적 방법(애자일)과 순차적 방법(워터폴)의 선택

어떤 선행 조건들을 충족할지에 대한 범위는 프로젝트의 종류와 형식, 기술적 환경, 구성원의 능력, 사업적 목표 등에 따라 달라진다.

다음의 경우에는 순차적 접근 방법을 선호할 것이다.
- 요구사항이 상당히 안정적일 때
- 설계가 직관적이며 이해하기 쉬울 때
- 개발 팀이 해당 응용분야에 익숙할 때
- 프로젝트의 위험 부담이 적을 때
- 장기적인 계획이 중요할 때
- 요구사항, 설계, 코드 변경 비용이 높을 것 같을 때

다음의 경우에는 반복적인 접근 방법을 선호할 것이다.
- 요구사항을 제대로 이해할 수 없거나 다른 여러가지 이유 때문에 변경될 가능성이 많을 때
- 설계가 복잡하거나 어려울 때
- 개발 팀이 해당 응용 분야에 대해 잘 모를 때
- 프로젝트의 위험 부담이 높을 때
- 장기적인 계획이 중요하지 않을 때
- 요구사항, 설계, 코드 변경 비용이 높지 않을 것 같을 때

구현 시 가장 먼저 해야 할 일은 프로젝트에 가장 적합한 선행 조건이 무엇인가를 결정하는 것이다.

# 3.3 문제-정의 선행 조건

구현에 들어가기에 앞어 완료해야 하는 첫 번째 선행 조건은 시스템이 해결해야 하는 문제를 명확하게 기술하는 것이다.

문제 정의는 해결책에 대해서는 언급하지 않고 문제가 무엇인지를 정의한다. 간단한 문서지만 반드시 문제점에 대해 언급해야 한다.

문제 정의는 반드시 사용자의 언어로 작성해야 하면 문제는 사용자 관점에서 기술해야 한다.  
이 규칙에 있어서 예외적인 사항은 문제가 컴퓨터에 있는 경우다.

문제를 정의하는 데 실패하면 잘못된 문제를 해결하느라 많은 시간을 낭비한다.

> 프로그램 개발 프로세스
> - 문제 정의
> - 요구사항
> - 아키텍처
> - 구현
> - 시스템 테스트
> - 향후 개선

# 3.4 요구사항 선행 조건

요구사항은 소프트웨어 시스템이 무엇을 수행해야 하는지에 대해 상세하게 기술하고 해결책을 구하기 위한 첫번째 과정이다.

### 명시적인 요구사항 필요성

명시적 요구사항은 다음의 여러 가지 이유 때문에 중요하다.
- 명시적 요구사항은 개발자 대신 사용자가 시스템의 기능을 주도하게 하는 데 도움이 된다.
- 명시적 요구사항은 개발자, 사용자간의 논쟁을 피하게 해준다.
- 요구사항에 집중하면 개발을 시작하고 난 후 변경 사항을 최소화하는데 도움을 준다.
- 요구사항을 제대로 명시하는 것은 프로젝트 성공에 있어 효과적인 구현 기술보다 더 중요하다.

### 구현 중에 요구사항 변경 다루기

구현 중에 발생하는 요구사항의 변경을 잘 다루기 위한 몇 가지 방법이다.
- 요구사항 체크리스트로 요구사항의 품질을 평가한다.
- 모든 사람이 요구사항 변경 비용에 대해 알게 한다.
- 요구사항 변경 절차를 구축한다.
- 변경 사항들을 수용하는 개발 접근 방법을 사용한다.
- 프로젝트를 취소한다
- 프로젝트의 사업성을 주시한다.

요구사항 체크리스트의 내용에는 '구체적인 기능 요구사항', '비기능적 (품질) 요구사항', 요구사항의 품질, 요구사항의 완성도 등이 있다.

# 3.5 아키텍처 선행 조건

소프트웨어 아키텍처는 소프트웨어 설계의 상위 부분에 속하며 설계 중에서 더 상세한 부분을 담은 틀이다.  
전형적으로 아키텍처는 "아키텍처 명세서" 혹은 "최상위 설계" 라고 하는 문서 하나로 작성한다.

아키텍처가 선행 조건에 포함되는 이유는 아키텍처의 품질이 시스템의 개념적 무결성을 결정하기 때문이다. 이는 곧 시스템의 궁극적인 품질을 결정한다.  
좋은 아키텍처는 구현을 쉽게 만든다. 나쁜 아키텍처는 구현을 거의 불가능하게 만든다.  
아키텍처가 변경되면 구현이나 그 후의 작업에 많은 비용이 든다. 아키텍처 오류 수정은 코드 오류를 수정할 때가 아니라 요구사항 오류를 수정할 때 함께 진행해야 한다.

### 전형적인 아키텍처의 구성 요소

#### 프로그램 구조

우선 시스템 아키텍처는 시스템을 일반적인 말로 기술한 개요가 필요하다.  

아키텍처에서 최종 구조에 대한 대안을 고려했던 근거와 다른 대안들 대신 지금의 구조를 선택한 이유를 찾아야 한다.  

아키텍처는 프로그램 내의 중요한 빌딩 블록을 정의해야 한다.  
- 빌딩 블록은 하나의 독립된 클래스일 수도 있고 많은 클래스로 구성된 서브시스템일 수도 있다.
- 각 빌딩 블록은 하나의 클래스거나 상호자와 상호작용하거나 웹 페이지를 보여주거나 명령을 해석하거나 비즈니스 규칙을 캡슐화하거나 데이터에 접근하는 것과 같이 상위 수준의 기능을 처리하는 클래스나 루틴의 집합이다.
- 하나의 빌딩 블록은 반드시 한 분야를 책임져야 하며 다른 빌딩 블록에 대해 가능한 한 조금 알아야 한다.
- 각 빌딩 블록에 대한 커뮤니케이션 규칙도 명확하게 정의해야 한다.  
(직접적으로 사용할 수 있는 빌딩 블록, 간접적으로 사용할 수 있는 블록, 절대로 사용되서는 안되는 블록)

#### 주요 클래스

아키텍처는 주요 클래스를 명시해야 한다.
- 각각의 중요한 클래스가 맡은 역할과 클래스 사이의 상호작용을 어떻게 할 것인지를 규명해야 한다.
- 클래스 계층 구조와 상태 전이, 객체 지속성에 대한 설명도 포함해야 한다.
  - 클래스 계층 구조 : 주요 클래스들이 상속, 추상화, 인터페이스 등을 통해 어떤 관계를 가지는지 설명
  - 상태 전이 : 객체가 프로그램 실행 중 어떤 상태를 가지며, 어떤 사건에 의해 다른 상태로 변경되는지 설명하는 것
  - 객체 지속성 : 프로그램의 실행이 끝나거나 객체가 메모리에서 제거된 이후에도 객체의 중요한 상태를 어떻게 보존할 것인가
- 시스템이 꽤 크다면 클래스들의 서브시스템에 대해서도 기술해야 한다.

아키텍처는 고려했던 다른 클래스 설계에 대해서 기술하고 왜 지금가 같은 구조를 선택하게 되었는지에 대한 이유를 설명해야 한다.

#### 데이터 설계

아키텍처는 중요한 파일과 테이블 설계를 기술해야 한다. 또한 고려했던 다른 대안들에 대해 기술하고 현재의 방법을 선택한 이유를 설명해야 한다.

데이터는 일반적으로 하나의 서브시스템이나 클래스에서만 직접 접근해야 한다.

아키텍처는 모든 데이터베이스의 고수준 구조와 내용에 대해 명시해야 한다. 또한 데이터베이스의 타입, 이점, 연동성에서의 장점 등을 설명할 수 있어야 한다.

#### 비즈니스 규칙

아키텍처가 특정한 비즈니스 규칙을 따른다면 반드시 이를 규명해야 하고 그러한 규칙들이 시스템 설계에 미친 영향을 기술해야 한다.

#### 사용자 인터페이스 설계

아키텍처는 웹 페이지 형식, GUI, 명령줄 인터페이스 등 주요 요소를 명시해야 한다.

아키텍처는 비즈니스 규칙이나 프로그램의 결과에 영향을 미치지 않고 새로운 사용자 인터페이스로 대체할 수 있도록 모듈화되어야 한다.

#### 자원 관리

아키텍처는 데이터베이스 연결과 스레드(thread), 핸들(handle)과 같이 부족한 자원을 관리하기 위한 계획을 기술해야 한다.

아키텍처는 일반적인 상황과 최악의 상황에서 사용되는 자원을 측정해야 한다.

#### 보안

아키텍처는 설계 단계와 코드 단계의 보안에 대한 접근 방법을 기술해야 한다.

#### 성능

성능을 염려한다면 요구사항에 원하는 성능을 명시해야 한다. 속도나 메모리, 비용 같은 자원 사이의 우선순위를 성능 목표에 명시해야 하는 경우라면 자원 사용도 그 내용에 포함해야 한다.

아키텍처는 추정치를 제공해야 하며 설계자가 그러한 목표에 도달할 수 있는 이유를 설명해야 한다. 어떤 영역이 목표를 달성하지 못할 위험에 처해 있다면 그러한 내용에 대해서도 언급해야 한다.

#### 확장성

확장성은 추후의 요구를 충족시키기 위해 시스템이 확장할 수 있는 능력이다.  
시스템이 확장될 가능성이 없거나 확장성이 문제가 되지 않는다면 아키텍처는 그러한 가정에 대해 명시적으로 언급해야 한다.

#### 상호운용성

시스템이 다른 소프트웨어나 하드웨어와 함께 데이터나 자원을 공유할 거라고 예상된다면 아키텍처는 그러한 기능을 어떻게 구현할 것인지 기술해야 한다.

#### 국제화와 지역화

국제화는 프로그램이 여러 나라를 지원하기 위한 기술적 준비 작업이다. 지역화는 특정한 언어를 지원하기 위한 번역 작업이다.

#### 입력/출력

아키텍처는 입력 체계가 선행인지 후행인지, 아니면 상황에 따라 선택되는지 명시해야 한다.  
그리고 필드나 레코드, 스트림, 파일 수준에서 어떤 입출력 오류가 검출되는지를 명시해야 한다.

#### 오류 처리

오류 처리를 위해서는 굉장히 많은 코드가 작성되므로 오류를 처리하기 위한 일관된 방법이 아키텍처에 명시되어 있어야 한다.
