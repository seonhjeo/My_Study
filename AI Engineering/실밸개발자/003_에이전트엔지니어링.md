#  에이전틱 엔지니어링

[영상](https://www.youtube.com/watch?v=m99Vs94oHTQ)

바이브 코딩에서 나아긴 개념으로 다음과 같은 점이 추가되었다.
- AI가 구현하되, 인간이 아키텍처와 품질과 정확성을 소유
- 체계적 위임과 감독
- 5가지 핵심 개념이 있음

## 1. 에이전트

목표를 해석하고, 계획을 세우고, 도구슬 사용해 자율적으로 실행하는 주체
- 동작 방식 : 목표 해석 -> 계획 -> 실행 -> 평가 루프
- 도구 사용 : 파일 읽기/쓰기, 터미널, API 호출 등
- 자율성 : 목표만 주면 알아서 진행
- 오류 대응 : 스스로 감지하고 수정 시도

### Multi-Agent 오케스트레이션

#### Lost-in-the-middle 현상

하나의 컨텍스트 윈도우 안에서 여러 가지 작업을 시키면 컨텍스트가 길어질수록 성능이 떨어진다
- 연구에 따르면 컨텍스트 중간에 배치된 작업의 기억률이 극적으로 떨어진다

#### 멀티 에이전트 오케스트레이션

여러 개의 컨텍스트에 각각의 단일 작업을 집중시키고 그걸 총감독인 오케스트레이션 에이전트로 관리하는 구조

#### 예시 에이전트들
- Orchestration Agent : 메인 총감독 에이전트. 아래에 다음 에이전트들을 둔다
- 프론트엔드 전문 : 서브 에이전트. UI/UX, 컴포넌트, 스타일링 관리
- 백엔드 전문 : 서브 에이전트. API/비즈니스 로직/인프라 관리
- DB 설계 전문 : 서브 에이전트. 스키마, 쿼리 최적화, 마이그레이션 관리
- 테스트 전문 : 서브 에이전트. 유닛, 통합, E2E 테스트

오케스트레이터가 작업을 분해해 각각의 전문 서브 에이전트에 위임하고, 각 서브 에이전트는 독립적인 컨텍스트와 도구를 가지고 작업한 후 오케스트레이션에서 다시 결과를 통합한다. 이를 **Fan out(작업 분배) -> 병렬 실행 -> Fan in(결과 통합) 패턴이라 한다**


## 2. 컨텍스트 엔지니어링

기존 프롬프트 엔지니어링과의 차이점

| 프롬프트 엔지니어링       | 컨텍스트 엔지니어링            |
| ------------------- | --------------------- |
| 어떻게 물어볼지에 집중 | 어떤 정보를 제공할까에 집중 |
| 질문을 잘 쓰면 답이 나온다 | 무엇을, 언제 어떤 형태로 넣을지 체계적 설계       |
| 단일 상호작용 최적화 | 전체 시스템 최적화  |

### 컨텍스트 작성 예시

프롬프트 엔지니어링은 "맛있는 거 해줘" 라 단순히 묻는 거면, 컨텍스트 엔지니어링은 재료, 현재 인원, 알레르기와 같은 제약 사항, 예산 비용과 같은 자원 상황을 정보로 제공해준다.

### 컨텍스트의 3가지 레이어

시스템 컨텍스트
- 에이전트가 항상 참조하는 기본 설정
- CLAUDE.md, 프로젝트 규칙, 아키텍처 문서 등

Conversation Context
- 대화 과정에서 누적되는 정보
- 이전의 대화, 실행 결과, 사용자 피드백 등

Tool & Environment Context

도구 실행으로 얻는 실시간 정보
- 파일 내용, API 응답, 테스트 결과, MCP 데이터 등

### 컨텍스트 설계의 중요한 이유

컨텍스트는 3가지 압박을 받고 있다. 따라서 설계를 잘 해 압박을 최대한 풀어줘야 한다.

1. 비용과 지연 폭발
   - 컨텍스트가 커질수록 비용과 응답 시간이 급증한다.
   - 읽는 양(입력)이 답변(출력)의 100배 -> 넣는 만큼 토큰 소모
2. 신호 약화(Lost-in-the-middle)
   - 관련 없는 정보가 넘치면 모델이 핵심을 놓친다
   - 중간 정보의 회상률이 급락한다
3. 캐시 효율성
   - 같은 정보를 반복 전달하면 두 번째부터는 10분의 1 비용이다
   - 바뀌지 않는 정보를 앞에 고정 -> 캐시 극대화

핵심 원칙은 **필요한 정보만, 적시에, 적절한 형태로 제공해라**

#### CLAUDE.md 실전 예시

Claude.md에 프로젝트 사용 툴, 스타일, 테스트 방식, 사용 DB, 규칙 등을 미리 정의해두면 다음과 같은 이득을 얻는다.
- 매번 불필요한 설명 반복 불필요
- 에이전트가 프로젝트 맥락 파악한 상태로 시작
- 일관된 코딩 스타일 유지


# 3. Tool, Plugin & MCP

에이전트의 손과 발로써 에이전트가 실제 세계와 상호작용하는 수단으로 계층 구조를 이룬다.
- Tool (레벨 1) : 개별 함수. 파일 읽기, 터미널 실행, 웹 검색
- Plugin (레벨 2) : Tool의 묶음. Github 플러그인 (PR 조회 + 생성 + 리뷰)
- MCP(레벨 3) : 표준 프로토콜. 모든 Tool/Plugin을 표준화된 인터페이스로 연결

## Tool 설계 4가지 원칙

최소 권한 원칙
- 필요한 Tool만 노출
- 너무 많으면 혼란, 너무 적으면 불능

검증 가능성
- Tool 호출 결과를 인간이 쉽게 확인
- 투명성이 신뢰를 만든다

에러 핸들링 내장
- 실패 시 대안 경로 선택 가능
- Github API 무응답 -> 로컬 캐시 사용

보안 경계 설정
- 읽기 전용 vs 쓰기 가능 명확 구분
- 프로덕션 DB 보호


# 4. Hook & Skill

에이전트의 행동을 제어하는 데 사용한다

## Hook

에이전트의 워크플로우 특정 지점에서 자동으로 실행되는 인터셉터
- A일이 발생하면 B 작업도 수행하라

### Hook의 4가지 유형

Hook 유형 | 동작 시점 | 실전 예시
--------- | --------- | --------
Pre-action | 에이전트가 행동하기 전 | 코드 저장 전 lint 자동 실행
Post-action | 에이전트가 행동한 후 | 커밋 후 자동 테스트 실행
Validation | 에이전트 출력의 품질 검증 | 보안 취약점 스캔
Notification | 특정 조건 충족 시 인간에게 알림 | 비용 임계치 초과 경고

### Claude Code Hook 실전 예시

- 파일 변경 시 -> 관련 테스트 자동 실행
- package.json 수정 시 -> 의존성 충돌 검사
- 보안 관련 파일 수정 시 -> 보안 리뷰 에이전트 자동 호출
- 토큰 사용량 초과 시 -> 컨텍스트 압축 트리거

에이전트가 알아서 작업하더라도, 위험한 순간에 자동으로 안전장치가 작동


## Skill

에이전트가 특정 작업을 수행할 때 참조하는 Best Practice 문서 같은 것  
보통 SKILLS.md 파일로 정의

- PPT를 만들 때 스킬을 이용해 원하는 방향으로 커스터마이징 가능, 스킬이 없을 시 제네릭한 결과물이 나옴

## Hook + Skill 시너지

Hook은 감지, Skill은 행동을 수행한다.

 Hook | Skill
 ---- | ----
.pptx 생성 감지 | pptx 베스트 프랙티스 자동 로드
보안 코드 변경 감지 | 보안 리뷰 체크리스트 자동 적용
API 통합 코드 감지 | 해당 API 가이드라인 자동 주입

## 맞춤법 검사 + 스타일 가이드 비용

Hook : 맞춤법 자동 검사
- 글을 쓰는 순간 자동으로 오류 감지
- 빨간 밑줄로 즉시 피드백
- 없으면 오타투성이가 됨

Skill : 글쓰기 스타일 가이드
- 이런 상황에서는 이렇게 써라
- 베스트 프랙티스 참조
- 없으면 글이 중구난방됨

둘 다 있어야 깔끔한 결과물이 나온다


# 5. Planning & Human in the loop

## Planning Loop

에이전트를 단순한 챗봇과 구분짓는 가장 핵심적인 특성은 계획-실행 검증 루프이다.  
- 에이전트는 한 번에 답을 뱉는 게 아니라 반복적인 사고 루프를 돈다.
- 한 번에 완벽한 결과를 뱉는 게 아니라 계속 수정하면서 목표에 수렴해 나가는 것이다.

## 위임의 스펙트럼

레벨이 낮을수록 에이전트의 자율성이 높다

  - | Level 1 - 완전 자율 | Level 2 - 감독 위임 | Level 3 - 협업 | Level 4 - 인간 주도
---- | ---- | ---- | ---- | ----   
인간이 하는 일 | 결과만 확인 | 계획 승인 후 위임 | 핵심 결정 개입 | 직접 설계 및 지시
에이전트가 하는 일 | 계획부터 실행까지 전부 수행 | 계획 + 실행 | 실행과 보조 | 구현 보조
적합한 직업 | 보일러플레이트 작성, 리팩터링 | 새 기능, 버그 수정 | 아키텍처, 보안 코드 | 아키텍처, 보안 코드

## 위임 직감 키우기

작업이 주어졌을 때 내가 결과를 빠르게 검증할 수 있는가를 바탕으로 위임의 범위를 정한다

빠르게 검증 가능할 시
- 에이전트에 위임한다
- 보일러플레이트, 리팩터링, 테스트 작성, 버그 재현 등

빠르게 검증이 불가능할 시
- 직접 하거나 협업한다
- 아키텍처 결정, 보안 민감 코드, 성능 크리티컬 등

처음에는 조심스럽게 시작해서 경험이 쌓이면 점차 범위를 넓혀간다

## 검증 체계

바이브 코딩과 에이전틱 엔지니어링의 가장 큰 차이는 테스트이다.  
견고한 테스트 스위트가 있으면 AI 에이전트가 테스트가 통과할 때까지 반복할 수 있고, 결과에 높은 확신을 가질 수 있다.

- 테스트가 존재할 시에는 명확한 성공 기준이 있으므로 테스트 통과가 완료가 되고 결과물에 높은 확신을 가진다.
- 테스트가 없을 시에는 기준이 없으므로 깨진 코드에 완료를 선언할 수 있게 되어 확신이 불가능하다.

# 정리

- 컨텍스트 엔지니어링으로 에이전트와 서브 에이전트의 두뇌를 설게한다
- 훅과 스킬로 에이전트들의 품질을 제어한다
- 툴과 MCP를 주어 에이전트의 손과 발을 커넥트한다
- 감독과 플래닝으로 에이전트에게 자율성을 준다

## 한 줄 요약

개념 | 한 줄 요약
---- | ----
Agent & Sub-Agent | 계층적으로 위임하고 병렬로 실행한다
Context Engineeering | 에이전트에게 줄 정보를 전략적으로 설계한다
Tool & MCP | 표준화된 도구로 에이전트의 행동 반경을 넓힌다
Hook & Skill | 자동 안전장치와 전문 지식으로 품질을 제어한다
Planning & HITL | 계획 - 실행 - 검증 루프를 돌리되 인간이 감독한다

## 핵심 메시지

Agent가 Context를 바탕으로 Plan을 세우고,  
Tool/MCP를 사용해 실행하고,  
Hook과 Skill로 품질을 제어하고,  
Human이 감독한다
